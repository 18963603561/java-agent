# Shannon 对齐（LLM 压缩 + 三段滑窗）P0 包设计改造任务清单

## 1. 目标

- 面向“包设计合理性”完成 P0 阶段改造清单细化。
- 优先解决职责混杂、跨层依赖、可替换性不足问题，为 P1 的 LLM 压缩接入提供稳定骨架。
- 约束：P0 只做架构骨架与边界治理，不做大规模业务语义改写。

## 2. 当前包设计问题（P0 视角）

1) `budget.trim` 包同时承担了触发策略、执行编排、结果回填、指标记录，职责过重。  
涉及：`ContextCompressionService`、`DefaultCompressionExecutionService`、`DefaultCompressionSummaryApplier`、`DefaultCompressionTriggerPolicy`。

2) 压缩执行能力缺少稳定端口抽象，未来 LLM 压缩与 rule 压缩只能通过服务内分支扩展，演进成本高。  
涉及：`CompressionExecutionService` 当前只表达“执行”，未表达“模式路由/失败降级上下文”。

3) 上下文构建层直接感知压缩细节，耦合过深。  
涉及：`DefaultContextBuilder` 直接构建 `ContextCompressionRequest` 并调用压缩服务。

4) 压缩域模型分散在 `budget.trim.model`，与上下文装配/LLM 路由语义边界不清。  
涉及：`ContextCompressionRequest/Result`、`CompressionExecutionResult`。

5) 触发策略与窗口策略未分层，后续接入三段滑窗会继续堆叠在同一包内。  
涉及：`DefaultCompressionTriggerPolicy`、`MemoryPolicy`。

## 3. P0 具体改造任务（按包设计合理性）

---

### P0-PKG-001：建立“压缩能力”独立边界包（先增量，不做大迁移）

- 任务目标：从 `budget.trim` 中抽出稳定入口，形成单一编排门面。
- 具体动作：
  - 新增包：`com.example.agent.capabilities.context.compression`
  - 新增门面：`ContextCompressionFacade`（仅暴露 `compressIfNeeded`）
  - `DefaultContextBuilder` 只依赖 Facade，不再依赖具体执行/触发实现。
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/DefaultContextBuilder.java`
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/ContextCompressionFacade.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/DefaultContextCompressionFacade.java`
- 验收标准：
  - 构建层不再直接依赖 `CompressionExecutionService` 与 `CompressionTriggerPolicy`。

---

### P0-PKG-002：压缩执行能力改为 Port/Adapter 结构

- 任务目标：把 rule/llm/hybrid 的可替换性放到包结构层，而非 `if/else` 里。
- 具体动作：
  - 新增应用端口包：`...compression.application.port`
  - 定义端口：`CompressionExecutor`、`CompressionModeResolver`
  - 新增适配包：
    - `...compression.infrastructure.rule`（现有 rule 执行适配）
    - `...compression.infrastructure.llm`（P0 先放占位 Adapter 与超时降级骨架）
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/application/CompressionExecutionService.java`
  - `src/main/java/com/example/agent/budget/trim/application/DefaultCompressionExecutionService.java`
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/port/CompressionExecutor.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/application/CompressionExecutionRouter.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/infrastructure/rule/RuleCompressionExecutorAdapter.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/infrastructure/llm/LlmCompressionExecutorAdapter.java`
- 验收标准：
  - 执行路径可通过模式路由切换，不改调用方代码。

---

### P0-PKG-003：触发策略与窗口策略拆包（策略分层）

- 任务目标：为后续三段滑窗能力预留独立策略位，避免策略类持续膨胀。
- 具体动作：
  - 新增包：`...compression.domain.policy`
  - 触发策略接口归一：`CompressionTriggerPolicy`（预算阈值、比例阈值统一入口）
  - 窗口策略占位：`HistoryWindowPolicy`（P0 仅定义接口与默认实现占位）
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/application/DefaultCompressionTriggerPolicy.java`
  - `src/main/java/com/example/agent/capabilities/memory/policy/MemoryPolicy.java`
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/HistoryWindowPolicy.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/DefaultHistoryWindowPolicy.java`
- 验收标准：
  - 触发策略与窗口策略物理隔离，P2 可直接挂接 `shapeHistory` 实现。

---

### P0-PKG-004：配置模型按“功能子域”收敛

- 任务目标：配置键与包结构对齐，减少配置散落与语义漂移。
- 具体动作：
  - 扩展 `ContextCompressionProperties` 为分组配置：
    - `mode`（rule/llm/hybrid）
    - `trigger`（预算阈值/比例阈值）
    - `window`（primers/recents）
    - `llm`（scene/timeout/retry/fallback）
  - 配置保留向后兼容映射（旧 key 不立即删除）。
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/config/ContextCompressionProperties.java`
  - `src/main/resources/application.yml`
  - `src/main/resources/application.yml.example`
- 验收标准：
  - 新配置可表达 P1/P2 需求，旧配置仍可运行。

---

### P0-PKG-005：压缩域模型统一并建立防腐层

- 任务目标：避免上下文层、预算层、LLM 层直接共享底层模型导致连带修改。
- 具体动作：
  - 在压缩域定义统一对象：`CompressionCommand`、`CompressionOutcome`。
  - 现有 `ContextCompressionRequest/Result` 仅作为上游入参/出参，不承载 LLM 细节。
  - 通过 Mapper 做对象转换，隔离 `ModelRequest` 等外部模型。
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/model/ContextCompressionRequest.java`
  - `src/main/java/com/example/agent/budget/trim/model/ContextCompressionResult.java`
  - `src/main/java/com/example/agent/budget/trim/model/CompressionExecutionResult.java`
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/model/CompressionCommand.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/model/CompressionOutcome.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/application/CompressionModelMapper.java`
- 验收标准：
  - 压缩域对象不直接暴露 LLM SDK/Provider 类型。

---

### P0-PKG-006：可观测性改为端口化依赖

- 任务目标：压缩核心域不直接依赖 `MetricsPublisher`，降低基础设施耦合。
- 具体动作：
  - 抽象端口：`CompressionTelemetryPort`。
  - 由适配器桥接到 `MetricsPublisher`。
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
  - `src/main/java/com/example/agent/budget/trim/application/DefaultCompressionExecutionService.java`
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/port/CompressionTelemetryPort.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/infrastructure/telemetry/MetricsCompressionTelemetryAdapter.java`
- 验收标准：
  - 核心编排逻辑可在不注入 `MetricsPublisher` 的单测环境下运行。

### P0-PKG-007：测试包按新边界重组（先增量）

  - `src/test/java/com/example/agent/context/DefaultContextBuilderTest.java`（改为依赖 Facade）

## 4. P0 实施顺序（建议）

1) `P0-PKG-001`（先建门面）  
2) `P0-PKG-002`（再做执行路由）  
3) `P0-PKG-004`（补配置骨架）  
4) `P0-PKG-005`（模型防腐）  
5) `P0-PKG-003`（策略拆包）  
6) `P0-PKG-006`（端口化观测）  
7) `P0-PKG-007`（测试重组）

## 5. P0 完成判定

- 包层面具备“门面 -> 应用路由 -> 端口 -> 适配器”的清晰依赖方向。  
- `DefaultContextBuilder` 不再直接耦合压缩细节实现类。  
- 新增 LLM 压缩时仅新增 Adapter 与 Prompt 相关实现，不修改上游调用链路。  
- 为 P1/P2 留出扩展点（`ModelScene.CONTEXT_COMPRESS`、`HistoryWindowPolicy`、`CompressionModeResolver`）。
