# Shannon 对齐（LLM 压缩 + 三段滑窗）P1 包设计改造任务清单

## 1. 目标与边界

- 目标：在已完成 P0 包边界治理基础上，落地可用的 `LLM` 压缩主能力，并保持包职责清晰、扩展路径稳定。
- 边界：P1 聚焦“能力落地 + 包结构合理性”，不在本阶段实现完整三段滑窗整形（该部分在 P2 完成）。
- 原则：
  - 调用链方向固定为：`Facade -> Application -> Port -> Adapter`。
  - 上游构建层不感知 `LLM SDK` 与 Provider 细节。
  - 失败可降级、过程可观测、参数可配置、行为可测试。

## 2. P0 基线（作为 P1 输入）

- 已具备压缩门面：`ContextCompressionFacade`。
- 已具备执行路由：`CompressionExecutionRouter`。
- 已具备执行端口：`CompressionExecutor`、`CompressionModeResolver`、`CompressionTelemetryPort`。
- 已具备模式适配器骨架：`RuleCompressionExecutorAdapter`、`LlmCompressionExecutorAdapter`（占位）。
- 已具备配置子域：`mode / trigger / window / llm`。
- 已具备策略拆包：`CompressionTriggerPolicy` 与 `HistoryWindowPolicy`。

## 3. P1 包设计合理性问题（需解决）

1) `LlmCompressionExecutorAdapter` 仍为占位实现，缺少独立应用编排服务，导致适配器将来可能膨胀。  
2) 压缩提示词构建与输出解析尚未形成独立包，后续演进易出现“执行器 + Prompt + 解析”耦合。  
3) 压缩失败语义仅有简单原因码，缺少可扩展的降级策略端口。  
4) 摘要写回虽可用，但尚未拆出“安全治理与长度治理”子能力边界。  
5) 可观测性已端口化，但缺少 LLM 专项维度（场景、降级类型、重试结果）的统一事件语义。

## 4. P1 具体改造任务（按包设计合理性）

---

### P1-PKG-001：落地 LLM 压缩应用编排服务（避免 Adapter 过重）

- 任务目标：将 LLM 调用编排从 Adapter 中拆出，形成稳定应用服务。
- 具体动作：
  - 新增应用服务：`LlmCompressionOrchestrator`。
  - `LlmCompressionExecutorAdapter` 仅负责端口适配与调用委派。
  - 编排服务负责：请求构造、模型调用、重试/超时、结果校验、失败码映射。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/LlmCompressionOrchestrator.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/application/model/LlmCompressionCommand.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/application/model/LlmCompressionResult.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/infrastructure/llm/LlmCompressionExecutorAdapter.java`
- 验收标准：
  - `Adapter` 类不包含 Prompt 拼装与解析逻辑。
  - LLM 调用失败可返回结构化失败原因，不抛出到上游主链路。

---

### P1-PKG-002：建立 Prompt 子包，隔离提示词资产与输入整形

- 任务目标：确保提示词资产与执行编排解耦，支持模板演进与 A/B。
- 具体动作：
  - 新增 `prompt` 子包，集中管理系统提示、约束、输出格式。
  - 抽象 `CompressionPromptBuilder` 接口与默认实现。
  - 明确输入模型：只接受压缩域对象，不直接接触外部 SDK 请求对象。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/prompt/CompressionPromptBuilder.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/prompt/DefaultCompressionPromptBuilder.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/prompt/CompressionPromptTemplate.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/LlmCompressionOrchestrator.java`
- 验收标准：
  - Prompt 变更无需修改执行器与路由层代码。
  - Prompt 内容可在单测中独立验证（长度、字段完整性、约束语义）。

---

### P1-PKG-003：建立 LLM 输出解析/校验子包（防腐层）

- 任务目标：将模型原始输出与压缩域结果隔离，避免解析逻辑污染业务编排。
- 具体动作：
  - 新增 `parser` 子包：解析 JSON 文本、容错处理、字段校验。
  - 定义解析结果对象，包含 `success / summary / reason / violations`。
  - 统一失败码，如：`LLM_TIMEOUT`、`LLM_EMPTY`、`LLM_PARSE_ERROR`、`LLM_POLICY_REJECTED`。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/parser/CompressionResponseParser.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/parser/CompressionParseResult.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/parser/CompressionValidationPolicy.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/LlmCompressionOrchestrator.java`
  - `src/main/java/com/example/agent/budget/trim/model/CompressionExecutionResult.java`
- 验收标准：
  - 主链路不直接解析 LLM 原始文本。
  - 解析失败与业务失败可通过失败码清晰区分。

---

### P1-PKG-004：降级策略端口化（规则降级策略可替换）

- 任务目标：将“是否降级、如何降级”从路由硬编码中抽离。
- 具体动作：
  - 新增策略端口：`CompressionFallbackPolicy`。
  - 默认实现支持：`llm -> rule` 与 `llm -> none` 两类策略。
  - 路由层仅执行策略决策，不编码业务策略细节。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/CompressionFallbackPolicy.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/DefaultCompressionFallbackPolicy.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/CompressionExecutionRouter.java`
  - `src/main/java/com/example/agent/budget/trim/config/ContextCompressionProperties.java`
- 验收标准：
  - 切换降级策略仅改配置或策略实现，不改路由调用方。
  - 降级路径在指标和结果对象中可明确识别。

---

### P1-PKG-005：摘要写回能力拆分“治理层”

- 任务目标：在回填前增加统一安全治理与质量治理边界。
- 具体动作：
  - 在 `summary` 子包新增治理组件：长度限制、敏感信息治理、空摘要拦截。
  - `DefaultCompressionSummaryApplier` 专注“字段映射与回填”，不做复杂治理判断。
  - 输出治理结果标签，用于后续审计与指标聚合。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/summary/CompressionSummaryGuard.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/summary/CompressionSummaryGuardResult.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/application/DefaultCompressionSummaryApplier.java`
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
- 验收标准：
  - 摘要写回前必须经过治理层。
  - 治理失败不破坏主链路，且返回可观测失败原因。

---

### P1-PKG-006：LLM 压缩配置校验器独立成包

- 任务目标：防止配置无效值扩散到运行期分支。
- 具体动作：
  - 新增配置校验器：校验 `timeout/retry/ratio/fallback/scene`。
  - 在启动期输出结构化告警，必要时拒绝启动（可配置）。
  - 为旧键兼容映射增加弃用告警。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/config/CompressionConfigValidator.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/config/CompressionConfigValidationResult.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/config/ContextCompressionProperties.java`
  - `src/main/resources/application.yml`
  - `src/main/resources/application.yml.example`
- 验收标准：
  - 无效配置可在启动期或首个调用前被识别并告警。
  - 配置异常不会以空指针或隐式默认值形式泄漏到业务流程。

---

### P1-PKG-007：LLM 压缩可观测语义扩展

- 任务目标：实现“触发-调用-降级-回填”的完整观测闭环。
- 具体动作：
  - 增加指标维度：`mode/source/fallback/failure_reason/retry_count`。
  - 增加关键日志节点：调用开始、调用结束、降级决策、回填结果。
  - 在 `CompressionExecutionResult` 与 `ContextCompressionResult` 保留必要观测字段。
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/infrastructure/telemetry/MetricsCompressionTelemetryAdapter.java`
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
  - `src/main/java/com/example/agent/budget/trim/model/CompressionExecutionResult.java`
  - `src/main/java/com/example/agent/budget/trim/model/ContextCompressionResult.java`
- 验收标准：
  - 能区分“LLM 成功 / LLM 失败后规则降级成功 / 全链路失败”。
  - 关键路径日志与指标字段一致，可互相对账。

---

  - 失败用例可定位到单一子层（编排/提示词/解析/策略）。

## 5. P1 推荐实施顺序

1) `P1-PKG-001`（先打通 LLM 编排）  
2) `P1-PKG-002`（再拆 Prompt 资产）  
3) `P1-PKG-003`（补解析与校验防腐）  
4) `P1-PKG-004`（抽降级策略端口）  
5) `P1-PKG-005`（落摘要治理边界）  
6) `P1-PKG-006`（加配置校验器）  
7) `P1-PKG-007`（完善可观测闭环）  
8) `P1-PKG-008`（补齐测试与守卫）

## 6. P1 完成判定

- `LLM` 压缩在新包结构下可独立运行，且上游调用链无需改动。
- 执行器、Prompt、解析器、降级策略、摘要治理各自独立成层。
- 失败原因码、降级行为、指标日志可统一对齐。
- 后续 P2 接入“三段滑窗整形”时仅需新增窗口策略实现，不改 P1 主编排骨架。
