# Shannon 对齐（LLM 压缩 + 三段滑窗）P2 包设计改造任务清单

## 1. 目标与边界

- 目标：在 P1 已具备 `LLM` 压缩能力的基础上，完成“三段式滑窗 + 摘要注入装配”的包级能力闭环，使压缩从“可调用”升级为“可稳定复用”。
- 边界：P2 聚焦包设计合理性与职责收敛，核心是“策略可替换、链路可观测、模型可扩展”，不做 P3 的外部契约文档对齐。
- 原则：
  - 依赖方向固定：`Builder/Assembler -> Facade -> Application -> Domain Policy -> Adapter`。
  - 三段滑窗与压缩执行解耦：窗口整形不依赖具体 `rule/llm` 执行实现。
  - 摘要注入在装配层统一治理：禁止分散到 Builder、Prompt 模板、压缩执行器多处重复拼装。

## 2. 当前 P2 视角的包设计问题

1) `HistoryWindowPolicy` 仅返回 `ContextSnapshot`，无法表达“首段保留条数/尾段保留条数/中段是否被压缩”等整形元数据，导致装配层和观测层无法感知整形结果。  
涉及：`src/main/java/com/example/agent/capabilities/context/compression/domain/policy/HistoryWindowPolicy.java`

2) `DefaultHistoryWindowPolicy` 当前是透传实现，尚未形成独立“三段滑窗”策略实现类，后续叠加逻辑将继续压入服务层。  
涉及：`src/main/java/com/example/agent/capabilities/context/compression/domain/policy/DefaultHistoryWindowPolicy.java`

3) `ContextCompressionService` 目前关注“触发判定 + 执行压缩 + 摘要回填”，尚未纳入“窗口整形”职责接口，链路缺失 `shape -> compress -> apply` 的明确阶段。  
涉及：`src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`

4) `DefaultContextAssembler` / `PromptContextPolicyApplier` 尚未建立“摘要注入策略”专用边界，只有通用 `system/developer/user` 文本填充，无法表达 `context_summary` 注入策略。  
涉及：
`src/main/java/com/example/agent/capabilities/context/assembly/DefaultContextAssembler.java`  
`src/main/java/com/example/agent/capabilities/context/assembly/PromptContextPolicyApplier.java`

5) `ContextCompressionResult` 缺少窗口整形与注入结果字段，导致后续指标、日志、事件无法统一复盘“为何触发 + 如何整形 + 是否注入”。  
涉及：`src/main/java/com/example/agent/budget/trim/model/ContextCompressionResult.java`

6) 配置层已具备 `window/trigger` 基础字段，但缺少跨字段约束与注入配置分组，难以防止“触发比例与目标比例关系错误”“注入策略缺省歧义”。  
涉及：
`src/main/java/com/example/agent/budget/trim/config/ContextCompressionProperties.java`  
`src/main/java/com/example/agent/capabilities/context/compression/config/CompressionConfigValidator.java`

## 3. P2 具体改造任务（按包设计合理性）

---

### P2-PKG-001：重定义历史窗口策略契约（从“快照透传”升级为“整形结果对象”）

- 任务目标：让窗口策略既返回整形后快照，也返回可观测元数据，避免后续层级重复计算。
- 具体动作：
  - 将 `HistoryWindowPolicy` 入参/出参改为命令对象与结果对象（如 `HistoryWindowShapeCommand`、`HistoryWindowShapeResult`）。
  - 结果对象最少包含：`primersRetained`、`recentsRetained`、`middleWindowSize`、`windowShaped`、`shapeReason`。
  - 保留默认无副作用实现作为兜底策略，但统一走结果对象。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/model/HistoryWindowShapeCommand.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/model/HistoryWindowShapeResult.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/HistoryWindowPolicy.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/DefaultHistoryWindowPolicy.java`
- 验收标准：
  - 上游调用方不再自行计算窗口统计字段。
  - 触发压缩链路可直接消费窗口整形结果，不依赖内部实现细节。

---

### P2-PKG-002：落地 Shannon 风格三段滑窗策略实现（Primers + Middle + Recents）

- 任务目标：将三段式窗口逻辑集中在策略实现层，禁止在服务层硬编码首尾切片。
- 具体动作：
  - 新增 `ThreeSegmentHistoryWindowPolicy`（或等效命名）实现三段切分与边界处理。
  - 明确边界语义：当 `primers + recents >= total` 时返回“未整形”并给出 `shapeReason=WINDOW_TOO_SMALL`。
  - 中段作为压缩输入窗口来源，首段与尾段保持原序。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/policy/ThreeSegmentHistoryWindowPolicy.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/config/ContextCompressionProperties.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/config/CompressionConfigValidator.java`
- 验收标准：
  - 三段窗口规则仅在 `HistoryWindowPolicy` 实现中出现。
  - 配置非法值（负数、过大）可在启动期或首调期识别。

---

### P2-PKG-003：在压缩应用服务中建立“整形 -> 执行 -> 回填”阶段编排

- 任务目标：把窗口整形接入主编排，形成可追踪阶段边界。
- 具体动作：
  - 在 `ContextCompressionService` 中显式接入 `HistoryWindowPolicy`。
  - 使用整形结果构建压缩命令，避免压缩执行器再做窗口判定。
  - 统一记录阶段结果：`shapeStart/shapeEnd/shapeSkipped`。
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/application/CompressionModelMapper.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/domain/model/CompressionCommand.java`
- 验收标准：
  - 压缩执行器收到的是“已整形输入”，不再关心三段策略细节。
  - 日志可区分“未触发压缩”和“触发但窗口无需整形”两类场景。

---

### P2-PKG-004：装配层新增摘要注入策略边界（context_summary）

- 任务目标：摘要注入逻辑从通用文本填充中分离，形成可替换注入策略。
- 具体动作：
  - 新增注入策略接口（如 `ContextSummaryInjectionPolicy`）与默认实现。
  - `DefaultContextAssembler` 仅编排注入调用，不持有注入细节判断。
  - `PromptContextPolicyApplier` 保留通用 role 填充职责，避免继续扩张为“万能装配器”。
- 计划新增文件：
  - `src/main/java/com/example/agent/capabilities/context/assembly/ContextSummaryInjectionPolicy.java`
  - `src/main/java/com/example/agent/capabilities/context/assembly/DefaultContextSummaryInjectionPolicy.java`
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/assembly/DefaultContextAssembler.java`
  - `src/main/java/com/example/agent/capabilities/context/assembly/PromptContextPolicyApplier.java`
  - `src/main/java/com/example/agent/capabilities/context/assembly/PromptAssemblyInput.java`
- 验收标准：
  - 关闭注入开关后，装配路径不出现摘要文本。
  - 开启注入时，注入位置、注入角色、注入来源可追踪。

### P2-PKG-005：扩展压缩结果模型，承载窗口与注入元数据

- 任务目标：让结果模型成为跨层统一事实源，避免指标与事件层二次猜测。
- 具体动作：
  - 在 `ContextCompressionResult` 增加字段：`windowShaped`、`shapeReason`、`primersRetained`、`recentsRetained`、`summaryInjected`、`summaryInjectReason`。
  - 在 `CompressionExecutionResult` 或等效执行结果中补齐 `targetRatio`、`actualRatio`、`targetMet`（如尚缺失）。
  - `DefaultContextAssembler` 的 `assemblyMetadata` 统一取值于结果模型。
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/model/ContextCompressionResult.java`
  - `src/main/java/com/example/agent/budget/trim/model/CompressionExecutionResult.java`
  - `src/main/java/com/example/agent/capabilities/context/assembly/DefaultContextAssembler.java`
- 验收标准：
  - 压缩与装配关键事件可由同一组字段还原执行事实。
  - 不同模式（rule/llm/hybrid）的结果字段语义保持一致。

### P2-PKG-006：配置分组补齐“注入子域”，并增加跨字段校验

- 任务目标：让 `window`、`trigger`、`injection` 三组配置语义闭合，防止运行时歧义。
- 具体动作：
  - 在 `ContextCompressionProperties` 增加 `injection` 子配置：`enabled`、`role`、`maxChars`、`attachTag`。
  - 在 `CompressionConfigValidator` 增加跨字段校验：`triggerRatio >= targetRatio`、`primers + recents` 边界、注入 `role` 枚举合法性。
  - 将默认值同步到 `application.yml` 与 `application.yml.example`。
- 计划修改文件：
  - `src/main/java/com/example/agent/budget/trim/config/ContextCompressionProperties.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/config/CompressionConfigValidator.java`
  - `src/main/resources/application.yml`
  - `src/main/resources/application.yml.example`
- 验收标准：
  - 非法组合在启动期可识别并阻断或告警。
  - 配置键可直接映射到 P2 包边界，无跨包语义漂移。

### P2-PKG-007：可观测语义补齐为“触发-整形-压缩-注入”四段闭环

- 任务目标：补齐阶段性指标与日志，支撑线上定位与效果评估。
- 具体动作：
  - 在压缩服务与装配服务增加阶段事件：`shape_applied`、`shape_skipped`、`summary_injected`、`summary_injection_skipped`。
  - `CompressionTelemetryPort` 增加窗口/注入维度标签（`window_shaped`、`injected`、`shape_reason`）。
  - 指标字段与日志字段命名保持一致，避免同义多名。
- 计划修改文件：
  - `src/main/java/com/example/agent/capabilities/context/compression/application/port/CompressionTelemetryPort.java`
  - `src/main/java/com/example/agent/capabilities/context/compression/infrastructure/telemetry/MetricsCompressionTelemetryAdapter.java`
  - `src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
  - `src/main/java/com/example/agent/capabilities/context/DefaultContextBuilder.java`
- 验收标准：
  - 任意一次压缩请求均可判定处于四段中的哪个阶段失败或跳过。
  - 指标与日志可交叉对账，避免观测口径冲突。

## 4. P2 推荐实施顺序

1) `P2-PKG-001`（先重定义窗口策略契约）  
2) `P2-PKG-002`（再落地三段滑窗策略实现）  
3) `P2-PKG-003`（接入主编排阶段链路）  
4) `P2-PKG-005`（统一结果模型语义）  
5) `P2-PKG-004`（补装配层摘要注入边界）  
6) `P2-PKG-006`（收敛配置与校验）  
7) `P2-PKG-007`（补观测闭环）  
8) `P2-PKG-008`（补齐测试契约）

## 5. P2 完成判定

- 三段式滑窗逻辑只存在于窗口策略实现层，不散落在服务或装配层。  
- 压缩链路具备清晰阶段：`trigger -> shape -> compress -> apply -> assemble`。  
- 摘要注入成为可配置、可测试、可观测的独立子域能力。  
- 结果模型字段可完整复盘一次压缩是否触发、是否整形、是否注入、是否达成目标比例。  
- P3 可以直接在 P2 输出字段基础上做契约与外部文档对齐，无需再次回改包边界。
