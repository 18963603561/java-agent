# 压缩包设计边界评估（`budget` vs `capabilities/context/compression`）

## 1. 你问的问题（直接结论）

结论：**是的，这两个目录当前都包含“压缩相关实现”**，并且已经出现了较明显的边界交叉。  
进一步结论：不是“完全不合理”，但按包设计与职责边界看，**当前状态属于“部分合理 + 明显耦合过深”**，建议收敛。

## 3. 合理性评估

## 3.1 合理的部分

1. 从业务语义上，“预算触发压缩”放在 `budget.trim` 可以成立。  
2. 从能力语义上，“压缩执行与策略域（rule/llm/experiment）”放在 `capabilities/context/compression` 也可以成立。  

也就是说，“两个目录都涉及压缩”**并非天然错误**。

## 3.2 不合理的部分（当前主要问题）

1. **边界不闭合**：出现双向依赖，包职责不再清晰。  
2. **模型归属混乱**：`capabilities` 领域模型直接引用 `budget.trim.model`。  
3. **配置归属混乱**：压缩配置在 `budget`，却由 `capabilities` 直接消费。  
4. **门面方向反直觉**：`capabilities` 的门面实现反向依赖 `budget` 主服务。

综合判断：当前包设计状态应定性为 **“中度不合理（可运行，但可维护性风险上升）”**。

---

## 4. 风险影响

1. 未来调整压缩策略时，容易同时改两边，变更面扩大。  
2. 单测与架构守卫会越来越依赖“约定”而不是“结构自然约束”。  
3. 新成员理解成本高：难判断“压缩问题应该改 budget 还是 capabilities”。

---

## 5. 建议的目标边界（推荐）

推荐采用：**预算域只做“是否触发”，压缩能力域做“如何压缩”**。

### 5.1 目标职责

- `budget`：
  - 预算分配、预算裁剪、触发信号。
  - 不承载压缩执行细节与压缩实验治理细节。

- `capabilities/context/compression`：
  - 压缩命令/结果契约、模式路由、LLM 编排、三段滑窗、双轨实验、质量评估、回滚、观测。

### 5.2 最小落地路径（不一次性大搬家）

P0（必须）：
1. 新建压缩契约层（例如 `capabilities/context/compression/contract`），把 `ContextCompressionRequest/Result`、`CompressionExecutionResult` 从 `budget.trim.model` 迁出。  
2. `capabilities/context/compression` 不再 import `budget.trim.model` 与 `budget.trim.config`。  

P1（高优先）：
1. 把 `ContextCompressionProperties` 迁到 `capabilities/context/compression/config`，`budget` 仅通过接口读取压缩触发相关子集。  
2. 让 `ContextCompressionService` 只依赖 `ContextCompressionFacade`（端口），移除对执行域细节类的直接 import。

P2（中优先）：
1. 补架构守卫：禁止 `capabilities/context/compression/**` import `budget.trim.**`。  
2. 保留 `budget.trim` 中“裁剪/估算”职责，压缩能力类逐步收口到 `capabilities/context/compression`。

---

## 6. 结论（最终回答）

你的问题答案是：

1. **是的，两个包都包含压缩。**  
2. **当前包设计有不合理点，核心是不该出现双向依赖与模型/配置所有权混杂。**  
3. 建议按“预算触发 vs 压缩能力”做边界收敛，先做契约与配置归属拆分，再做服务依赖收口。
