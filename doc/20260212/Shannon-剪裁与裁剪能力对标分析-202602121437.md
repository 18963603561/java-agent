## 3. Shannon 的压缩实现细节

### 3.1 判定层

1. 先估算 token（主要按字符近似，非精确 tokenizer）。
2. 超过阈值（默认窗口 75%）才考虑压缩。
3. 通过会话元数据做压缩限频（新增消息数与时间间隔）。

### 3.2 执行层

1. 向 `llm-service` 发送 `messages + target_tokens`。
2. `llm-service` 压缩接口实现位于：
   - `vendor/Shannon/python/llm-service/llm_service/api/context.py:25`
3. 该接口有两条路径：
   - **有模型提供方时**：使用模型生成摘要。
   - **无模型提供方时**：回退为简单拼接+截断。
     - `vendor/Shannon/python/llm-service/llm_service/api/context.py:33`
     - `vendor/Shannon/python/llm-service/llm_service/api/context.py:35`

### 3.3 结果层

1. 摘要结果进入工作流上下文（`context_summary`）。
2. 历史消息进行首尾整形（primers + recents）。
3. 摘要文本做脱敏处理后再存储与注入。

### 3.4 关键判断

Shannon 的“上下文压缩”主路径不是单纯字符串截断，而是“阈值触发 + LLM 摘要 + 滑窗重排 + 脱敏 + 限频”的组合流程。

## 5. 对标结论：是否一致

结论：**不一致（默认运行路径明显不一致）**。

### 5.1 一致点

1. 两边都有“窗口整形”概念。
2. 两边都有 token 预算阈值触发概念。
3. 两边都有字符串保护性截断逻辑。

### 5.2 关键不一致点

1. **压缩主体不同**：
   - Shannon 主路径是 LLM 摘要压缩。
   - 本工程默认主路径是 rule 规则拼接 + 截断。

2. **窗口参数差异较大**：
   - Shannon 默认 `3 + 20`。
   - 本工程默认 `2 + 6`。

3. **触发比例差异**：
   - Shannon 常用默认 `0.75 / 0.375`。
   - 本工程默认 `0.85 / 0.70`。

4. **限频机制差异**：
   - Shannon：20 条消息 + 30 分钟双阈值。
   - 本工程：冷却秒级（默认 30 秒）为主。

5. **JSON 内容处理差异**：
   - Shannon 在压缩执行中依赖 LLM 对文本语义抽取。
   - 本工程默认 rule 链路将 JSON 视为普通字符串，主要做长度截断。

## 6. 对你当前观察的最终判断

你提出的判断“本工程里裁剪/剪裁主要是按长度暴力截断，且 JSON 内容未识别”在**默认配置与主路径**下是成立的。

更准确表达为：

1. 本工程并非只有“暴力截断”，还包含“按分段预算删除条目”的裁剪动作。
2. 但在文本层处理上，核心确实大量采用 `substring` 与字符阈值推导。
3. 在默认 `rule` 模式下，压缩摘要确实未进行 JSON 字段语义抽取。
4. 若要接近 Shannon 的语义压缩效果，需要切换或强化 LLM 压缩路径，而非仅依赖 rule 路径。

## 7. 对标建议（可执行）

1. 先将压缩模式从 `rule` 切到 `hybrid` 或 `llm`，并保留 `rule` 兜底。
2. 在入压缩前增加 JSON 感知提取器（字段白名单与摘要模板），避免直接截断原始 JSON 字符串。
3. 将窗口参数从 `2+6` 调整到与 Shannon 更接近的可配置档位（如 `3+20` 起步）。
4. 将触发/目标比与冷却策略按场景拆分，避免单一阈值覆盖所有任务。
5. 为“语义摘要质量”增加可观测指标（字段覆盖率、关键信息保留率、JSON 关键键命中率）。
