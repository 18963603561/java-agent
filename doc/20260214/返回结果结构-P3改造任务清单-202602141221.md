# 返回结果结构 P3 改造任务清单

## 目标与范围
1. 目标：完成 `steps[*].summary` 的冗余裁剪与 `result.quality.truncated` 类型统一，提升返回结构稳定性与可读性。
2. 范围：仅覆盖返回结果结构相关能力，不改动规划、执行、反思主流程语义。
3. 约束：保持 `responseMode=full` 完整语义不变；`compact` 才执行结构瘦身规则。

## 当前问题确认
1. `steps[*].summary` 在 `text` 为空时，仍可能包含 `truncated=false`、空列表等字段，语义噪声较高。
2. `result.quality.truncated` 在不同路径存在 `null/false` 混用，客户端需要额外判空，协议一致性不足。
3. 以上问题集中在“输出结构一致性”，不属于执行引擎正确性问题，适合在 P3 做协议层与结构层治理。

## P3 任务清单（按包职责拆分）

### 任务 1：步骤摘要裁剪策略（无 `text` 时仅保留 `highlights`）
1. 所在包/模块
- 响应后处理：`com.example.agent.api.http.response`
- 映射入口：`com.example.agent.api.http.mapper.TaskHttpMapper`
- 结果模型参考：`com.example.agent.runtime.model.SemanticSummary`
2. 任务内容
- 新增步骤摘要裁剪策略组件（建议：`StepSummaryCompactionPolicy`），仅在 `compact` 模式执行。
- 规则一：`summary.text` 有值时，保持现有 `summary` 结构（继续走通用去空逻辑）。
- 规则二：`summary.text` 为空且 `highlights` 非空时，`summary` 仅保留 `highlights`。
- 规则三：`summary.text` 为空且 `highlights` 为空时，移除整个 `summary` 节点。
- 规则四：该策略只作用于 `steps[*].summary`，不影响 `finalOutput.summary`。
- 增加调试日志：记录被裁剪步骤数、移除节点数，便于回归观察。
3. 验收标准
- 示例一：`text=null`、`highlights=[...]`，输出只包含 `highlights`。
- 示例二：`text=null`、`highlights=[]`，输出不再包含 `summary`。
- 示例三：`text` 非空，输出保持现有语义字段。
- `full` 模式下不触发上述裁剪。

### 任务 2：质量字段一致性（`quality.truncated` 统一布尔值）
1. 所在包/模块
- 结构化质量模型：`com.example.agent.runtime.structured.result.StructuredQuality`
- 质量评分：`com.example.agent.runtime.structured.StructuredQualityScorer`
- 质量合并：`com.example.agent.runtime.structured.StructuredExtractorRegistry`
2. 任务内容
- 将 `StructuredQuality.truncated` 从可空语义改为明确布尔语义（推荐新工程直接统一为 `boolean`，默认 `false`）。
- 在质量评分输出中显式赋值 `truncated=false`（除非明确识别到截断）。
- 在质量合并逻辑中取消 `null` 分支，统一按布尔值合并（建议规则：`existing || scored`）。
- 对提取器兜底路径和降级路径保持一致：所有路径都输出布尔值。
3. 验收标准
- `result.quality.truncated` 在所有步骤返回中恒为 `true/false`，不再出现 `null`。
- 不因类型统一引入兼容异常或序列化异常。
- 质量评分相关单测全部通过。

### 任务 3：响应瘦身管道顺序与可观测性固化
1. 所在包/模块
- 瘦身处理器：`com.example.agent.api.http.response.ResultPayloadCompactor`
- 去重策略：`com.example.agent.api.http.response.FinalOutputDedupPolicy`
- 新增策略：`com.example.agent.api.http.response.StepSummaryCompactionPolicy`
2. 任务内容
- 固化 `compact` 管道顺序：去重 -> 步骤摘要裁剪 -> 递归去空。
- 增加处理统计信息（`debug` 级别）：去重字段数量、摘要裁剪数量、去空节点数量。
- 明确幂等要求：同一 payload 重复执行 compact，结果必须一致。
3. 验收标准
- 同一输入重复 compact 两次，输出完全一致。
- 关键统计日志可用于定位回归。

## 包设计合理性检查要点（P3 约束）
1. 职责归位
- 步骤摘要裁剪是“对外展示策略”，放在 `api.http.response`，不侵入 `runtime.step` 执行链。
- `quality.truncated` 统一是“领域数据契约”，在 `runtime.structured` 内闭环处理。
2. 依赖方向
- `api.http` 只依赖 runtime 输出对象，不反向影响 runtime 主流程。
- `runtime.structured` 不依赖 controller/DTO，保持领域边界干净。
3. 协议稳定性
- `compact` 为增强能力，`full` 为回退路径。
- 开关与模式入口统一在 mapper 层，不在 controller 分散实现。

## 测试与验收计划
1. 单元测试
- 步骤摘要裁剪四类场景：有 text、无 text 且有 highlights、无 text 且无 highlights、full 模式。
- `quality.truncated` 一致性：成功、降级、兜底三类路径。
2. 集成回归
- `POST /api/v1/tasks` 同步与异步场景各一组。
- `GET /api/v1/tasks/{taskId}` 与 `GET /api/v1/tasks` 在 `compact/full` 双模式对比。
3. 全量回归
- 执行 `mvn test`，确保返回结构改造不影响现有主流程。

## 风险与回滚
1. 风险：客户端依赖 `summary.truncated` 或 `quality.truncated=null` 的旧判断。
- 处理：在发布说明中明确“布尔统一”变更，并提供 `full` 回退模式。
2. 风险：步骤摘要裁剪误删客户端使用字段。
- 处理：策略默认仅裁剪 `steps[*].summary`，且保留 `full` 直通。
3. 回滚策略
- 出现兼容问题时，可临时切回 `responseMode=full`。
- 若需快速回退，禁用 `StepSummaryCompactionPolicy` 注入并恢复旧 compact 逻辑。
