# 返回结果结构 P2 改造任务清单

## 目标与边界
1. 目标：围绕 `responseMode=compact/full` 与结果去重能力完成外部响应瘦身，提升接口可读性与传输效率。
2. 边界：仅调整对外响应映射与展示语义，不改动运行时执行主流程、不改变任务持久化结果原文。
3. 约束：默认模式为 `compact`，显式指定 `full` 时返回完整结构。

## P2 任务清单（按包职责拆分）

### 任务 1：引入响应模式协议（`compact/full`）
1. 所在包/模块
- HTTP 入参模型：`com.example.agent.api.http.dto`
- 控制器参数接入：`com.example.agent.api.http.controller`
- 响应映射入口：`com.example.agent.api.http.mapper`
- 响应模式配置：建议新增 `com.example.agent.api.http.config`

2. 任务内容
- 在 `TaskRequest` 增加 `responseMode` 字段，支持 `compact/full`。
- 在 `TaskQuery` 增加 `responseMode` 字段，用于 `GET /api/v1/tasks` 与 `GET /api/v1/tasks/{taskId}`。
- 新增响应模式枚举（建议 `ResponseMode`），统一解析逻辑，非法值回退默认模式并记录 `warn`。
- 控制器将解析后的模式透传给 `TaskHttpMapper`，避免控制器内分支拼装。
- 新增配置项 `agent.api.response.default-mode=compact`，作为全局兜底。

3. 验收标准
- 未指定模式时返回 `compact` 响应。
- 指定 `full` 时返回完整响应，不触发瘦身规则。
- 同步、异步、任务状态查询、任务列表查询均可稳定识别模式。

### 任务 2：实现 `compact` 统一瘦身处理器
1. 所在包/模块
- 响应后处理器：建议新增 `com.example.agent.api.http.response`
- 映射接入点：`com.example.agent.api.http.mapper.TaskHttpMapper`

2. 任务内容
- 新增统一处理器（建议 `ResultPayloadCompactor`），由 `TaskHttpMapper` 在 `appendStepIndex` 之后统一调用。
- 在 `compact` 模式下执行以下规则：
  - 移除 `null` 字段。
  - 移除空数组与空对象（保留协议必需字段）。
  - 去除重复 `planSummary`：当顶层 `planSummary` 与 `finalOutput.meta.planSummary` 内容一致时，仅保留一处。
  - 去除重复答案文本：当 `finalOutput.result.answer` 与 `finalOutput.summary.text` 语义相同且文本一致时，保留主路径字段。
- 在 `full` 模式下完全跳过瘦身，保持原始结构。

3. 验收标准
- `compact` 模式返回体明显缩小，核心业务字段仍完整。
- `full` 模式与当前返回保持兼容，不出现字段丢失。
- 处理器对未知扩展字段保持幂等，不改变字段值语义。

### 任务 3：落实 `answer/summary` 一致性裁剪策略
1. 所在包/模块
- 规范策略：`com.example.agent.api.http.response`
- 输出结构生成：`com.example.agent.runtime.finalize`（只读，不改主流程语义）

2. 任务内容
- 明确主字段优先级：`finalOutput.result.answer` 为主回答字段。
- 当 `finalOutput.summary.text` 与 `finalOutput.result.answer` 全量相等时，在 `compact` 下删除 `summary.text`。
- 若 `summary` 仅剩空字段且无 `highlights/openQuestions/risks/sourceRefs`，删除 `summary` 节点。
- 若 `summary` 仍包含其它结构化信息，仅移除重复文本，保留其余字段。

3. 验收标准
- 重复文本消除后，客户端仍可直接从 `finalOutput.result.answer` 读取最终回答。
- 存在摘要附加信息时不误删 `summary` 节点。
- 不影响反思/回归链路的数据判断输入（主路径仍基于 `result`）。

## 包设计合理性检查要点（P2 约束）
1. 展示层职责闭环：`responseMode` 与瘦身逻辑落在 `api.http`，不侵入 `runtime.engine/runtime.step`。
2. 主路径稳定性：不修改 `RuntimeFinalizationService` 的核心组装语义，避免对记忆写入和事件发布造成副作用。
3. 处理器可复用：瘦身规则集中在单一组件，避免 `TaskResponse`、`TaskStatusResponse`、`TaskListResponse` 各自重复实现。
4. 协议兼容：`full` 保留历史行为，`compact` 为增量能力，不破坏现有调用方。

## 测试与验收计划
1. 协议测试
- `responseMode` 缺省、`compact`、`full` 三组入参测试。
- 非法模式值回退默认模式测试。

2. 规则测试
- `null`、空数组、空对象移除测试。
- `planSummary` 重复去重测试。
- `finalOutput.result.answer` 与 `finalOutput.summary.text` 重复去重测试。
- `summary` 节点保留与删除边界测试。

3. 全链路回归
- 同步执行成功场景。
- 异步提交后状态查询场景。
- 工具步骤、LLM 步骤、异常步骤三类场景。

## 风险与回滚策略
1. 风险：部分前端可能依赖 `null` 字段判断，`compact` 可能导致展示逻辑空指针。
- 处理：默认提供 `full` 回退能力，并在接入说明中明确字段可缺省语义。

2. 风险：去重规则误删字段。
- 处理：以“只删重复文本、不删主字段”为硬约束，并通过快照用例回归。

3. 风险：列表查询与状态查询的模式不一致。
- 处理：统一走 `TaskHttpMapper` 的后处理入口，禁止各控制器分散处理。
