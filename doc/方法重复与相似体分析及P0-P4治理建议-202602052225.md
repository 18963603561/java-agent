# 方法重复与相似体分析及 P0-P4 治理建议

## 1. 分析目标

本次分析面向当前工程 `src/main/java`，识别：

- 完全重复或高度同构的方法体。
- 高相似度的方法体（语义接近、实现差异较小）。
- 这些方法是否适合统一下沉到通用 `util` 包或按功能分层组件。

## 2. 分析方法与口径

- 扫描方法数：949
- 过滤条件：忽略过短方法（token 小于 12）
- 重复判定：基于结构归一化后的方法体哈希分组
- 相似判定：基于归一化文本相似比（阈值约 0.78）聚类

统计结果：

- 重复方法簇：97 组
- 高相似方法簇：9 组

## 3. 重复数量降序（重点清单）

### 3.1 完全重复 Top（按重复数量降序）

1. `getTenantContext`（11 处）
- 主要位置：多个 `api/http/controller/*Controller.java`
- 判断：典型横切重复，适合统一。

2. `isTruthy`（8 处）
- 主要位置：`AgentRuntime`、`PlannerService`、`LlmStepService`、`RuntimeApprovalGate` 等
- 判断：布尔解析逻辑重复，适合统一。

3. 令牌估算方法（7 处）
- 主要位置：`ContextCompressionController`、`DefaultContextTrimmer`
- 判断：同一领域估算逻辑重复，适合按“预算领域组件”统一。

4. 上下文解析方法（7 处）
- 主要位置：`PlannerService` 与 `PlanPromptBuilder`
- 判断：同一模块内重复，优先模块内抽取。

5. 文本截断 `trimText/truncate`（5 处）
- 主要位置：`DefaultContextBuilder`、`MemoryRecallService`、`MemoryWriteService` 等
- 判断：通用文本裁剪逻辑，适合统一。

6. `resolveTraceId`（5+5 处，运行时与控制层明显重复）
- 判断：链路追踪字段解析为横切能力，建议统一。

7. `authenticate`（5 处）
- 主要位置：多个 Controller
- 判断：接口层重复，适合下沉到基类或网关。

### 3.2 高相似方法簇 Top

1. `toJson`（3 处）
- 位置：`JdbcEventLogRepository`、`JdbcTaskRepository`、`JdbcStepRecordRepository`
- 判断：持久化层序列化逻辑可统一。

2. `sumTokens`（3 处）
- 位置：预算分配与裁剪模块
- 判断：建议统一到预算领域工具。

3. 模型调用实现相似体（2 处）
- 位置：`DefaultModelProvider.invokeOpenAiCompatible` 与 `invokeOllama`
- 判断：不建议进入通用 util，应在模型提供层做模板化抽象。

4. `resolvePolicyFromContext`（2 处）
- 位置：`DefaultContextBuilder`、`MemoryRecallService`
- 判断：应下沉到 context/memory 共享策略组件。

## 4. 是否应统一到通用 util 包

结论：可以统一，但不能“一股脑进 util”。

建议原则：

- 纯技术性、无业务语义的方法，进入通用 util。
- 领域语义明显的方法，进入对应领域 shared 组件，不进通用 util。
- 编排逻辑与外部协议逻辑，进入 facade/adapter，不进 util。

## 5. P0-P4 分级（按重复数量与治理收益）

### P0（立即治理，重复多且横切）

1. `getTenantContext`（11）
2. `isTruthy`（8）
3. `resolveTraceId`（≥10，分布于多层）
4. `authenticate`（5，API 层重复）

建议：

- 新建 `com.example.agent.common.util.auth.TenantContextResolver`
- 新建 `com.example.agent.common.util.bool.BooleanParser`
- 新建 `com.example.agent.common.util.trace.TraceIdResolver`
- Controller 侧引入 `ApiAuthSupport`（抽象基类或组合组件）

### P1（高优先，领域内重复明显）

1. `estimate*Tokens` / `sumTokens`（预算与裁剪重复）
2. `toJson`（JDBC 仓储重复）
3. `trimText/truncate`（文本裁剪重复）

建议：

- `com.example.agent.budget.shared.TokenEstimateSupport`
- `com.example.agent.persistence.shared.JsonCodecSupport`
- `com.example.agent.common.util.text.TextTrimSupport`

### P2（中优先，相似度高但涉及语义差异）

1. `resolvePolicyFromContext`（context/memory）
2. `applyPromptBundle`（research/debate/repair）

建议：

- 在领域包内建 `shared` 组件，不放通用 util。
- 保留调用方差异参数，避免过度抽象。

### P3（低优先，模块内重复）

1. `resolveContextSnapshot/resolveContextBudget/resolveContextPrune`
- 主要在 `PlannerService` 与 `PlanPromptBuilder`

建议：

- 优先在 `planning` 包内提取 `PlanningContextAccessor`。

### P4（观察项，暂不统一）

1. `DefaultModelProvider` 内模型调用相似体
2. 算法型服务内部相似流程

建议：

- 先保持可读性，待协议稳定后再模板化。

## 6. 建议的包分层方案

### 6.1 通用 util（仅纯技术能力）

- `com.example.agent.common.util.bool.BooleanParser`
- `com.example.agent.common.util.trace.TraceIdResolver`
- `com.example.agent.common.util.text.TextTrimSupport`
- `com.example.agent.common.util.map.SafeMapReader`

### 6.2 领域 shared（有业务语义，不进 util）

- `com.example.agent.budget.shared.TokenEstimateSupport`
- `com.example.agent.planning.shared.PlanningContextAccessor`
- `com.example.agent.persistence.shared.JsonCodecSupport`
- `com.example.agent.api.support.ApiAuthSupport`

### 6.3 编排与适配层（禁止 util 化）

- 模型调用适配（OpenAI/Ollama）
- MCP 协议调用与重试降级
- Runtime/Planner 主流程编排

## 7. 实施顺序建议

1. 先做 P0，优先消除横切重复。
2. 再做 P1，降低预算与持久化层重复。
3. 最后做 P2-P3，按模块稳定性逐步抽取。
4. P4 保持观察，避免过度工程化。

## 8. 总结

当前工程“可统一”的重复方法主要集中在：认证上下文解析、布尔解析、trace 解析、token 估算、文本截断、JSON 序列化。建议采用“通用 util + 领域 shared”双层治理，不建议将业务语义方法全部归并到单一 util 包，以避免形成新的“工具上帝类”。
