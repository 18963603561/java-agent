# 工具模型格式规范-调整影响分析

**背景与目标**
依据 `doc/notes/有关工具模型格式规范.txt` 的格式规范，对工程中的 `EvidencePack`、`Step` 输入输出、`raw/structured/summary/refs` 与 `Hook` 收口机制进行设计级别对齐。该工程被视为新工程，不考虑历史包袱，强调清晰职责、可复用性与扩展性。

**全量检索说明**
已对 `src/main/java` 与 `src/test/java` 执行关键词、类名、包名级别的全量检索，覆盖 `context`、`runtime`、`agentcore`、`tools.hook`、`model`、`memory`、`research`、`streaming`、`governance` 等相关包与测试。检索命中显示当前证据写入分散在 `ToolExecutor`、`MemoryRecallService`、`AgentRuntime`，`HookManager` 仅有 `pre/post tool` 与 `pre/post step`，未覆盖 `memory/research/trim` 写入收口。

**现状与规范差距（要点）**
当前 `EvidencePack` 结构为 `toolCalls/memoriesUsed/citations`，缺少规范中的 `evidences[]` 通用项、`packId`、`index`、统一 `ref/digest` 结构。
当前证据写入发生在 `ToolExecutor`、`MemoryRecallService`、`AgentRuntime`，违反“单写入口必须在 `Hook`”的收口要求。
`HookManager` 未提供 `postRecall/postResearch/postTrim` 等生命周期钩子，无法承载证据收口。
步骤输出以 `Map` 方式散落在 `StepRecord` 与 `StepResponse`，没有 `meta + rawRef + structured + summary + refs` 的稳定契约。
`raw` 未落库也无 `rawRef` 统一引用，无法满足“可回溯但不常驻上下文”的要求。
`StructuredExtractorRegistry`、`StructuredResult`、`ResultKind` 等规范组件缺失，后续步骤无法稳定依赖 `structured`。
`StepOutputSummaryBuilder` 基于输出散列摘要，未以 `structured` 为主、`raw` 为辅的摘要策略。
`PromptAssembler` 与 `ContextAssembler` 未显式注入 `EvidencePack`，缺少 “`Evidence-aware` 组装”能力。

**目标设计蓝图（新工程视角）**
数据流：`Tool/Model` 产出 `raw` → `RawStore` 落库生成 `rawRef` → `StructuredExtractorRegistry` 产出 `structured` → `SummaryBuilder` 产出 `summary` → `StepOutput` 落库 → `Hook` 事件统一写入 `EvidencePack`。
写入收口：所有证据写入仅在 `Hook` 完成，通过 `EvidencePackHookHandler` 接收 `postTool/postRecall/postResearch/postTrim` 事件，`EvidencePackService` 仅负责追加与统计。
步骤契约：`StepInput` 仅传递 `structured + refs + 可选 summary`；`StepOutput` 统一包含 `meta + rawRef + structured + summary + errors`。
结构化结果：通过 `ResultKind` 抽象语义域，`StructuredResult` 采用固定外壳 `kind/schemaVersion/quality/refs`，`data` 为 `kind` 特定最小字段集。
证据包：`EvidencePack` 采用 `packId/tenantId/workflowId/snapshotId/evidences[]/stats/index` 结构，`EvidenceItem` 统一字段 `type/stepId/ref/digest/createdAt/source`，允许扩展 `CONTEXT_TRUNCATION`、`BUDGET_STOP` 等类型。

**数据模型建议（摘要版）**
`EvidencePack`：`packId/tenantId/workflowId/snapshotId/evidences[]/stats/index`。
`EvidenceItem`：`evidenceId/type/stepId/ref/digest/source/createdAt`。
`RawRef`：`store/key/size/mediaType/createdAt/hash`。
`StructuredResult`：`kind/schemaVersion/data/quality/refs`。
`StepOutput`：`meta/rawRef/structured/summary/errors`。
`StepInput`：`question/dependsOn/contextRefs/upstream{structured/refs/summary}/constraints`。

**结论**
若严格按规范调整，核心变更集中在“证据写入统一收口”与“步骤 I/O 契约化”两条主线。建议以新增结构化抽取与 `rawRef` 落库为第一阶段，再将 `EvidencePack` 写入迁移至 `Hook`，最终补齐 `Prompt` 注入与可观测统计，形成可扩展的稳定编排内核。
