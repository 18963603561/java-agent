# agent上下文对比分析与改进方案

**对比依据**
- 文档：`doc/20260213/agent上下文.md`
- 现有工程关键实现：
`src/main/java/com/example/agent/capabilities/context/DefaultContextBuilder.java`
`src/main/java/com/example/agent/budget/trim/application/DefaultContextPruner.java`
`src/main/java/com/example/agent/budget/trim/application/DefaultContextTrimmer.java`
`src/main/java/com/example/agent/budget/trim/application/ContextCompressionService.java`
`src/main/java/com/example/agent/budget/trim/application/DefaultCompressionSummaryApplier.java`
`src/main/java/com/example/agent/capabilities/context/assembly/DefaultContextAssembler.java`
`src/main/java/com/example/agent/capabilities/context/assembly/DefaultContextSummaryInjectionPolicy.java`

`src/main/java/com/example/agent/runtime/summary/StepOutputSummaryBuilder.java`
`src/main/java/com/example/agent/capabilities/memory/write/MemoryWriteService.java`

**结论概览**
- 文档强调 `Retrieve -> Prune -> Compress -> Trim` 的层层收缩与基于令牌的控制；工程当前顺序为 `Prune -> Trim -> Compress`，且压缩后不再执行最终裁剪，存在预算闭环不完整的问题。
- 文档建议将原始输出仅用于调试，系统应以 `structured_result` 与 `summary` 驱动流程与记忆；工程当前保留了较多原始输出与混合结构，摘要与结构化的边界不够清晰。
- 工程的记忆与上下文层次实现相对简化，缺少“最近对话窗口”与语义评分裁剪等能力，导致与文档的工程化目标存在差距。

## 一、问题一：令牌语义、记忆与 `Prune/Compress/Trim` 处理逻辑对比

**文档要点**
- 所有上下文最终都会被序列化为 `token` 序列，预算控制必须围绕 `token`。
- `Prune` 是语义层面的筛选删除，优先删除低相关、低重要、重复或已完成内容。
- `Compress` 是摘要替代，用短文本保留信息。
- `Trim` 是机械截断，最后手段。
- 推荐流程为 `Retrieve -> Prune -> Compress -> Trim`。

**工程现状**
- 顺序为 `Prune -> Trim -> Compress`，见 `DefaultContextBuilder.build`。
- `Prune` 仅基于数量上限与固定顺序删除：
`DefaultContextPruner` 对记忆、证据、引用按最大条数截断，未使用相关度或重要度评分。
- `Trim` 基于分段预算与总预算执行机械裁剪，见 `DefaultContextTrimmer`。
- `Compress` 在裁剪后触发，使用压缩结果回填到工作记忆与长期记忆，见 `ContextCompressionService` 与 `DefaultCompressionSummaryApplier`。
- `token` 估算基于字符除以四的近似算法，见 `TokenEstimator` 与 `ContextTokenEstimator`、`PromptTrimEngine`。
- 上下文快照不包含“最近对话窗口”，仅包含工作记忆摘要与关键事实，见 `ContextSnapshot` 与 `WorkingMemory`。

**差异与缺陷分析**
1. 顺序不一致：文档要求 `Prune -> Compress -> Trim`，工程执行 `Prune -> Trim -> Compress`。
结果是压缩发生在已经被裁剪的上下文之上，压缩质量受限，同时缺少最终裁剪保证。
2. 缺少压缩后的最终裁剪：`ContextCompressionService` 只记录 `stillOverBudget`，没有再次触发裁剪或提示上游处理。
这会导致预算闭环不完整，存在“压缩后仍超预算”的风险。
3. `Prune` 语义不足：目前仅按数量上限裁剪，缺乏相关度与重要度判定，与文档“语义修剪”的定义不匹配。
4. 令牌估算粗糙：基于字符长度的近似在多语言场景下误差较大，易导致预算误判与裁剪位置不稳定。
5. 缺失对话窗口层：上下文未显式携带“最近对话窗口”，文档强调的“摘要 + 最近对话”结构未落地。
6. 压缩回填覆盖问题：`DefaultCompressionSummaryApplier` 直接覆写长期记忆引用为单条压缩记录，可能丢失已召回的记忆引用。

**是否需要完善**
需要。当前实现偏“预算保底”，与文档的工程化目标存在差距，且已出现预算闭环、语义裁剪与对话窗口缺失等结构性问题。

## 二、问题二：`LLM` 与工具输出的原始结果与摘要处理对比

**文档要点**
- 原始输出仅用于调试，不应成为系统逻辑与长期记忆的核心来源。
- 系统应以 `structured_result` 驱动流程，以 `summary` 进入长期记忆。
- 推荐任务输出协议包含 `meta`、`result`、`decision`、`summary` 四段。
- 强制 `JSON` 与 `JSON Schema` 校验，失败则重试或降级。

**工程现状**
- 工具输出由 `ToolOutputAssembler` 组装，包含 `RAW_RESULT`、`RAW_REF` 以及摘要字段。
- `ToolSummaryService` 可生成摘要，但失败时回退为模板文本，缺少统一质量门槛。
- `RawOutputEnvelopeBuilder` 会在原始输出层进行截断并保留快照。
- `StepOutputSummaryBuilder` 生成摘要与指纹，但输出结构与任务协议未统一。
- `MemoryWriteService` 会将最终输出整体序列化并写入记忆，同时生成简易摘要。

**差异与缺陷分析**
1. 原始输出保留范围偏大：原始输出被封装并可能落入记忆写入路径，与文档“原始仅调试”的原则不一致。
2. 缺少统一任务输出协议：当前输出结构分散在 `ToolOutputAssembler`、`StepOutputSummaryBuilder` 等处，`structured_result` 与 `summary` 的边界不清晰。
3. 缺少强制结构化校验：未见统一的 `JSON Schema` 校验与自动重试流程，结构化结果可靠性不足。
4. 摘要与结构化结果未形成固定主从关系：摘要不一定进入长期记忆，结构化结果也未被明确作为流程控制唯一来源。

**是否需要完善**
需要。若以多步骤 `Agent` 为目标，必须建立稳定的输出协议与结构化校验机制，降低原始输出对系统的干扰。

**问题二补充：原始输出到结构化/摘要的输出协议评估**
**文档要求**
`agent上下文.md` 明确建议大模型输出“可读解释 + 结构化结果”，例如：`{"analysis": "...", "structured_data": {...}}`，并强调长期记忆只保留 `structured_result` 与 `summary`，`analysis` 仅用于调试或展示。
**工程现状**
1. 输出协议未落地：运行时输出键集中在 `OutputKeys`/`RuntimeOutputKeys`（如 `result`、`rawResult`、`summary`），未定义 `analysis` 与 `structured_data` 的统一键，也未强制要求模型按协议输出。
2. 结构化结果为“后置提取”：`StructuredExtractorRegistry` 依据 `rawOutput` 做结构化提取或兜底，而非强制模型直接输出 `structured_data`，且缺少统一 `JSON Schema` 校验。
3. 最终输出优先使用原始数据：`RuntimeFinalizationService.extractFinalOutput` 先取 `StepResult.raw`，再取 `structured`，最后才用 `summary`，导致原始输出仍是主路径。
4. 记忆写入偏原始输出：`MemoryWriteService` 直接序列化 `finalOutput` 落库，`summary` 只是派生的文本截断，不是模型输出的结构化摘要。
5. 仅见“推理文本清洗”而非结构化协议：`CotAnswerSanitizer` 用于移除 `analysis`/推理痕迹，反向说明输出仍以“自然语言”为主。
**差距结论**
工程尚未形成“analysis/structured_data/summary”三段式输出协议，也未实现“结构化为主、摘要入库、原始仅调试”的主张，存在协议缺失与使用路径偏原始输出的问题。
**完善建议**
1. 定义统一输出协议与键：新增 `analysis`、`structured_result`（或 `structured_data`）、`summary` 作为运行时契约，并在 `OutputKeys` 统一维护。
2. 强制结构化与校验：引入 `JSON Schema` 校验，不通过则重试或降级；结构化字段为主流程数据来源。
3. 调整最终输出优先级：优先输出 `structured_result` + `summary`，仅在调试模式或显式开关时返回 `analysis` 与原始输出。
4. 调整记忆写入：长期记忆仅写入 `summary` 与必要的结构化字段，原始输出转为调试路径。
5. 补齐提示模板：在模型提示中明确输出协议，减少后置解析与兜底。

## 三、完整改进方案

**目标**
- 对齐文档中的上下文收缩顺序与输出协议。
- 形成“预算闭环 + 结构化输出 + 摘要入库”的稳定链路。

**阶段一：顺序与预算闭环修复**
1. 将上下文处理流程调整为 `Prune -> Compress -> Trim`，或在压缩后补一次 `Trim`，确保最终预算必达。
2. 在 `ContextCompressionService` 增加“压缩后裁剪触发”策略与结果回填，避免 `stillOverBudget` 仅记录不处理。
3. 修复压缩回填覆盖问题，改为“追加压缩记忆引用”或“保留原有记忆引用并标记压缩条目”。

**阶段二：语义裁剪与令牌精度提升**
1. 引入相关度或重要度评分，将 `Prune` 从“数量裁剪”升级为“语义裁剪”，并将评分结果显式挂载到上下文条目，便于调试与验收。
2. 语义裁剪的核心定义：以当前任务目标和最新对话为中心，先保留必须内容，再在预算内选择高分内容，低分内容被删除或进入后续压缩候选。
3. 评分维度建议包含：相关度、重要度、时效性、来源权重、任务完成度、重复度惩罚、成本惩罚（按 `token` 消耗）。权重与阈值需配置化，支持按场景切换。
4. 评分方法建议：相关度可由 `embedding` 相似度或 `LLM` 二分类判定；重要度由规则表决定（例如系统规则 > 开发约束 > 用户目标 > 工具证据 > 历史对话）；时效性按时间衰减；重复度用近似去重；成本惩罚按 `token` 消耗归一化。
5. 选择策略建议：建立“强制保留集合”（系统指令、开发约束、用户当前问题、最近 `N` 轮对话、关键错误与安全信息），其余内容按综合分降序保留；当仍超预算时触发压缩或再次裁剪，保证预算闭环。
6. 落地步骤建议：新增评分接口与结果模型，`DefaultContextPruner` 在裁剪前调用评分并记录排序；评分规则与权重写入配置；在关键分支记录评分与保留原因日志；补齐单元测试与回归用例。
7. 替换基于字符的 `token` 估算，实现模型级分词器或可插拔的精确估算器。
8. 增加对话窗口层，至少保留“摘要 + 最近 `N` 轮对话”并参与裁剪与压缩。

**阶段二补充：语义评分细化说明**
**评分对象与输入**
评分对象是“上下文条目”，包括系统指令、开发约束、用户消息、工具输出摘要、证据片段、记忆片段与历史对话。评分输入建议包含：当前任务目标、最新一轮对话、工具调用结果、上下文条目元数据（来源、时间、类型、长度）。
**相关度评分（Relevance）**
1. `embedding` 相似度：对“任务目标 + 最新用户问题”生成向量，与条目向量计算余弦相似度，得到 `0~1` 分。
2. `LLM` 二分类判定：提示模型判断条目“是否直接支撑当前任务”，输出 `0/1` 或 `0~1` 置信度。
3. 融合策略：`relevance = 0.7 * sim + 0.3 * llm_score`，当 `embedding` 不可用时回退为 `LLM` 判定。
**重要度评分（Importance）**
1. 规则表分级：系统规则 > 开发约束 > 用户目标 > 工具证据 > 历史对话 > 其他。
2. 分级映射示例：系统规则 `1.0`，开发约束 `0.9`，用户目标 `0.8`，工具证据 `0.7`，历史对话 `0.4`，其他 `0.2`。
3. 强制保留集合：系统指令、开发约束、当前问题、关键错误与安全信息直接标记“必留”，跳过后续裁剪。
**时效性评分（Recency）**
1. 时间衰减：`recency = exp(-age_minutes / half_life)`，半衰期可按条目类型配置。
2. 类型差异：错误诊断与关键决策衰减慢，闲聊与短期细节衰减快。
**重复度惩罚（Redundancy）**
1. 近似去重：用指纹或 `embedding` 聚类，计算与已保留条目的相似度。
2. 惩罚策略：当相似度高于阈值，`redundancy_penalty` 线性递增。
**成本惩罚（Cost）**
1. 长度归一化：`cost = min(1, tokens / token_budget_segment)`。
2. 惩罚策略：`cost_penalty = cost * cost_weight`，长条目在同等语义价值下优先被压缩或裁剪。
**综合得分与选择**
1. 综合公式示例：`score = w1*relevance + w2*importance + w3*recency - w4*redundancy - w5*cost`。
2. 阈值策略：分数低于下限进入裁剪候选；分数介于阈值之间进入压缩候选。
3. 保留策略：先保留“必留集合”，再按综合分降序填充预算，超出部分进入压缩或裁剪。
**可观测性与回归**
1. 为每条目记录评分明细、保留原因、裁剪原因与摘要引用，便于回归与抽检。
2. 对评分结果进行抽样审计，确保“高重要、低相关”和“高相关、低重要”两类条目的处理符合预期。

**阶段二补充：滑动窗口压缩评估（参考 7.3）**
**方案概述**
当上下文预算使用率达到阈值时触发压缩，将历史切分为“前若干条（Primers） + 中间摘要 + 后若干条（Recents）”，默认示例为前 3 条、后 20 条，压缩目标约为预算的 37.5%，触发阈值约为 75%。
**合理性评估**
1. 符合“摘要 + 最近对话”的结构化目标，能够保留对话开端的任务背景与最近上下文的连续性。
2. 中间摘要可承接 `Compress` 的职责，控制预算同时减少遗忘风险。
3. 具备可调参数，能针对调试类场景提高保留量，满足不同使用场景的稳定性需求。
**工程适用性评估**
1. 工程已有压缩能力与摘要回填链路，可复用为中间摘要生成，新增成本可控。
2. 现有上下文快照缺少“最近对话窗口”，需要补充对话窗口层与窗口切片逻辑。
3. 需与 `Prune -> Compress -> Trim` 顺序对齐，避免“先裁剪后摘要”导致信息缺失。
**落地建议**
1. 新增对话窗口层与窗口切片策略，明确 `primers_count`、`recents_count`、`compression_trigger_ratio`、`compression_target_ratio` 等配置项。
2. 设计“中间摘要”结构体与来源区间标识，摘要进入工作记忆或专用段落，避免与原始消息混淆。
3. 触发压缩时保留“强制保留集合”，其余按语义评分排序后进入压缩候选或裁剪候选。
4. 在压缩触发、摘要生成、预算达标位置补充日志与指标，支持回归评估与质量抽检。
**注意事项**
1. 摘要有损，调试与排障场景需提高 `recents_count` 与触发阈值，避免关键细节丢失。
2. 需确保系统指令与开发约束始终在 `Primers` 范围内，防止被压缩覆盖。
3. 避免重复压缩同一段历史，需记录已压缩区间并在后续请求中复用摘要。

**阶段三：统一输出协议与摘要入库**
1. 设计并落地标准任务输出协议：`meta`、`result`、`decision`、`summary`。
2. 对 `LLM` 与工具输出启用统一 `JSON Schema` 校验，失败执行自动重试与降级。
3. 调整记忆写入逻辑，仅将 `summary` 与必要的 `structured_result` 入库，原始输出仅保留调试路径。
4. 调整证据包与摘要生成逻辑，使 `Tool` 结果摘要成为证据主载体，减少原始结果噪声。

**验收标准**
1. 压缩后必有最终裁剪或明确的预算达标证明。
2. `Prune` 具备可配置的语义评分或相关度过滤。
3. 输出协议统一且通过 `JSON Schema` 校验。
4. 长期记忆只保存 `summary` 与必要的结构化字段，原始输出不进入记忆主路径。
