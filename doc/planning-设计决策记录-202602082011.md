# planning 设计决策记录（ADR）

## ADR-001：`PlannerService` 仅保留编排职责

### 状态

- 已采纳

### 背景

- 早期规划实现存在编排层承载细节逻辑的问题，导致单类职责过宽。
- 能力评估映射、审批策略写入、LLM 规划控制混杂，扩展成本高。

### 决策

- `PlannerService` 仅做流程编排。
- 能力映射下沉到 `PlanningCapabilityService`。
- 审批写入下沉到 `PlanningApprovalService`。
- LLM 调用与解析保持在 `LlmPlanEngine`。

### 结果

- 编排路径清晰，可独立替换具体能力实现。
- 单测维度更聚焦，回归边界更明确。

## ADR-002：解析失败类型统一词典

### 状态

- 已采纳

### 背景

- 规划解析失败在日志与 trace 中口径不统一，难以横向分析。

### 决策

- 建立 `PlanParseErrorTypes` 作为唯一错误类型词典。
- `PlanParser.parseAttempt` 返回 `PlanParseAttemptResult`，显式暴露失败类型。
- `LlmPlanEngine` 和 trace 统一使用该词典。

### 结果

- 观测语义统一，问题归因效率提升。
- 失败路径可测试，避免隐式 `null` 语义。

## ADR-003：策略调度顺序显式化与冲突失败快返

### 状态

- 已采纳

### 背景

- 策略顺序若依赖“约定俗成”，存在冲突时会产生不确定行为。

### 决策

- 引入 `PlanningStrategyOrders` 统一维护顺序常量。
- `PlanningStrategyRegistry` 初始化阶段校验 order 唯一性。
- 检测冲突直接抛错，禁止系统带病运行。

### 结果

- 策略扩展行为稳定，启动期即暴露配置问题。
- 随机注册顺序下仍能保证执行稳定。

## ADR-004：策略上下文只读视图与受控写入

### 状态

- 已采纳

### 背景

- 策略上下文直接暴露可变集合，易产生外部副作用与不可预期修改。

### 决策

- `PlanningStrategyContext` 构造阶段防御性拷贝。
- 对外返回只读视图。
- 写入统一走 `appendStep/appendDependency`。

### 结果

- 不变式可验证，避免集合被外部篡改。
- 策略行为更可预期，测试稳定性提升。

## ADR-005：提示词追踪从遥测组件中拆分

### 状态

- 已采纳

### 背景

- `PlanTelemetry` 职责持续膨胀，既管理上下文事件又管理 trace 组装。

### 决策

- 新增 `PlanningPromptTraceService` 负责 prompt trace 组装与上报。
- `PlanTelemetry` 作为门面委托 trace 服务。

### 结果

- 遥测模块职责边界更清晰。
- trace 逻辑可独立测试与增强。

## ADR-006：`PlanResult` 产物默认只读

### 状态

- 已采纳

### 背景

- 规划结果步骤集合可被外部随意修改，影响链路稳定性。

### 决策

- 提供 `PlanResult.readonly(...)` 工厂方法。
- 引擎与回退构建链路统一产出只读步骤列表。

### 结果

- 输出对象边界更稳固，减少下游误改风险。

---

## ADR-007：诊断工具只用于测试与排障

### 状态

- 已采纳

### 背景

- 需要快速复现 planning 状态，但不希望把诊断逻辑侵入主链路。

### 决策

- 增加 `PlanningDiagnosticsSnapshotBuilder`。
- 明确仅用于测试与诊断，不参与运行时决策。

### 结果

- 故障复现效率提升，同时保持主链路行为稳定。

## 总结

- 本 ADR 集中回答了 planning 架构“为何这样设计”。
- 后续新增关键设计时，应按相同模板追加 ADR，保障可追溯性。
