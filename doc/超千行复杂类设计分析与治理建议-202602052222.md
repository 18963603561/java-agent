# 超千行复杂类设计分析与治理建议

## 分析目标

本次分析面向 `src/main/java` 下实现代码超过 1000 行的 Java 类，目标如下：

- 识别当前超大类清单。
- 基于静态复杂度判断是否存在设计不合理。
- 给出优先级明确、可落地的治理建议。

## 统计口径

- 统计范围：`src/main/java/**/*.java`
- 过滤条件：文件总行数 `> 1000`
- 指标：总行数、方法数、`if` 分支数、`catch` 数

## 设计合理性结论

### 一、明确不合理（高风险）

1. `AgentRuntime`
- 结论：设计不合理。
- 主要问题：编排、路由、审批、恢复、上下文管理、结果收口职责集中，已经形成“超级协调器”。
- 风险：任意一处变更都会扩大回归面，故障定位成本高。

2. `PlannerService`
- 结论：设计不合理。
- 主要问题：能力评估、LLM 规划、规则回退、修复、归一化和校验耦合度过高。
- 风险：策略迭代频繁时容易引入联动缺陷。

3. `LlmStepService`
- 结论：设计不合理。
- 主要问题：模型调用协议、工具参数注入、输出整形和兼容逻辑混在同层。
- 风险：模型或工具协议变化将引发全链路影响。

4. `McpToolClient`
- 结论：设计不合理。
- 主要问题：HTTP 调用、初始化、重试、降级、异常处理高度混合，`catch` 数偏高。
- 风险：网络抖动和协议差异会持续放大复杂度。

### 二、需要治理（中风险）

1. `DefaultModelProvider`
- 结论：存在明显膨胀，建议拆分。
- 主要问题：不同模型与参数策略可能在一个类内交叉实现。

2. `DefaultContextBuilder`
- 结论：边界不够清晰。
- 主要问题：上下文组装、预算应用、裁剪处理、证据融合职责交叠。

3. `DefaultContextTrimmer`
- 结论：规则复杂度偏高。
- 主要问题：策略决策与执行算法混在一起，分支多。

### 三、可接受但建议模块化（低到中风险）

1. `StepOutputSummaryBuilder`
- 结论：职责相对聚焦，但体量偏大。
- 建议：拆分输入摘要、输出摘要、digest 计算模块。

2. `ChainOfThoughtService`
- 结论：算法流程较长但可理解。
- 建议：抽离模板装配与流程控制，保留核心推理主干。

## 优先级建议

### P0（立即推进）
- `AgentRuntime`
- `PlannerService`
- `McpToolClient`

### P1（紧随其后）
- `LlmStepService`
- `DefaultModelProvider`
- `DefaultContextBuilder`

### P2（持续优化）
- `DefaultContextTrimmer`
- `StepOutputSummaryBuilder`
- `ChainOfThoughtService`

## 落地改造建议

1. 采用“门面 + 组件”结构
- 门面只保留阶段编排。
- 将协议适配、解析、校验、修复下沉到组件。

2. 收敛动态上下文边界
- 减少跨层 `Map<String, Object>` 直接透传。
- 对关键阶段引入明确输入输出对象。

3. 建立复杂度治理阈值
- 建议阈值：单类 < 800 行，方法数 < 35，`if` 数 < 80。
- 超阈值类进入治理清单，按季度清理。

4. 先补契约测试再拆分
- 对事件顺序、输出结构、审批状态迁移建立契约回归。
- 采用小步 PR（每个 PR 只变一类职责）。

## 建议的首批治理任务

1. 继续沿你现有最小 PR 清单推进 `AgentRuntime` 和 `PlannerService` 的职责下沉。
2. 新增 `McpTransport`、`McpRetryPolicy`、`McpProtocolAdapter` 三层，拆解 `McpToolClient`。
3. 将 `LlmStepService` 拆为 `LlmInvocationFacade`、`ToolInjectionService`、`LlmOutputNormalizer`。
4. 给 P0 类补充“复杂度哨兵测试”，防止再次回涨。

## 总结

当前工程存在 9 个超千行类，其中 4 个已处于高风险设计状态。建议优先处理运行时编排、规划服务与 MCP 客户端，持续按小步可回滚方式治理复杂度，可显著降低后续功能迭代和缺陷修复成本。
