# reasoning 包设计合理性与坏味道复评

## 1. 评估范围

- 目录范围：`src/main/java/com/example/agent/reasoning`
- 评估维度：分层结构、职责边界、可复用性、可演进性、可测试性、坏味道风险
- 评估方式：静态代码审阅 + 关键类规模统计 + 规则与契约一致性检查

## 2. 总体结论与等级

### 2.1 总体等级

- **设计合理性等级：B+（中上，已具备工程化基础）**
- **坏味道等级：P1 为主，P2 次之，暂无明确 P0 阻断项**

### 2.2 结论摘要

1. `common` 层（`config/telemetry/orchestrator/result/selection`）已经形成，公共能力聚合方向正确。
2. 三类策略包（`cot/debate/thoughttree`）边界清晰，具备按策略演进的基础。
3. 仍存在少数大类、规则硬编码和输入契约弱类型化问题，长期演进成本偏高。

## 3. 包设计合理性分析

### 3.1 结构合理性（较好）

- `ReasoningStrategy + ReasoningStrategyRegistry` 建立统一入口，便于新增策略。
- `ReasoningOrchestrator` 承接并行执行与仲裁，避免执行器内重复并行逻辑。
- `ReasoningEventPublisher/ReasoningTraceRecorder/ReasoningMetricsPublisher` 统一可观测实现，方向正确。
- `ReasoningExecutionProperties + Resolver + Validator` 已形成配置治理闭环。

### 3.2 职责边界（中等）

- `ChainOfThoughtService`、`DebateCoordinator` 仍然承担较多流程细节，职责密度偏高。
- `ThoughtTreeService` 将“树构建 + 评分规则 + 回溯策略”集中在单类，维护成本上升。

### 3.3 契约设计（中上）

- `ReasoningResult` 已以强类型 `payload` 为主，契约方向明显改善。
- 但 `ReasoningRequest.input` 仍是 `Map<String, Object>`，调用方依赖字符串键，类型安全不足。

## 4. 关键坏味道清单

| 编号 | 坏味道 | 等级 | 影响 | 证据 |
|---|---|---|---|---|
| RSN-SMELL-01 | 过大类（God Class） | P1 | 可读性、回归风险、单测粒度 | `src/main/java/com/example/agent/reasoning/cot/ChainOfThoughtService.java`（约 637 行，依赖字段多） |
| RSN-SMELL-02 | 协调器职责聚合偏重 | P1 | 内聚性下降、变更耦合 | `src/main/java/com/example/agent/reasoning/debate/DebateCoordinator.java`（约 385 行） |
| RSN-SMELL-03 | 算法与规则耦合 | P1 | 算法迭代成本高 | `src/main/java/com/example/agent/reasoning/thoughttree/ThoughtTreeService.java`（评分阈值与业务规则内嵌） |
| RSN-SMELL-04 | 输入弱类型化（字符串键驱动） | P1 | 编译期无法发现字段错误 | `src/main/java/com/example/agent/reasoning/common/ReasoningRequest.java` + 各执行器传参 |
| RSN-SMELL-05 | 规则硬编码 | P2 | 策略扩展与灰度能力受限 | `src/main/java/com/example/agent/reasoning/common/selection/ReasoningStrategySelector.java` |
| RSN-SMELL-06 | 降级顺序硬编码 | P2 | 动态策略治理能力不足 | `src/main/java/com/example/agent/reasoning/common/selection/ReasoningDegradePolicy.java` |
| RSN-SMELL-07 | 计划对象可变且缺少自校验 | P2 | 非法计划输入风险 | `src/main/java/com/example/agent/reasoning/common/orchestrator/ReasoningExecutionPlan.java` |

## 5. 关键证据摘要

1. 类规模集中：
   - `ChainOfThoughtService` 约 637 行。
   - `ThoughtTreeService` 约 414 行。
   - `DebateCoordinator` 约 385 行。
2. 策略选择阈值与业务条件硬编码：`complexityScore > 0.7`、`highRisk/requiresDeliberation`。
3. 思维树评分规则存在大量魔法数：`0.5/0.2/0.1/0.05` 等。

## 6. 分项评分

| 维度 | 评分 | 说明 |
|---|---|---|
| 分层结构 | A- | 公共层清晰，策略包分离良好 |
| 职责内聚 | B | 关键服务类仍偏重 |
| 可复用性 | B+ | telemetry/config/orchestrator 可复用性较好 |
| 契约稳定性 | B | 输出强类型提升明显，但输入仍弱类型 |
| 可测试性 | B+ | 关键编排与策略已具备专项测试 |
| 可演进性 | B | 规则硬编码限制后续策略治理 |

## 7. 风险优先级建议

### 7.1 P1（建议优先处理）

1. 拆分 `ChainOfThoughtService` 与 `DebateCoordinator`，将编排与规则分离。
2. 将 `ThoughtTreeService` 的评分规则与终止判定抽为可替换策略组件。
3. 为 `ReasoningRequest` 引入强类型输入对象（至少覆盖核心字段）。

### 7.2 P2（可并行推进）

1. `ReasoningStrategySelector/ReasoningDegradePolicy` 规则配置化。
2. `ReasoningExecutionPlan` 改为不可变对象并增加构建期校验。
3. 增加策略治理指标：降级命中率、仲裁胜出分布、并行失败类型分布。

## 8. 最终判断

`reasoning` 包已从“可用”提升到“可维护且可扩展的雏形”，但尚未达到“高内聚、低耦合、强约束”的成熟状态。
在当前阶段给出 **B+** 评级较为客观；若完成 P1 项收敛，可提升到 **A-**。
