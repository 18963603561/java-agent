# `runtime` 第二阶段整改任务清单（类/方法级可执行版）

## 一、范围与目标

- 范围：基于 `doc/runtime包设计合理性与坏味道评估-202602071330.md` 的“第二阶段”建议执行整改。
- 周期建议：`2~4` 周。
- 目标：
  - 拆分超大类，降低单类复杂度和变更风险。
  - 消除关键双向依赖，恢复分层稳定性。
  - 在不改变业务语义前提下，提升可维护性与可测试性。
- 非目标：
  - 不做第三阶段的全面类型化改造。
  - 不做跨模块（`capabilities`）大规模架构重写。

## 六、风险与回滚策略

- 风险 1：拆分类后行为细节偏移。
  - 缓解：每拆一类即补定向测试并执行阶段回归。
- 风险 2：模型输出组装字段兼容性回归。
  - 缓解：对 `OutputKeys` 相关字段做快照断言测试。
- 风险 3：接口迁移导致循环依赖临时放大。
  - 缓解：先引入 `contract` 层再逐步替换引用。

回滚策略：

- 每个任务独立提交与回滚（D/E/F/G/H 分支化推进）。
- 若 D 或 E 失败：保留原门面类完整实现并回退新增协同器引用。
- 若 G 或 H 失败：保留旧模型位置与旧包引用，待契约迁移完成后二次切换。
