# 运行时核心类重构设计分析

## 1. 分析范围与目标

本次分析范围包含以下三个类：

- `src/main/java/com/example/agent/runtime/engine/AgentRuntime.java`
- `src/main/java/com/example/agent/runtime/engine/StepRuntimeService.java`
- `src/main/java/com/example/agent/planning/PlannerService.java`

目标是进行设计层面重构分析，而不是立即改写全部实现。核心诉求如下：

- 降低单类职责密度，减少“一个类承担完整流程”的风险。
- 收敛运行时编排、规划、结果装配的边界，便于测试与演进。
- 在不破坏现有行为的前提下，给出可分阶段落地的重构路径。

## 2. 复杂度基线

基于当前代码静态统计（2026-02-05）：

| 类 | 行数 | 方法数 | if 分支数 | catch 数 | 构造参数数 | private final 字段数 |
|---|---:|---:|---:|---:|---:|---:|
| `AgentRuntime` | 2005 | 75 | 191 | 6 | 30 | 28 |
| `PlannerService` | 1411 | 53 | 152 | 7 | 9 | 11 |
| `StepRuntimeService` | 514 | 23 | 57 | 0 | 8 | 9 |

结论：三个类都存在高复杂度，`AgentRuntime` 与 `PlannerService` 尤其明显，已超过“单类可控编排器”范围。

## 3. 当前设计主要问题

### 3.1 `AgentRuntime` 的问题

核心症状：运行时主类同时承担“流程编排 + 步骤执行 + 策略决策 + 上下文组装 + 审批控制 + 事件发布 + 结果拼装”。

典型表现：

- `run(...)` 同时做内存召回、上下文快照、规划、循环执行、重规划、最终输出、落库。
- `executeStep(...)` 用超长 `if/else` 分发多种步骤类型（`LLM/TOOL/REACT/THOUGHT_TREE/DEBATE/RESEARCH/...`）。
- 审批与执行控制逻辑分散在 `applyExecutionControl(...)` 和 `requestApprovalIfNeeded(...)`，与步骤执行耦合。
- 工具参数解析链过长：`resolveToolName*`、`resolveToolArguments*`、`resolveFlatToolArguments(...)`、`filterReservedToolArguments(...)`。
- `Map<String, Object>` 运行时上下文在全链路传递，键名约定分散，缺少类型边界。

设计风险：

- 新增一步骤类型会继续膨胀主类，变更回归面不断扩大。
- 执行、审批、重试、回退相互穿插，导致故障定位成本高。
- 过度依赖“字符串键 + 约定”，隐藏运行时错误。

### 3.2 `PlannerService` 的问题

核心症状：规划服务同时承担“能力评估 + LLM 规划 + JSON 修复 + 规则回退 + 提示词装配 + 上下文摘要 + 计划解析”。

典型表现：

- `plan(...)` 内同时处理评估、上下文写回、LLM 路径、回退路径。
- `tryLlmPlan(...)` 内部包含提示词构建、模型调用、解析、修复、trace 记录。
- `buildHeuristicPlan(...)` 包含多策略分支拼装，逐步扩展后复杂度会快速攀升。
- `buildPlanPrompt(...)` 内嵌超长提示词文本，代码和策略内容耦合。
- `parsePlan(...)` 与 `buildStepSpec(...)` 既做结构转换，又做约束校验和兼容逻辑。

设计风险：

- 规划策略变更与模型调用链路强耦合，难以独立验证。
- 提示词更新需要改代码并重新回归编译链。
- 回退路径与 LLM 路径一致性难长期保障。

### 3.3 `StepRuntimeService` 的问题

核心症状：步骤生命周期管理与结果装配强耦合。

典型表现：

- `startStep(...)`、`completeStep(...)`、`failStep(...)` 同时处理状态机、事件、指标、存储。
- `completeStep(...)` 内叠加摘要生成、结果构造、事件发布、落库。
- `buildStepResult(...)` 下挂 `resolveRaw*`、`resolveRefs(...)`、`resolveStructured(...)`、`resolveSummary(...)`，结果装配逻辑集中。

设计风险：

- 结果模型一旦扩展，生命周期服务会持续膨胀。
- “状态变更”与“输出结构转换”难以分别测试。

## 4. 目标架构（重构后）

建议从“按流程拆分”转为“按职责拆分”，形成三个编排层。

### 4.1 Runtime 层

建议角色：

- `RuntimeOrchestrator`：仅负责主流程编排与阶段切换。
- `RuntimePreparationService`：召回记忆、构建上下文、同步证据。
- `StepExecutionCoordinator`：循环执行、重试、回退、重规划触发。
- `StepExecutorRouter`：按步骤类型路由到对应执行器。
- `ApprovalGateService`：统一审批判定、申请、等待、结果回写。
- `ExecutionControlGate`：统一暂停/恢复/取消控制。

### 4.2 Planning 层

建议角色：

- `PlanningFacade`：统一入口与策略分派。
- `CapabilityPolicyService`：能力评估与上下文写回。
- `LlmPlanGenerator`：提示词装配、模型调用、解析修复。
- `HeuristicPlanGenerator`：规则规划生成。
- `PlanNormalizer`：`Map -> StepSpec` 规范化转换。
- `PlanValidationService`：规则约束校验（如 TOOL 参数完整性）。

### 4.3 Step 生命周期层

建议角色：

- `StepLifecycleService`：`start/complete/fail` 的状态和持久化。
- `StepEventPublisher`：事件发布与序列管理。
- `StepMetricsService`：指标打点。
- `StepResultAssembler`：`raw/structured/summary/refs` 装配。

## 5. 关键重构原则

- 行为不变优先：先拆结构，不改业务语义。
- 先提取对象，再提取策略：优先消除“长参数 + Map 直传”。
- 运行时上下文类型化：引入 `RuntimeContext` 包装，统一键定义与访问器。
- 步骤执行插件化：以 `StepTypeExecutor` 接口替代 `if/else` 链。
- 规划双轨一致性：LLM 与规则规划共同经过 `PlanNormalizer + PlanValidationService`。

## 6. 分阶段落地方案

### 阶段 0：建立防护网

交付：

- 为 `AgentRuntime`、`PlannerService`、`StepRuntimeService` 建立现有行为回归基线测试。
- 抽取关键场景快照：`TOOL`、`REACT`、`RESEARCH`、审批、回退、重规划。

收益：

- 后续拆分类可以“边拆边验”，降低回归风险。

### 阶段 1：拆 `AgentRuntime` 的前后处理

交付：

- 提取 `RuntimePreparationService`。
- 提取 `RuntimeFinalizationService`（最终输出、记忆持久化）。
- `AgentRuntime` 仅保留流程骨架。

收益：

- `run(...)` 由“全能方法”降为“阶段编排方法”。

### 阶段 2：拆步骤执行路由

交付：

- 新增 `StepTypeExecutor` 接口与默认实现集合。
- 提取 `StepExecutorRouter`。
- 把 `executeStep(...)` 的类型分发迁移到各执行器。

收益：

- 增加新步骤类型时不再修改主编排器。

### 阶段 3：拆审批与执行控制

交付：

- 抽出 `ApprovalGateService` 与 `ExecutionControlGate`。
- `AgentRuntime` 只在固定时机调用 gate。

收益：

- 审批逻辑与执行逻辑解耦，测试场景更清晰。

### 阶段 4：拆规划服务

交付：

- `PlannerService` 改为 `PlanningFacade`。
- 提取 `LlmPlanGenerator`、`HeuristicPlanGenerator`、`PlanNormalizer`、`PlanValidationService`。
- 提示词模板从代码搬到资源文件（例如 `resources/prompts/planner.md`）。

收益：

- 规划策略演进与模型调用链路可独立迭代。

### 阶段 5：拆步骤结果装配

交付：

- `StepRuntimeService` 拆出 `StepResultAssembler`、`StepEventPublisher`、`StepMetricsService`。
- `completeStep(...)` 只做状态切换和编排。

收益：

- 生命周期管理与结果结构演进解耦。

## 7. 建议优先级

建议先做阶段 1 和阶段 2，再做阶段 4。

原因：

- `AgentRuntime` 是当前复杂度和变更风险最高点。
- 先把执行编排稳定下来，再拆规划链路，能降低联动风险。

## 8. 风险与缓解

主要风险：

- 重构后事件时序变化，导致下游订阅或测试断言变化。
- 运行时上下文键迁移时出现兼容问题。
- LLM 规划与回退规划在新归一化流程中行为差异暴露。

缓解手段：

- 对 `EventType` 事件顺序建立契约测试。
- 引入过渡期适配器：旧键仍可读，新键优先写。
- 对 LLM/回退两条路径输出同构校验（结构、必填字段、审批位）。

## 9. 验收标准

- 三个类的主类行数和方法数显著下降。
- `AgentRuntime` 不再直接包含步骤类型 `if/else` 长链。
- `PlannerService` 不再直接承载超长提示词文本。
- `StepRuntimeService` 不再直接装配完整 `StepResult` 细节。
- 全量测试通过，关键回归场景通过。

## 10. 建议的第一批落地任务清单

- 任务 1：新增 `RuntimePreparationService` 并迁移 `run(...)` 前置逻辑。
- 任务 2：新增 `RuntimeFinalizationService` 并迁移最终输出与记忆写入逻辑。
- 任务 3：定义 `StepTypeExecutor` 接口并落地 `LLM/TOOL/REACT` 三类执行器。
- 任务 4：把审批决策与等待逻辑迁入 `ApprovalGateService`。
- 任务 5：为新边界补齐契约测试（事件顺序、步骤输出结构、审批行为）。
