# planning 包设计合理性评审

## 1. 评审范围
- 代码范围：`src/main/java/com/example/agent/planning`
- 关联调用：`src/main/java/com/example/agent/runtime/engine/AgentRuntime.java`
- 测试依据：`src/test/java/com/example/agent/planning/PlannerServiceTest.java`
- 核验命令：`mvn -q -Dtest=PlannerServiceTest test`

## 2. 总体结论与等级
- 总体等级：**C（中高风险，当前可用但可维护性偏弱）**
- 结论摘要：
  - `planning` 包对外职责清晰（生成 `PlanResult` 供运行时消费），但内部实现过度集中到 `PlannerService`，形成明显单点复杂度。
  - `PlannerService` 同时承担策略决策、提示词构造、模型调用、结果修复、解析、事件发布、审批注入，职责边界不清。
  - 包内存在“模型缺血 + 服务肥大”组合，导致扩展和回归成本上升。
  - 日志可观测性虽有覆盖，但存在中文乱码、异常堆栈缺失、关键信息粒度不足的问题。

## 3. 维度评分

| 维度 | 等级 | 说明 |
|---|---|---|
| 包职责边界 | B- | 对外接口统一通过 `PlannerService.plan(...)`，入口清晰；但入口内部承载过多职责。 |
| 内聚性 | D+ | `PlannerService` 行数 1759、方法数 41、导入 42，明显“上帝类”倾向。 |
| 耦合度 | C- | 直接依赖 `capabilities/governance/budget/runtime/streaming/security/api` 多域能力，改动扩散面大。 |
| 可扩展性 | C | 策略分支以 `if/else + Map key` 叠加，新增策略会继续推高复杂度。 |
| 可测试性 | B- | 已有 `PlannerServiceTest`，但测试主要围绕行为结果，内部复杂路径依赖大量 Mock。 |
| 可观测性 | C- | 有 `info/warn` 节点，但异常多处仅记录 `ex.getMessage()`，且日志文本存在乱码。 |

## 4. 主要坏味道清单（按严重度）

### 高严重度

1) **上帝类（God Class）**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:58`
- 量化：该类 1759 行、41 个方法、42 个导入，聚合了规划全链路能力。
- 风险：任一子功能变更（例如提示词、解析、事件、审批）都可能影响整类回归。

2) **文本编码污染（提示词与日志可读性风险）**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:842`（长提示词），`src/main/java/com/example/agent/planning/PlannerService.java:600`（日志文案）。
- 现象：源码中中文文本为乱码形态；执行 `PlannerServiceTest` 时日志输出出现乱码（如“瑙勫垝...”）。
- 风险：
  - 提示词语义失真，影响模型规划质量稳定性。
  - 生产日志可读性差，故障排查成本上升。

3) **异常处理弱化（吞错倾向）**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:628`
- 现象：捕获 `Exception` 后返回 `null`，日志仅记录 `ex.getMessage()`，未附堆栈。
- 风险：问题定位困难，且可能把真实故障误判为“可回退场景”。

### 中严重度

4) **策略分支重复与逻辑复制**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:671`、`src/main/java/com/example/agent/planning/PlannerService.java:752`、`src/main/java/com/example/agent/planning/PlannerService.java:780`、`src/main/java/com/example/agent/planning/PlannerService.java:817`
- 现象：摘要拼装与 `context.put("planSteps"/"planDependencies"/"executionStrategy"/"cognitiveStrategy")` 多处重复。
- 风险：后续改一处漏一处，产生行为不一致。

5) **魔法字符串泛滥（弱类型上下文）**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:381`、`src/main/java/com/example/agent/planning/PlannerService.java:1030`、`src/main/java/com/example/agent/planning/PlannerService.java:1645`
- 现象：大量依赖 `Map<String, Object>` + 字符串键访问，键名分散，约束不集中。
- 风险：拼写错误难被编译期发现，跨模块协作容易产生隐式契约偏差。

6) **可疑/退化逻辑**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:1577`
- 现象：`resolveExecutionStrategy(...)` 的分支返回值均为 `"sequential"`。
- 风险：方法形态与业务意图不一致，增加理解成本。

7) **复杂度估算规则疑似受编码影响**
- 证据：`src/main/java/com/example/agent/planning/PlannerService.java:1533`
- 现象：`split` 正则字符集出现乱码字符。
- 风险：复杂度评分偏差，影响策略选择结果。

### 低严重度

8) **包内模型存在闲置类（疑似历史遗留）**
- 证据：`src/main/java/com/example/agent/planning/Plan.java:9`、`src/main/java/com/example/agent/planning/PlanRequest.java:8`
- 现象：在 `src/main/java` 与 `src/test/java` 未检索到有效引用。
- 风险：增加认知负担，误导新开发者。

## 5. 设计合理性正向点
- 规划入口稳定：`PlannerService.plan(...)` 输出统一 `PlanResult`，与运行时边界清楚。
- 具备回退机制：LLM 失败可回退启发式规则，韧性基础较好。
- 具备修复链路：`JsonOutputRepairService` 参与输出修复，避免因格式噪音直接失败。
- 具备审批注入：能力评估结果可向步骤注入审批要求，治理链路有落点。

## 6. 建议整改优先级

### P0（优先处理）
1. 修复 `PlannerService` 中文文本编码，保证提示词、日志、注释可读。
2. 异常日志统一输出堆栈（至少在 `warn/error` 级别保留 `ex`）。
3. 将 `buildPlanPrompt(...)` 从服务类抽离为独立模板组件，避免超长内嵌字符串。

### P1（短期处理）
1. 拆分类职责：
   - `LlmPlanEngine`（模型请求与回包）
   - `HeuristicPlanBuilder`（规则规划）
   - `PlanParser`（解析与校验）
   - `PlanTelemetry`（事件与指标）
2. 引入 `PlanningContext` 强类型对象，替代核心链路中的裸 `Map<String, Object>`。
3. 提取上下文键常量，集中维护键名契约。

### P2（中期处理）
1. 清理或合并未使用的 `Plan`、`PlanRequest`。
2. 为 `planning` 增加编码守卫测试，避免再次引入乱码文本。
3. 将策略分支改为可扩展注册机制（策略枚举/策略处理器）。

## 7. 验收建议
- 功能验收：在 `PlannerServiceTest` 基础上增加“提示词关键语义断言”和“异常日志堆栈断言”。
- 架构验收：`PlannerService` 行数降至 600 行以内、核心职责拆分为至少 3 个协作组件。
- 可观测验收：关键外部调用具备开始/结束日志与错误堆栈，日志中文可读。
