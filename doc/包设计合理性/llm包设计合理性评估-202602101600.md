# `capabilities/llm` 包设计合理性评估

## 1. 评估范围

- 评估对象：`src/main/java/com/example/agent/capabilities/llm`
- 评估维度：分层边界、职责内聚、依赖方向、扩展性、可维护性、可观测性
- 参考实现：同时抽查了调用侧与架构守卫测试

## 2. 结论摘要

- 总体结论：**中上，整体可用，具备持续演进基础**。
- 当前包结构在“按能力分包”上比较清晰，且关键调用链路的日志、事件、错误映射较完整。
- 主要风险集中在：**分层反向依赖、局部职责过重、重复实现与 Map 协议键散落**。
- 若按优先级推进 2~3 轮重构，可将维护成本和回归风险明显下降。

## 3. 结构盘点

当前子包与文件规模：

- `client`：14
- `config`：2
- `contract`：5
- `prompt`：13

- `client -> contract/prompt/provider/support`

检测到一个显式双向循环依赖：

- `config <-> provider`

## 5. 主要问题与合理性风险

### 5.1 分层边界反向耦合（优先级：高）

- `prompt` 和 `tooling` 直接依赖 HTTP 层 DTO `TaskRequest`，导致领域能力层被接口层反向牵引。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/prompt/PromptAssembler.java:3`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/prompt/PromptAssemblyContextResolver.java:3`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/tooling/ToolingContextMapper.java:3`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/tooling/ModelToolResolver.java:9`
- 影响：后续若接入新入口（非 HTTP）会扩大改造面，且测试替身需要模拟接口层对象。

### 5.2 内部存在 `config <-> provider` 双向依赖（优先级：高）

- `ModelConfigProperties` 持有 `provider.ModelDefinition`，同时 `provider` 又依赖 `config`。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/config/ModelConfigProperties.java:3`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/ModelRouter.java:3`
- 影响：配置模型与执行模型概念耦合，增加演进成本，妨碍模块独立测试与未来拆分。

### 5.3 局部类职责过重（优先级：高）

- `ModelInvocationService`（285 行）同时承担参数兜底、路由、调用、事件、失败映射、追踪计算。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/client/ModelInvocationService.java:30`
- `ModelToolResolver`（393 行）同时承担上下文解析、技能约束、工具筛选、按需加载、指标与日志。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/tooling/ModelToolResolver.java:34`
- `LocalFallbackStrategy`（412 行）包含多个场景专用兜底生成逻辑，已接近“策略集合体”。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/LocalFallbackStrategy.java:27`

### 5.4 协议模型边界不够纯（优先级：中）

- `contract.ModelRequest` 依赖 `prompt.PromptMessage`，导致“请求契约”绑定“提示词实现细节”。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/contract/ModelRequest.java:3`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/prompt/PromptMessage.java:6`
- 影响：`contract` 复用时需要连带引入 `prompt`，弱化“纯契约层”价值。

### 5.5 重复实现与模板化不足（优先级：中）

- `resolvePrompt` 在 `DefaultModelProvider` 与 `ModelMessageBuilder` 各实现一份。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/DefaultModelProvider.java:120`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/ModelMessageBuilder.java:79`
- `OpenAiProviderAdapter` 与 `OllamaProviderAdapter` 的调用骨架高度重复（建请求、超时、异常映射、统计）。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/OpenAiProviderAdapter.java:65`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/OllamaProviderAdapter.java:63`
- `resolveToolCount` 在两个适配器重复。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/provider/OpenAiProviderAdapter.java:126`

### 5.6 空指针边界存在隐患（优先级：中）

- `PromptTrimEngine.resolvePromptBudgetTokens` 未判空 `allocation`，若上游漏填预算分配会触发 NPE。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/prompt/PromptTrimEngine.java:53`
  - 证据：`src/main/java/com/example/agent/capabilities/llm/prompt/PromptTrimEngine.java:115`

### 5.7 Map 协议键散落（优先级：中）

- `metadata/context` 键名在 `ModelInvocationService`、`LlmEventPublisher`、`ToolingContextMapper` 多处硬编码。
  - 证据：`src/main/java/com/example/agent/capabilities/llm/client/ModelInvocationService.java:91`

- 影响：字段重命名和跨模块协作时容易“静默不兼容”。

## 6. 建议改造路线

### 6.1 第一阶段（建议先做，低风险高收益）

- 增加空安全：为 `PromptTrimEngine.resolvePromptBudgetTokens` 增加 `allocation == null` 兜底。
- 统一重复方法：保留 `ModelMessageBuilder.resolvePrompt`，删除 `DefaultModelProvider` 私有重复实现。
- 抽公共模板：提炼 `BaseHttpProviderAdapter` 或 `ProviderInvocationTemplate`，收敛两家适配器重复骨架。

### 6.2 第二阶段（结构优化）

- 拆分 `ModelInvocationService`：
  - `InvocationContextFactory`（入参归一化）
  - `InvocationExecutor`（调用与错误映射）
  - `InvocationTelemetryPublisher`（日志/事件/指标）
- 拆分 `LocalFallbackStrategy` 为多场景处理器注册表，例如 `FallbackHandler`。

### 6.3 第三阶段（分层治理）

- 引入能力层输入模型，例如 `LlmTaskContext`，由入口层负责把 `TaskRequest` 转换后再进入 `prompt/tooling`。
- 打破 `config <-> provider`：将 `ModelDefinition` 下沉到 `contract` 或新建 `model` 包，避免配置层依赖执行层。
- 收敛 Map 键为常量类或强类型元数据对象，优先治理 `promptScene/provider/scene/toolChoice/disableTools`。

## 7. 综合评价

- 若按“可读性、扩展性、稳定性、治理完备度”四项评分，当前可给 **7.5/10**。
- 当前设计已经具备工程化框架，但尚未达到“长期低成本演进”的最佳态。
- 结论建议：**保持现有包边界不大改，优先做边界去耦与职责拆分**，可以在不破坏现有功能的前提下提升长期可维护性。
