# 超千行实现类复杂度分析与重构建议

## 1. 目标与范围

本次分析目标：

- 识别 `src/main/java` 下实现代码超过 1000 行的类。
- 评估这些类是否存在设计不合理问题。
- 给出可落地的重构建议与优先级。

说明：

- 行数为静态扫描结果（包含注释与空行）。
- 复杂度参考指标包含：方法数、`if` 分支数、`catch` 数。

## 3. 设计合理性判定

### 3.1 高风险（明确存在设计不合理）

1) `AgentRuntime`

- 判定：设计不合理（高风险）。
- 原因：运行时编排、步骤路由、审批门禁、失败恢复、上下文写回、最终输出等职责仍集中在单类，变更面过大。
- 风险：新增步骤类型或恢复策略时，回归范围大且故障定位困难。

2) `PlannerService`

- 判定：设计不合理（高风险）。
- 原因：评估策略、LLM 规划、修复、规则规划、归一化、校验等逻辑仍有较高耦合，属于“门面 + 细节实现”混合。
- 风险：策略升级和提示词演进容易牵动核心流程。

3) `LlmStepService`

- 判定：设计不合理（高风险）。
- 原因：模型调用编排、工具摘要模式、参数注入、输出清洗等高度聚合，边界不清晰。
- 风险：任何模型协议变化都会影响工具链路与输出契约。

4) `McpToolClient`

- 判定：设计不合理（高风险）。
- 原因：协议适配、重试、降级、初始化、调用、异常处理都在同一类，`catch` 数明显偏高。
- 风险：网络抖动和协议变体导致逻辑分支爆炸，维护成本高。

### 3.2 中风险（存在明显膨胀，需要拆分）

1) `DefaultModelProvider`

- 判定：中风险。
- 原因：多模型适配与默认策略可能共存于同一实现，条件分支偏多。
- 建议：按模型家族拆 provider adapter，再由 facade 聚合。

2) `DefaultContextBuilder`

- 判定：中风险。
- 原因：上下文拼装、预算、裁剪、证据合并职责有交叉。
- 建议：拆为 `ContextAssemble`、`BudgetApply`、`TrimApply` 三段管线。

3) `DefaultContextTrimmer`

- 判定：中风险。
- 原因：规则判断和实际裁剪算法耦合，分支密度偏高。
- 建议：将“裁剪策略决策”与“裁剪执行器”解耦。

### 3.3 可接受但建议优化（低到中风险）

1) `StepOutputSummaryBuilder`

- 判定：低到中风险。
- 原因：虽然行数较大，但职责相对聚焦在摘要构建。
- 建议：可按输入摘要、输出摘要、digest 计算做内部模块化。

2) `ChainOfThoughtService`

- 判定：低到中风险。
- 原因：属于算法型服务，复杂度来源于推理流程本身。
- 建议：优先抽离模板与策略，保留核心流程主干。

## 4. 优先级建议（按收益/风险比）

### P0（优先立即推进）

- `AgentRuntime`
- `PlannerService`
- `McpToolClient`

目标：先降编排层复杂度与外部不稳定依赖的耦合度。

### P1（紧随其后）

- `LlmStepService`
- `DefaultModelProvider`
- `DefaultContextBuilder`

目标：统一模型与上下文链路边界，减少横向连带改动。

### P2（持续治理）

- `DefaultContextTrimmer`
- `StepOutputSummaryBuilder`
- `ChainOfThoughtService`

目标：在不改语义前提下做模块化拆分与测试补强。

## 5. 具体落地建议

1) 统一采用“门面 + 组件”结构

- 门面类只保留流程编排。
- 细节下沉到可独立测试的组件类。

2) 统一 DTO/上下文边界

- 减少 `Map<String,Object>` 跨层透传。
- 为关键阶段定义显式输入输出对象。

3) 强化契约测试

- 先为事件顺序、步骤输出结构、审批状态迁移建立回归用例。
- 再做拆分，确保每个 PR 可独立验证。

4) 控制单类复杂度阈值

- 建议阈值：单类 < 800 行，方法数 < 35，`if` 分支 < 80。
- 超阈值类进入“重构候选池”。

## 6. 结论

当前工程中超过 1000 行的类大多存在不同程度的设计膨胀，尤其 `AgentRuntime`、`PlannerService`、`LlmStepService`、`McpToolClient` 已达到高风险区间。建议继续沿你已采用的最小 PR 切分方式推进，将复杂类逐步收敛到“单一主责 + 可替换组件”的结构。
