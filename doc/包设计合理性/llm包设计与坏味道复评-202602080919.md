# `llm` 包设计合理性与坏味道复评

## 1. 评审范围与结论摘要

评审范围：`src/main/java/com/example/agent/capabilities/llm`

本次基于当前代码快照重新评估包设计与代码质量，重点关注：

1. 分层与职责边界是否清晰
2. 包间依赖是否稳定、是否存在反向耦合
3. 是否存在明显坏味道（大类、魔法键、协议漂移、可维护性风险）

### 总体等级

1. **包设计合理性等级：B+**
2. **代码坏味道等级：中度（P1×3，P2×5，P0×0）**
3. **综合等级：B（78/100）**

结论：

1. P2 拆包方向是正确的，`client/provider/prompt/tooling/repair/config/support` 的域边界基本成型。
2. 当前主要风险已从“结构混乱”转为“局部耦合与实现复杂度偏高”。
3. 若继续演进，建议优先消除 `provider <-> tooling` 双向依赖与超大类职责过载。

## 2. 结构合理性评估

## 2.1 正向结果（做得好的部分）

1. 根包已瘦身，子包语义明确，聚合度较上一轮显著提升。
2. `client` 内已形成统一执行结果协议（`LlmExecutionResult` 等），事件结构化程度明显提升。
3. 错误码映射与可观测性已有统一入口：`ProviderErrorMapper` + `llm_invocation_error_total` 指标。
4. `ModelInvocationService` 已具备调用开始/结束/失败日志，关键链路可追踪。

## 2.2 依赖关系观察

静态扫描得到的主要包间依赖（跨包）包括：

1. `client -> prompt/provider/support`
2. `provider -> config/prompt/tooling`
3. `tooling -> provider`
4. `repair -> client/provider/prompt/support`

其中最值得关注的是：

1. **`provider` 与 `tooling` 已形成双向依赖**，会导致后续拆分与复用成本上升。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/provider/ModelRequest.java:4`
2. `src/main/java/com/example/agent/capabilities/llm/provider/ModelRequest.java:5`

## 3. 坏味道清单（含等级）

分级定义：

1. `P0`：高风险、应立即处理（功能正确性/稳定性直接受影响）
2. `P1`：中高风险、应优先处理（架构腐化、维护成本快速上升）
3. `P2`：中低风险、可排期处理（可读性/一致性/扩展性隐患）

## 3.1 P1 级问题

### P1-1 包双向依赖（`provider <-> tooling`）

现象：

1. `provider` 依赖 `ModelToolChoice/ModelToolDefinition`。
2. `tooling` 反向依赖 `provider.ModelRequest`。

风险：

1. 破坏单向依赖边界，后续提取独立模块时会出现牵一发而动全身。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/provider/ModelRequest.java:4`
2. `src/main/java/com/example/agent/capabilities/llm/provider/ModelRequest.java:5`
3. `src/main/java/com/example/agent/capabilities/llm/tooling/ModelToolResolver.java:4`

建议：

1. 提取 `llm.contract`（或 `llm.model`）承载 `ModelRequest/ModelToolChoice/ModelToolDefinition` 等共享协议对象。
2. 使 `provider` 与 `tooling` 仅依赖共享协议，不互相依赖实现包。

### P1-2 超大类职责过载

现象：

1. `DefaultPromptAssembler`（639 行）同时承担上下文补齐、预算裁剪、消息拼装、指标上报。
2. `ModelInvocationService`（533 行）同时承担路由、调用、事件映射、rawRef 管理、错误指标。
3. `LocalFallbackStrategy`（412 行）同时承担场景识别、上下文解析、多场景兜底生成。
4. `ModelToolResolver`（390 行）同时承担策略决策、目录查询、schema 装配、指标与日志。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/prompt/DefaultPromptAssembler.java:25`
2. `src/main/java/com/example/agent/capabilities/llm/client/ModelInvocationService.java:40`
3. `src/main/java/com/example/agent/capabilities/llm/provider/LocalFallbackStrategy.java:24`
4. `src/main/java/com/example/agent/capabilities/llm/tooling/ModelToolResolver.java:32`

建议：

1. 按“编排器 + 纯函数组件”拆分，每类控制在约 200~300 行内。
2. 先拆分 `ModelInvocationService` 与 `DefaultPromptAssembler`，收益最大。

### P1-3 `LocalFallbackStrategy` 对 Prompt 标记耦合过深

现象：

1. 基于多个字符串 marker（`PLAN_CONTEXT_JSON` 等）解析 prompt，再走大量分支生成 JSON。
2. 同时大量依赖 `Map<String, Object>` 魔法键读取（静态扫描 `.get("...")` 为 35 处）。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/provider/LocalFallbackStrategy.java:28`
2. `src/main/java/com/example/agent/capabilities/llm/provider/LocalFallbackStrategy.java:35`
3. `src/main/java/com/example/agent/capabilities/llm/provider/LocalFallbackStrategy.java:62`

风险：

1. Prompt 模板轻微调整即可触发兜底失配，扩场景时修改风险高。

建议：

1. 改为“显式场景枚举 + 场景处理器注册表”的策略模式。
2. 将 marker 协议从自由文本改为结构化 metadata 输入。

## 3.2 P2 级问题

### P2-1 事件 metadata 合并存在覆盖核心字段风险

现象：

1. 已写入 `phase/scene/provider/modelId/...` 后，再 `putAll(metadata)`。
2. 若 metadata 含同名 key，会覆盖核心字段。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/client/events/LlmEventPayloadMapper.java:46`
2. `src/main/java/com/example/agent/capabilities/llm/client/events/LlmEventPayloadMapper.java:80`
3. `src/main/java/com/example/agent/capabilities/llm/client/events/LlmEventPayloadMapper.java:91`

建议：

1. metadata 仅允许白名单字段或统一加前缀（如 `ext_`）。
2. 对核心 key 做不可覆盖保护。

### P2-2 请求协议键名并存导致语义漂移

现象：

1. 同时写入 `tool_choice` 与 `toolChoice`。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/provider/ModelRequestBodyBuilder.java:55`
2. `src/main/java/com/example/agent/capabilities/llm/provider/ModelRequestBodyBuilder.java:56`

建议：

1. 每个 Provider 只输出其官方协议键名，兼容映射下沉到适配层。

### P2-3 Provider 识别依赖字符串包含判断

现象：

1. 通过 `normalized.contains("openai"/"deepseek"/"ollama")` 判断适配器。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/provider/OpenAiProviderAdapter.java:55`
2. `src/main/java/com/example/agent/capabilities/llm/provider/OllamaProviderAdapter.java:55`

建议：

1. `ModelDefinition` 引入强类型 provider 枚举，避免名称漂移带来的错配。

### P2-4 `tooling` 层仍存在较多 Map 魔法键读取

现象：

1. `toolChoice/disableTools/allowTools` 等键在多个入口分支解析。

证据：

1. `src/main/java/com/example/agent/capabilities/llm/tooling/ToolingContextMapper.java:79`
2. `src/main/java/com/example/agent/capabilities/llm/tooling/ToolingContextMapper.java:101`
3. `src/main/java/com/example/agent/capabilities/llm/tooling/ToolingContextMapper.java:149`

建议：

1. 用单一入参 DTO 承载工具治理输入，Map 只在边界层做一次转换。

### P2-5 注释可读性异常（疑似编码问题）

现象：

1. 多文件 JavaDoc/注释存在明显不可读文本，维护与评审效率下降。

证据示例：

1. `src/main/java/com/example/agent/capabilities/llm/client/ModelInvocationService.java:37`
2. `src/main/java/com/example/agent/capabilities/llm/prompt/DefaultPromptAssembler.java:21`
3. `src/main/java/com/example/agent/capabilities/llm/provider/ProviderErrorMapper.java:10`

建议：

1. 对 `llm` 包执行一次注释层面的编码修复与统一校验（UTF-8/LF），并纳入 CI 守卫。

## 4. 包级评分（复评）

1. `client`：**B+**（链路收口较好，但编排职责仍偏重）
2. `provider`：**B-**（适配器抽象清晰，但兜底策略过大、协议键名与 provider 识别偏弱类型）
3. `prompt`：**C+**（能力齐全，但 `DefaultPromptAssembler` 过大）
4. `tooling`：**C+**（治理方向正确，但 Map 协议与跨包耦合仍高）
5. `repair`：**B-**（功能闭环可用，但仍与 `client/provider` 紧耦合）
6. `config/support`：**B**（职责基本单一）

---

## 5. 改造优先级建议（下一轮）

### 第一优先级（建议立即排期）

1. 消除 `provider <-> tooling` 双向依赖（提取共享协议层）。
2. 拆分 `ModelInvocationService` 与 `DefaultPromptAssembler`。
3. 重构 `LocalFallbackStrategy` 为场景处理器注册机制。

### 第二优先级

1. 收紧事件 metadata 覆盖策略。
2. 统一 Provider 请求键名规范（移除双键并存）。
3. Provider 识别改为强类型枚举。

### 第三优先级

1. 清理 `llm` 包注释可读性问题并建立编码守卫。

---

## 6. 结论

当前 `llm` 包已具备较好的分包基础和可观测能力，整体处于“结构可用、实现待提纯”的阶段。若按上述优先级完成下一轮重构，综合等级可从 **B** 提升至 **A-**。
