# `src/main/java/com/example/agent/governance` 包设计合理性与坏味道评估

## 1. 评估范围与方法

### 1.1 评估范围
- 评估目录：`src/main/java/com/example/agent/governance`
- 子包范围：`approval`、`replay`、`evaluation`、`policy`、`ratelimit`、`circuitbreaker`
- 关联调用链抽样：
  - `src/main/java/com/example/agent/api/http/controller/ToolApprovalController.java`
  - `src/main/java/com/example/agent/api/http/controller/ReplayController.java`
  - `src/main/java/com/example/agent/api/http/controller/PolicyController.java`
  - `src/main/java/com/example/agent/capabilities/tools/mcp/McpToolClient.java`
  - `src/main/java/com/example/agent/planning/capability/PlanningCapabilityService.java`

### 1.2 评估维度
- 分层清晰度（职责边界、DTO 放置位置）
- 模块内聚/耦合（跨包依赖规模、职责聚合度）
- 可靠性（并发安全、状态生命周期、异常处理）
- 可观测性（关键路径日志、异常日志、指标）
- 可测试性（关键治理组件是否具备直接单测）

### 1.3 额外校验
- 执行构建：`mvn -DskipTests clean compile`
- 结果：构建成功（当前源码可编译）

## 2. 总体结论与等级

### 2.1 总体等级
- **总体等级：C+（中等风险，建议进入专项治理）**

### 2.2 分项等级
- **包分层合理性：B-**
  - 优点：按治理能力拆分子包，语义可读性较好。
  - 问题：领域层与接口传输层 DTO 有混放。
- **模块内聚性：C+**
  - 优点：治理能力（审批、回放、限流、熔断）基本独立。
  - 问题：`ApprovalService`、`ReplayService` 业务聚合过重。
- **可靠性：C**
  - 问题：多个内存状态容器无淘汰策略，长期运行存在膨胀风险。
- **可观测性：C**
  - 问题：`ratelimit`、`circuitbreaker` 缺失日志，异常信息上下文不完整。
- **可测试性：C+**
  - 优点：`approval`、`replay`、`evaluation` 有单测覆盖。
  - 问题：`ratelimit`、`circuitbreaker` 缺少直接单测。

## 3. 结构合理性分析

### 3.1 正向评价
- 子包拆分方向合理：`approval`、`replay`、`policy`、`evaluation`、`ratelimit`、`circuitbreaker` 基本对应治理能力域。
- 外部集成位置相对统一：
  - 规划链路使用能力评估：`src/main/java/com/example/agent/planning/capability/PlanningCapabilityService.java:69`
  - MCP 调用链使用限流/熔断：`src/main/java/com/example/agent/capabilities/tools/mcp/McpToolClient.java:174`、`src/main/java/com/example/agent/capabilities/tools/mcp/McpToolClient.java:386`
- 治理功能在主流程中可见，说明并非“摆设包”。

### 3.2 分层问题
- **接口 DTO 下沉到治理域**：
  - `ToolApprovalDecisionRequest/Response` 位于 `governance.approval`，但被控制器直接作为入参出参：
    - `src/main/java/com/example/agent/api/http/controller/ToolApprovalController.java:4`
    - `src/main/java/com/example/agent/api/http/controller/ToolApprovalController.java:5`
  - `ReplayRequest/ReplayResponse` 同理：
    - `src/main/java/com/example/agent/api/http/controller/ReplayController.java:8`
    - `src/main/java/com/example/agent/api/http/controller/ReplayController.java:9`
  - `PolicyRequest/PolicyDecision` 同理：
    - `src/main/java/com/example/agent/api/http/controller/PolicyController.java:8`
    - `src/main/java/com/example/agent/api/http/controller/PolicyController.java:10`
- **影响**：治理域模型与 HTTP 传输协议耦合，后续更换接口协议时会牵动治理核心包。

## 4. 坏味道清单（含等级）

### 4.1 高等级（P1）

#### 问题 A：内存状态容器缺乏生命周期治理
- 证据：
  - 审批挂起表：`src/main/java/com/example/agent/governance/approval/ApprovalService.java:33`
  - 回放会话表：`src/main/java/com/example/agent/governance/replay/ReplayService.java:46`
  - 熔断状态表：`src/main/java/com/example/agent/governance/circuitbreaker/CircuitBreakerManager.java:15`
  - 限流计数表：`src/main/java/com/example/agent/governance/ratelimit/RateLimitService.java:15`
- 观察：
  - `ReplayService` 中 `sessions` 仅写入：`src/main/java/com/example/agent/governance/replay/ReplayService.java:79`，未见读取/清理路径。
  - `ratelimit` 与 `circuitbreaker` 仅增长，不做按时间清理或按容量淘汰。
- 风险：长时间运行时内存持续增长，影响稳定性。

#### 问题 B：异常语义被“宽捕获+统一改写”弱化
- 证据：
  - `src/main/java/com/example/agent/governance/replay/ReplayService.java:108`
  - `src/main/java/com/example/agent/governance/replay/ReplayService.java:110`
- 观察：`resolveTask` 捕获 `RuntimeException` 后统一抛 `REPLAY_NOT_FOUND`，原始异常原因不透出。
- 风险：数据库不可用、网络故障、鉴权异常等被误报为“未找到”，排障成本高。

### 4.2 中等级（P2）

#### 问题 C：服务类职责过重（类膨胀）
- 证据：
  - `ApprovalService`：`src/main/java/com/example/agent/governance/approval/ApprovalService.java:24`（347 行）
  - `ReplayService`：`src/main/java/com/example/agent/governance/replay/ReplayService.java:34`（273 行）
- 观察：
  - `ApprovalService` 同时承担审批状态管理、等待机制、决策写入、参数摘要构建、指标采集。
  - `ReplayService` 同时承担任务查询、事件拼装排序、流事件发布、会话状态维护。
- 风险：维护成本提升，后续功能迭代容易引入回归。

#### 问题 D：关键治理组件可观测性不足
- 证据：
  - `CircuitBreakerManager` 未见 `Logger`：`src/main/java/com/example/agent/governance/circuitbreaker/CircuitBreakerManager.java`
  - `RateLimitService` 未见 `Logger`：`src/main/java/com/example/agent/governance/ratelimit/RateLimitService.java`
- 观察：限流命中、熔断打开/恢复等关键治理事件无日志沉淀。
- 风险：线上“被限流/被熔断”时缺少证据链。

#### 问题 E：策略评估规则硬编码程度偏高
- 证据：
  - 固定风险加权：`src/main/java/com/example/agent/governance/evaluation/CapabilityBoundaryEvaluator.java:118`、`src/main/java/com/example/agent/governance/evaluation/CapabilityBoundaryEvaluator.java:120`
  - 关键字硬编码：`src/main/java/com/example/agent/governance/evaluation/CapabilityBoundaryEvaluator.java:152`、`src/main/java/com/example/agent/governance/evaluation/CapabilityBoundaryEvaluator.java:155`
- 风险：规则难以按租户/场景动态调优，策略实验门槛高。

### 4.3 低等级（P3）

#### 问题 F：疑似未使用模型
- 证据：`RateLimitRule` 在主代码仅定义未被引用：
  - `src/main/java/com/example/agent/governance/ratelimit/RateLimitRule.java:6`
- 风险：增加认知噪音，影响代码可读性。

## 5. 建议治理优先级

### 5.1 第一优先级（建议 1~2 周）
- 为 `replay/ratelimit/circuitbreaker` 增加状态清理机制：
  - 定时清理、按容量淘汰、TTL 过期。
- 修复 `ReplayService` 异常分层：
  - 区分“未找到”和“依赖故障”，保留原始异常上下文与堆栈日志。
- 为限流/熔断补齐关键日志与指标：
  - 限流命中次数、熔断开启次数、熔断恢复次数。

### 5.2 第二优先级（建议 2~4 周）
- 按分层原则迁移 HTTP DTO：将 `Request/Response` 移至 `api/http/dto`，治理域保留领域命令与结果模型。
- 拆分 `ApprovalService` 与 `ReplayService`：
  - 审批状态仓储、审批编排、摘要构建分离。
  - 回放项构建器、回放发布器、会话存储分离。

### 5.3 第三优先级（持续优化）
- 将评估关键字与风险参数配置化（支持灰度和租户级覆盖）。
- 清理未使用模型 `RateLimitRule` 或补全其应用场景。
- 为 `RateLimitService`、`CircuitBreakerManager` 增加直接单测，覆盖并发与边界情况。

---

## 6. 结论摘要

- 当前 `governance` 包在“能力域划分”上是合理的，但在“分层解耦、状态治理、可观测性”方面存在明显治理债务。
- 建议以“状态生命周期 + 异常可观测性”作为第一阶段治理重点；该方向收益最高，且对外行为改动最小。
- 综上，给出当前版本等级：**C+（中等风险，建议尽快治理）**。
