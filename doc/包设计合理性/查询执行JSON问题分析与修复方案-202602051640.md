# 查询执行 JSON 问题分析与修复方案（2026-02-05）

## 1. 背景
本方案针对你提供的一次执行结果 JSON 进行定位与修复。
目标是解决“结果可读性差、状态不一致、最终输出退化”的问题，并给出可验收方案。

## 2. 现象与问题清单

### 2.1 时长字段异常
现象：`meta.timing.endedAt` 与 `meta.timing.startedAt` 相差约 2.5 秒，但 `durationMs=0`。
影响：监控与审计链路无法反映真实耗时，误导性能分析。

### 2.2 状态字段前后矛盾
现象：顶层 `meta.status=COMPLETED`，但 `summary.stepSummary.status=STARTED`。
影响：同一条步骤记录内状态语义冲突，前端和排障容易误判。

### 2.3 摘要字段膨胀与重复
现象：`raw.data` 中已经包含 `inputDigest/outputDigest/outputSummary/toolResultSummary/stepSummary`，随后又在 `summary` 再封装一层。
影响：
- 输出体积被放大。
- `outputSummary.sample` 出现“把摘要再摘要”的重复嵌套。
- 关键信息被噪声淹没。

### 2.4 finalOutput 退化为 keys/size
现象：`finalOutput` 为 `{keys:[...], size:14}`，不是用户可直接消费的回答内容。
影响：调用方拿不到最终答案，需要再读 steps 才能恢复语义。

## 3. 根因定位

### 3.1 durationMs 为 0 的根因
`StepRuntimeService.completeStep(...)` 在构建 `StepResult` 之后才写入 `record.completedAt`。
`buildMeta(...)` 内部计算 `durationMs` 时，`completedAt` 仍为 `null`，导致时长固定为 0。

### 3.2 STARTED 状态污染的根因
`AgentRuntime` 在反思前调用 `enrichOutputSummaryForReflection(...)`，并把“临时摘要”直接 merge 回业务输出。
该时点 `record.status` 仍是 `STARTED`，后续 `completeStep(...)` 再做一次摘要，最终把 STARTED 摘要写进了完成态结果。

### 3.3 摘要膨胀的根因
同一输出在两个阶段被摘要：
- 反思前临时摘要（用于 Reflection）
- 完成时正式摘要（用于持久化输出）
且前者被写回原始输出，导致后者重复采样，形成层层嵌套。

### 3.4 finalOutput 退化的根因
`AgentRuntime.extractFinalOutput(...)` 先取 `structured.data`，再取 `raw.data`。
当前通用结构化提取器 `GenericStructuredExtractor` 默认产物是 `{keys,size}` 诊断结构，因此覆盖了真实回答。

## 4. 已实施修复

### 4.1 修复完成时间写入时机
文件：`src/main/java/com/example/agent/runtime/StepRuntimeService.java`
改动：在 `completeStep(...)` 中，将 `record.setCompletedAt(Instant.now())` 前移到构建 `StepResult` 之前。
结果：`meta.timing.durationMs` 与 started/ended 时间一致。

### 4.2 反思摘要与最终输出解耦
文件：`src/main/java/com/example/agent/runtime/AgentRuntime.java`
改动：
- 新增 `reflectionOutput` 变量。
- 反思评估使用 `reflectionOutput`。
- `completeStep(...)` 仍使用原始 `output`，不再回写临时摘要。
结果：避免 `STARTED` 摘要污染完成态输出，并消除摘要重复叠加。

### 4.3 最终输出提取优先级调整
文件：`src/main/java/com/example/agent/runtime/AgentRuntime.java`
改动：`extractFinalOutput(...)` 改为优先取 `raw.data`，再取 `structured.data`。
结果：`finalOutput` 优先返回真实回答字段（如 `answer`），不再被 `{keys,size}` 覆盖。

## 6. 验收清单（建议线上前自测）

1. 用“常识问答（无需工具）”复现一条 LLM 步骤，确认：
- `meta.status=COMPLETED`
- `summary.stepSummary.status=COMPLETED`
- `timing.durationMs > 0`

2. 检查同一条步骤的 `raw.data`，确认不再包含 `outputSummary/toolResultSummary/stepSummary` 这类临时摘要字段。

3. 检查任务级 `finalOutput`，确认包含 `answer`（或 `finalAnswer`）等业务字段，而不是仅 `keys/size`。

4. 检查 `refs/rawRef`，确认追踪链路不受本次改动影响。

## 7. 后续可选增强

1. 在 `StepRuntimeService` 增加 debug 日志，记录“摘要来源（反思临时/完成正式）”标记，便于排查。
2. 为 `extractFinalOutput(...)` 增加单测，覆盖“structured=DIAGNOSIS + raw 含 answer”场景。
3. 为 `finalOutput` 增加契约测试，防止未来改动再次回退到 keys/size 诊断结果。
