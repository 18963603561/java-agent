# 工具参数是否可完全交给大模型识别的确认与方案

## 1. 结论（先回答问题）
- 可以让大模型识别工具参数，从而提升通用性，但不能“完全替代”直接调用工具的执行链路。
- 原因：工具执行不仅是参数识别，还包含权限/重试/错误映射/结果落库与一致性校验。
- 因此推荐的做法是：
  - 大模型负责“参数识别与结构化”。
  - 执行器负责“工具调用与结果保障”。

## 2. 为什么不能仅把工具名和问题交给大模型
即便大模型能生成参数，也仍然需要执行器完成：
- 参数合规校验（缺参、类型、范围、枚举）。
- 工具执行与安全策略（鉴权、限流、审计）。
- 重试与错误码映射（统一失败处理策略）。
- 结果标准化与上下文回写（保证后续步骤可复用）。

如果跳过执行器，风险包括：
- 参数不完整导致工具失败或结果错误。
- 执行失败无法落到统一错误处理策略。
- 结果输出结构与系统约定不一致，影响反思与最终输出。

## 3. 可行的通用化方案（建议）
方案 A：参数识别交给大模型，执行仍由工具层完成
1) 规划或运行时：只需要提供 `toolName` 与 `question`。
2) 大模型进行参数识别，输出 `arguments`。
3) 执行器使用 `toolName + arguments` 调用工具。
4) 保留执行器的重试、错误映射、上下文回写。

方案 B：双阶段（判定 + 参数）
- 第 1 阶段：判断是否必须调用工具（或确认工具名）。
- 第 2 阶段：仅做参数结构化。
- 适用于“工具不是必选”的场景。

方案 C：强约束模式（已知必须调用）
- 规划阶段确定 `toolName`，并要求 LLM 只做参数识别。
- 执行器不再接受模型的“是否调用”判断，只接受参数。

## 4. 落地要点（与当前代码的适配方向）
- 在 `stepType=TOOL` 场景，保持 `toolChoice=specified`，保证工具不被模型改写。
- 在 `stepInput` 中增加/约定 `arguments` 字段作为模型输出目标。
- 执行器调用 `executeToolStep` 前做参数校验与补全（必要时再回退到模型重试）。
- 统一输出结构，保持与 `LlmStepService.run` 的 `mode/tool/toolStatus` 格式一致。

## 5. 推荐执行策略（结合现状）
- 继续保留模型参与参数识别（通用性强）。
- 不建议完全跳过执行器，执行仍由工具层完成。
- 通过 `toolChoice=specified` 约束工具名，避免工具漂移。

## 6. 建议的最小改动实现思路
- 为 `stepType=TOOL` 增加“参数识别模式”，让模型只输出 `arguments`。
- 执行器读取 `arguments`，直接走 `executeToolStep`。
- 失败时回退到原有 `llmStepService.run` 路径，以保证可用性。
