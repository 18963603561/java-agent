# 默认规则规划走 `demo_tool` 的利弊分析

## 背景
当前 `agent.planner.llm-enabled=false` 时，`PlannerService.buildHeuristicPlan` 会生成 `TOOL` 步骤。
当请求上下文未指定工具名时，`AgentRuntime.resolveToolName` 默认返回 `demo_tool`。

## 好处
1. 兜底清晰：即使没有明确策略或工具指令，也能形成可执行步骤，避免空规划。
2. 观测一致：工具调用链路会产生日志、事件与证据包，便于追踪执行路径。
3. 接口一致性：统一走工具执行入口，减少分支行为差异，便于测试与回归。
4. 可替换性：后续只需注册同名工具即可平滑启用，不改业务逻辑。

## 坏处
1. 强依赖工具链：默认走工具会直接触发 `MCP` 调用，若工具未注册或 `MCP` 不可用，会导致任务失败。
2. 误用风险：简单问题也会走工具，增加额外调用与延迟，且可能触发不必要的外部访问。
3. 成本放大：工具调用会带来额外网络与审计成本，且容易触发限流或熔断。
4. 失败体验：当 `demo_tool` 不存在时，用户看到的是工具错误而不是模型回答。

## 结论
默认使用 `demo_tool` 适合作为研发阶段的可观测性兜底，但在生产或验证大模型链路场景会带来较高失败率与误用成本。
建议在以下场景调整默认策略：
- 需要保证“无工具也能回答”时，优先使用 `chain_of_thought` 或启用 `planner` 的 LLM 规划。
- 需要使用工具时，明确指定工具名与 `mcpServerId`，避免默认工具名导致失败。

## 建议策略
1. 只在测试或演示环境保留 `demo_tool` 默认值。
2. 在生产环境中将默认策略改为非工具路线，或要求显式传入工具名称。
3. 若仍需工具兜底，确保 `demo_tool` 已在远端 `MCP` 工具集注册并可用。
