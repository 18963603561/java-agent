# 大模型输出 rawRef 覆盖分析与改造方案

## 1. 背景与目标
- 目标问题：当前工具输出已经有 `rawRef`，需要确认“大模型输出”是否同样具备 `rawRef`，如果没有，如何实现。
- 分析要求：基于代码全量检索，不做抽样结论。

## 2. 全量检索范围与关键词
- 扫描目录：`src/main/java`、`src/test/java`。
- 关键词：`rawRef`、`rawResult`、`ModelResponse`、`modelInvocationService.invoke(...)`、`StepOutput`、`resolveRawRef(...)`。
- 本文结论均来自代码事实，不依赖历史假设。

## 3. 当前现状结论

### 3.1 工具原生执行链路：包含 `rawRef`
- 工具执行器在返回结果时写入 `rawRef`：`src/main/java/com/example/agent/agentcore/ToolExecutor.java:230`、`src/main/java/com/example/agent/agentcore/ToolExecutor.java:270`。
- `StepOutput` 契约本身支持 `rawRef`：`src/main/java/com/example/agent/runtime/io/StepOutput.java:21`。
- `StepRuntimeService` 也会读取 `rawOutput.rawRef`：`src/main/java/com/example/agent/runtime/StepRuntimeService.java:337`、`src/main/java/com/example/agent/runtime/StepRuntimeService.java:368`。

### 3.2 LLM 步骤输出：默认不在顶层暴露 `rawRef`
- 直接回答结构由 `buildAnswerOutput(...)` 生成，不含 `rawRef` 字段：`src/main/java/com/example/agent/runtime/LlmStepService.java:687`。
- 工具调用型输出会放 `rawResult`，但未放顶层 `rawRef`：`src/main/java/com/example/agent/runtime/LlmStepService.java:844`、`src/main/java/com/example/agent/runtime/LlmStepService.java:873`。
- 因为 `StepRuntimeService` 只认顶层 `rawRef`，所以这类输出不会进入 `StepOutput.rawRef`：`src/main/java/com/example/agent/runtime/StepRuntimeService.java:368`。

### 3.3 模型原始输出（纯模型文本）当前没有 `rawRef`
- `ModelResponse` 仅有 `modelId/content/inputTokens/outputTokens`：`src/main/java/com/example/agent/model/ModelResponse.java:6`、`src/main/java/com/example/agent/model/ModelResponse.java:15`。
- `ModelInvocationService.invoke(...)` 只调用模型并返回 `ModelResponse`，未写 `RawResultStore`：`src/main/java/com/example/agent/model/ModelInvocationService.java:105`、`src/main/java/com/example/agent/model/ModelInvocationService.java:133`。
- 结论：模型输出文本目前没有统一 `rawRef`。

### 3.4 其他大模型步骤输出同样未携带 `rawRef`
- `COT`、`REACT`、`MULTI_AGENT`、`DEBATE`、`RESEARCH`、`FINAL_OUTPUT` 都依赖 `modelInvocationService.invoke(...)`，但最终输出对象/Map 中未看到 `rawRef` 字段。
- 关键入口：
- `src/main/java/com/example/agent/runtime/AgentRuntime.java:475`
- `src/main/java/com/example/agent/runtime/AgentRuntime.java:477`
- `src/main/java/com/example/agent/runtime/AgentRuntime.java:479`
- `src/main/java/com/example/agent/runtime/AgentRuntime.java:482`
- `src/main/java/com/example/agent/runtime/AgentRuntime.java:489`
- `src/main/java/com/example/agent/runtime/FinalOutputService.java:115`

## 4. 影响与风险
- 风险1：LLM 步骤即便内部调用了工具，`rawRef` 可能只在 `rawResult.rawRef`，不会进入标准 `StepOutput.rawRef`。
- 风险2：`structured.refs.rawRef` 依赖 `StepOutput.rawRef`，因此会缺失：`src/main/java/com/example/agent/runtime/StepRuntimeService.java:394`、`src/main/java/com/example/agent/runtime/StepRuntimeService.java:395`。
- 风险3：任务结果 `steps` 目前是摘要化结构，不直接携带原始引用，问题定位更依赖 `/timeline/steps`：`src/main/java/com/example/agent/runtime/AgentRuntime.java:1319`、`src/main/java/com/example/agent/orchestrator/TaskOrchestrator.java:564`。

## 5. 是否包含 rawRef 的最终判定
- 工具原生输出：包含（是）。
- LLM 直接回答输出：不包含（否）。
- LLM 工具调用输出：仅可能嵌套在 `rawResult.rawRef`，顶层不包含（部分）。
- COT/REACT/MULTI_AGENT/DEBATE/RESEARCH/FINAL：不包含（否）。

## 6. 改造方案（建议采用“完整方案”）

### 6.1 方案A（快速补丁，低改动）
- 目标：先让 LLM 工具调用路径能够产出顶层 `rawRef`。
- 做法：
- 在 `LlmStepService` 的工具输出构建逻辑中，把 `rawResult.rawRef` 提升到顶层 `rawRef`。
- 在 `StepRuntimeService.resolveRawRef(...)` 增加兼容读取：`rawOutput.rawResult.rawRef`、`rawOutput.result.rawRef`。
- 优点：改动小、见效快。
- 局限：纯模型文本输出依然没有 `rawRef`。

### 6.2 方案B（完整方案，推荐）
- 目标：所有模型输出都可追溯到 `rawRef`。
- 核心设计：在模型调用层统一生成 `rawRef`，业务层只做透传。

#### 设计要点
- 在 `ModelResponse` 增加 `rawRef`（建议类型 `RawRef`，也可先用 `String rawRefKey`）。
- 在 `ModelInvocationService` 注入 `RawResultStore`，每次 `llmClient.generate(...)` 后存储原始模型输出并写入 `response.rawRef`。
- 在各业务服务返回结果时统一透传：
- `LlmStepService` 顶层写 `rawRef`。
- `FinalOutputService` 返回中加 `rawRef`。
- `ChainOfThoughtService`、`ReactLoopService`、`MultiAgentCoordinator`、`DebateCoordinator`、`ResearchPipeline` 将 `rawRef` 透传到其结果对象或返回 Map。
- `StepRuntimeService.resolveRawRef(...)` 保留多路径兼容读取（顶层优先）。

#### 推荐字段策略
- 标准字段：`rawRef`（单值，优先级最高引用）。
- 扩展字段：`refs`（多引用场景可用），例如：
```json
{
  "rawRef": "raw:model:xxxx",
  "refs": {
    "decisionRawRef": "raw:model:decision:xxxx",
    "summaryRawRef": "raw:model:summary:xxxx",
    "toolRawRef": "raw:tool:xxxx"
  }
}
```

## 8. 与 Hook/EvidencePack 的关系说明
- 现有证据写入会从 Hook 载荷读取 `rawRef`：`src/main/java/com/example/agent/tools/hook/EvidencePackHookHandler.java:146`、`src/main/java/com/example/agent/tools/hook/EvidencePackHookHandler.java:152`。
- `AgentRuntime` 的工具执行分支会触发 `preTool/postTool`：`src/main/java/com/example/agent/runtime/AgentRuntime.java:688`、`src/main/java/com/example/agent/runtime/AgentRuntime.java:694`。
- 但 `LlmStepService` 内部工具调用直接走 `enforcementGateway.executeWithArguments(...)`：`src/main/java/com/example/agent/runtime/LlmStepService.java:345`，该路径不经过 `AgentRuntime` 的 `postTool`。
- 若希望“LLM 内部工具调用”也稳定写入证据包，建议后续补一版 Hook 对齐。

## 9. 验收检查清单
- 检查1：LLM 直接回答步骤完成后，`/api/v1/timeline/steps` 中该步骤 `output.rawRef.key` 非空。
- 检查2：LLM 工具调用步骤完成后，`output.rawRef.key` 非空，且 `structured.refs.rawRef` 同步存在。
- 检查3：`COT/REACT/MULTI_AGENT/DEBATE/RESEARCH/FINAL` 至少有一类模型步骤可输出 `rawRef`（建议全部覆盖）。
- 检查4：历史工具输出 `rawRef` 行为保持不变。
- 检查5：任务同步返回结构不破坏既有字段，仅新增可选字段。

## 10. 结论
- 当前代码中，“工具原生输出”有 `rawRef`，“大模型输出”整体没有统一 `rawRef`。
- 建议采用方案B：在 `ModelInvocationService` 统一生成 `rawRef`，业务层透传，`StepRuntimeService` 做兼容读取。
- 该方案最符合新项目“统一设计、可复用、低分支”的目标。
