# `tools` 包 P2 改造任务清单

## 1. 目标

基于 `doc/tools包设计合理性与坏味道分析-202602081143.md` 中 P2 项，形成可直接排期执行、可验收的持续优化任务清单。

P2 总目标：

1. 逐步引入强类型请求/响应对象，收敛核心链路中的 `Map<String, Object>`。
2. 将 `ToolExecutor` 拆分为可组合职责单元，降低单类复杂度与改动耦合。

---

## 2. 设计取舍

1. 采用“核心先强类型、边界后兼容”策略：
   - 对核心执行链路优先落地强类型。
   - 对外部协议边界（如 MCP/HTTP）保留最薄转换层，不向核心透传通用 Map。
2. 拆分优先以职责完整为准，不做机械按行数拆分。
3. 新增类型对象遵循“输入、输出、上下文”三类模型分层，避免再次形成巨型上下文对象。
4. 所有拆分均要求日志与错误语义不倒退。

---

## 3. P2 任务总览

| 任务编号 | 任务主题 | 优先级 | 预计工作量 | 前置依赖 |
|---|---|---|---|---|
| P2-1 | 核心链路强类型对象建模 | 高 | 1.5~2.5 人日 | 无 |

## 4. 具体任务清单

## 4.1 P2-1 核心链路强类型对象建模

### 4.1.1 目标

把执行主链路中“语义稳定且高频使用”的 Map 结构收敛为强类型对象，提升编译期约束与可维护性。

### 4.1.2 实施方案

1. 新增工具执行输入模型（建议）：
   - `ToolExecutionRequest`：聚合 `request/tenantContext/toolName/usageId/taskId`。
   - `ToolInvocationArguments`：承载工具参数，封装内部保留字段剥离规则。
2. 新增工具执行输出模型（建议）：
   - `ToolExecutionResult`：包含 `tool/result/cacheHit/tokenUsage/rawRef/resultDigest`。
   - `ToolInvocationPayload`：封装真正工具输出，减少对外直接暴露内部临时字段。
3. 新增转换器（边界适配）：
   - `ToolExecutionMapper`：负责 `Map <-> 强类型` 的单点转换。
4. 收敛常量键名：
   - 将高频字符串键转为常量类（如 `ToolFieldKeys`），并在转换器中集中使用。

### 4.1.3 涉及文件（建议）

1. `src/main/java/com/example/agent/capabilities/tools/execution/model/*`
2. `src/main/java/com/example/agent/capabilities/tools/execution/mapping/*`
3. `src/main/java/com/example/agent/capabilities/tools/execution/ToolExecutor.java`

### 4.1.4 验收标准

1. `ToolExecutor` 主流程参数不再直接以裸 `Map<String, Object>` 贯穿。
2. 关键字段（tool/result/tokenUsage/rawRef）由强类型对象承载并有中文注释。
3. 键名变更不再需要全链路检索替换，集中在 Mapper 与常量层维护。

---

## 4.2 P2-2 `ToolExecutor` 职责拆分与编排重构

### 4.2.1 目标

将 `ToolExecutor` 从“全能类”重构为“编排器 + 可复用职责组件”，降低单类复杂度与回归风险。

### 4.2.2 实施方案

1. 将缓存职责抽离为独立组件：
   - 建议 `ToolExecutionCacheService`（缓存键、TTL、读写命中日志）。
2. 将远程调用职责抽离为独立组件：
   - 建议 `ToolInvocationService`（沙箱执行、MCP 调用、重试边界）。
3. 将计量与追踪职责抽离：
   - 建议 `ToolUsageRecorder`（token 记录）
   - 建议 `ToolExecutionTracer`（指标、链路日志、异常上下文）。
4. 将结果封装与落盘抽离：
   - 建议 `ToolResultAssembler`（`ToolExecutionResult` 组装）
   - 建议 `ToolRawRefService`（rawRef 存储与容错）。
5. `ToolExecutor` 保留最小编排职责：
   - 入参校验
   - 执行阶段串联
   - 统一异常语义透传

### 4.2.3 涉及文件（建议）

1. `src/main/java/com/example/agent/capabilities/tools/execution/ToolExecutor.java`
2. `src/main/java/com/example/agent/capabilities/tools/execution/service/*`
3. `src/main/java/com/example/agent/capabilities/tools/execution/model/*`

### 4.2.4 验收标准

1. `ToolExecutor` 代码行数与圈复杂度显著下降（建议：主流程方法不超过 120 行）。
2. 缓存、调用、计量、追踪、组装职责有独立可测试组件。
3. 异常码、日志关键节点、行为语义与改造前一致或更清晰。

---

## 4.3 P2-3 兼容层收口与 Map 使用面收缩

### 4.3.1 目标

将通用 Map 限制在协议边界和扩展插件边界，避免核心域继续扩散弱类型结构。

### 4.3.2 实施方案

1. 明确“允许使用 Map 的边界”：
   - MCP 协议适配层输入输出
   - 插件/外部系统非受控结构
2. 核心域内部禁用裸 Map 直传：
   - 通过 `ToolExecutionMapper` 入域转换，出域再转换。
3. 清理重复转换逻辑：
   - 去掉散落在 `ToolExecutor` 与调用链中的临时 Map 组装代码。
4. 对遗留 Map 路径增加 TODO 清单并标注收口计划（若本轮无法完全移除）。

### 4.3.3 涉及文件（建议）

1. `src/main/java/com/example/agent/capabilities/tools/mcp/*`
2. `src/main/java/com/example/agent/capabilities/tools/plugin/*`
3. `src/main/java/com/example/agent/capabilities/tools/execution/*`

### 4.3.4 验收标准

1. 核心执行域（execution/enforcement）新增逻辑不再新增裸 Map 协议键。
2. Map 转换入口可定位、可审计，转换逻辑集中化。
3. 新增或修改字段时，仅需改“模型 + Mapper + 边界适配”。

---

## 4.4 P2-4 测试与基线更新

### 4.4.1 目标

确保 P2 重构后行为稳定、可回归，并建立后续迭代的复杂度与性能基线。

### 4.4.2 子任务

1. 单元测试补齐：
   - 新增组件级测试：缓存服务、调用服务、计量记录、结果组装。
   - 增加 Mapper 双向转换测试与异常场景测试。
2. 集成回归：
   - 覆盖缓存命中、重试成功、重试失败、rawRef 失败兜底场景。
3. 可观测性回归：
   - 验证关键日志节点、指标名称、错误码不回退。
4. 文档更新：
   - 输出新的执行链路时序图与包职责图（写入 `doc/`）。

### 4.4.3 验收标准

1. `mvn -q -DskipTests compile` 通过。
2. `mvn -q test` 全量通过。
3. 重构前关键行为断言全部保留或升级，无静默语义漂移。

---

## 5. 建议实施顺序

1. 先做 `P2-1`：先立类型边界，避免拆分过程中继续引入 Map 扩散。
2. 再做 `P2-2`：基于强类型对象拆分 `ToolExecutor`。
3. 然后做 `P2-3`：统一收口边界 Map，清理残余转换散点。
4. 最后做 `P2-4`：补齐测试、压实回归、沉淀文档。

---

## 6. 风险与控制

1. 风险：拆分类别过细导致调用链复杂。
   - 控制：保持“编排器 + 4~6 个核心职责服务”粒度，不做过度微拆分。
2. 风险：强类型替换导致外部协议兼容问题。
   - 控制：边界层保留 Map，域内强类型，采用 Mapper 适配。
3. 风险：重构后日志与指标遗漏。
   - 控制：为关键日志/指标建立回归断言，并在代码评审中设检查项。

---

## 7. 完成定义

满足以下条件可判定 P2 完成：

1. 核心执行域形成稳定强类型模型，不再以裸 Map 贯穿主流程。
2. `ToolExecutor` 拆分完成，主类仅保留编排职责。
3. Map 使用面被限定在协议边界与外部扩展边界。
4. 全量测试通过，且文档能清晰说明新链路与职责边界。
