# `runtime` 第三阶段整改任务清单（类/方法级可执行版）

## 一、范围与目标

- 来源依据：`doc/runtime包设计合理性与坏味道评估-202602071330.md` 第 `6.3` 节（长期整改建议）。
- 建议周期：`4~8` 周。
- 阶段目标：
  - 收敛动态边界：对高频字段引入类型化对象，逐步减少核心链路裸 `Map`。
  - 扩展原始存储抽象：统一“写入 + 读取/解析能力”，消除 `resolve` 服务对具体实现类耦合。
  - 新项目治理原则：不保留无价值历史兼容分支，优先沉淀可复用、可扩展、可测试的稳定抽象。
- 非目标：
  - 不在本阶段重做业务编排语义（`engine` 执行时序保持不变）。
  - 不改动 `api` 对外协议字段名称（仅做内部对象与服务重构）。

---

## 二、交付清单总览（优先级）

### P0-1：任务 I（动态边界类型化）

- 核心方向：`StepSpec`、`RuntimeContext`、`StepExecutionRequest`、`StepExecutionOutput` 的高频字段类型化。

### P0-2：任务 J（Raw 存储抽象升级）

- 核心方向：将 `RawResultStore` 升级为可扩展读写接口 + 注册路由，`RawResultResolveService` 仅依赖抽象。

### P1-1：任务 K（核心链路切换与清理）

- 核心方向：执行链路切到类型化访问，删除临时兼容与魔法键分支，补齐架构防回退测试。

---

## 三、逐项任务（类/方法级）

## 任务 I：收敛动态边界（类型化对象）

### I.1 新增类型化输入模型

1. 新增 `src/main/java/com/example/agent/runtime/model/input/StepInputView.java`
   - 新增方法：
     - `StepInputView#from(StepSpec step, RuntimeContext runtimeContext)`
     - `StepInputView#toExecutionMap()`
     - `StepInputView#requiresApproval()`
     - `StepInputView#approvalSource()`
     - `StepInputView#dependsOn()`

2. 新增 `src/main/java/com/example/agent/runtime/model/input/ApprovalInput.java`
   - 字段：`requiresApproval`、`approvalSource`。
   - 新增方法：`ApprovalInput#isRequired()`。

3. 新增 `src/main/java/com/example/agent/runtime/model/input/LastStepInput.java`
   - 字段：`stepId`、`stepType`、`summary`、`rawRef`、`rawRefs`、`rawTruncated`。
   - 说明：承载运行时高频“上一步”信息，替代散落字符串键读取。

### I.2 改造 `StepSpec`

1. 修改 `src/main/java/com/example/agent/runtime/model/StepSpec.java`
   - 保留 `toExecutionInput()` 作为边界适配方法。
   - 新增方法：`StepSpec#toInputView(RuntimeContext runtimeContext)`。
   - 新增方法：`StepSpec#approvalInput()`，统一审批字段读取入口。

2. 调整调用方，不再直接拼装审批键：
   - `src/main/java/com/example/agent/runtime/engine/RuntimeContextUpdateService.java#mergeStepInput(...)`
   - `src/main/java/com/example/agent/runtime/react/ReactLoopService.java`（构建审批输入路径）

### I.3 改造 `RuntimeContext`

1. 修改 `src/main/java/com/example/agent/runtime/step/RuntimeContext.java`
   - 新增方法：
     - `RuntimeContext#getLastStepInput()`
     - `RuntimeContext#setLastStepInput(LastStepInput snapshot)`
     - `RuntimeContext#getApprovalInput()`
     - `RuntimeContext#setApprovalInput(ApprovalInput approvalInput)`
   - `asMap()` 仅保留为边界能力，核心链路禁止新增直接键访问。

2. 替换以下方法中的魔法键读写：
   - `src/main/java/com/example/agent/runtime/engine/RuntimeContextUpdateService.java#updateRuntimeContext(...)`
   - `src/main/java/com/example/agent/runtime/engine/RuntimeContextUpdateService.java#appendExecutedSteps(...)`

### I.4 改造执行请求与输出高频读取

1. 修改 `src/main/java/com/example/agent/runtime/step/contract/StepExecutionRequest.java`
   - 新增字段：`StepInputView stepInputView`。
   - 新增方法：`StepExecutionRequest#getStepInputView()`。
   - `getStepInput()` 保留为适配读取，内部来源统一由 `stepInputView.toExecutionMap()` 提供。

2. 修改 `src/main/java/com/example/agent/runtime/step/contract/StepExecutionOutput.java`
   - 新增高频读取方法：
     - `StepExecutionOutput#getAnswerText()`
     - `StepExecutionOutput#getMode()`
     - `StepExecutionOutput#getToolStatus()`
     - `StepExecutionOutput#getDecisionRawRef()`
     - `StepExecutionOutput#getSummaryRawRef()`
   - 约束：新增方法从 `payload` 解析并缓存，避免调用方重复解析键名。

### I.5 本任务验收标准

- `runtime` 核心链路（`engine/step/react`）新增代码不直接新增裸字符串键访问。
- `StepSpec`、`RuntimeContext`、`StepExecutionRequest`、`StepExecutionOutput` 均具备明确的类型化访问入口。
- 对外行为保持一致（接口协议、事件类型、错误码不变）。

## 任务 J：扩展原始存储抽象（写入 + 读取/解析）

### J.1 升级存储接口与注册路由

1. 修改 `src/main/java/com/example/agent/runtime/raw/store/RawResultStore.java`
   - 在保留 `store(...)` 基础上新增能力：
     - `RawStoreType storeType()`
     - `boolean supports(RawStoreType storeType)`（默认基于 `storeType()`）
     - `String loadByRefId(String refId)`
     - `String loadByStoreId(String storeId)`

2. 新增 `src/main/java/com/example/agent/runtime/raw/store/RawResultStoreRegistry.java`
   - 新增方法：
     - `RawResultStoreRegistry#findRequired(RawStoreType storeType)`
     - `RawResultStoreRegistry#loadByRefId(String refId)`
   - 说明：统一 store 路由，不允许 `resolve` 服务感知具体实现类。

### J.2 各存储实现统一实现读取能力

1. 修改 `src/main/java/com/example/agent/runtime/raw/store/InMemoryRawResultStore.java`
   - 实现 `storeType()/loadByRefId()/loadByStoreId()`。
   - 原 `load(String key)` 仅保留内部委托，不再作为跨类依赖入口。

2. 修改 `src/main/java/com/example/agent/runtime/raw/store/RedisRawResultStore.java`
   - 实现 `storeType()/loadByRefId()/loadByStoreId()`。

3. 修改 `src/main/java/com/example/agent/runtime/raw/store/SizeAwareRawResultStore.java`
   - 实现 `storeType()/loadByRefId()/loadByStoreId()`。
   - 约束：对 `file/txt` 分支读取统一走 `FileRawStorageSupport`。

4. 新增 `src/main/java/com/example/agent/runtime/raw/store/FileRawResultStore.java`
   - 说明：用于统一承接 `file/txt` 引用读取语义。
   - 新增方法：
     - `FileRawResultStore#storeType()`（返回 `RawStoreType.FILE`）
     - `FileRawResultStore#loadByRefId(String refId)`
     - `FileRawResultStore#loadByStoreId(String storeId)`

### J.3 改造统一提取服务

1. 修改 `src/main/java/com/example/agent/runtime/raw/RawResultResolveService.java`
   - 构造依赖替换为：`RawRefCodec` + `RawResultStoreRegistry` + `RawStoreProperties`。
   - 删除对具体实现类的 `ObjectProvider` 依赖：
     - `InMemoryRawResultStore`
     - `RedisRawResultStore`
     - `SizeAwareRawResultStore`
   - 删除历史兼容分支方法：`resolveLegacyRawKey(...)`。
   - `resolveByParsed(...)` 改为从注册表路由读取。

2. 修改 `src/main/java/com/example/agent/runtime/raw/store/RawResultStoreFallbackConfiguration.java`
   - 确保 fallback 仍满足“读写一体接口”注册要求。

### J.4 控制器侧统一下载入口（按引用而非文件名）

1. 修改 `src/main/java/com/example/agent/api/http/controller/RawResultController.java`
   - 新增接口：`GET /api/v1/raw/download?ref=`。
   - 下载逻辑统一走 `RawResultResolveService#resolve(ref)`，避免控制器识别存储类型。

2. 现有 `GET /api/v1/raw/files/{filename}` 保留为过渡入口（短期），后续阶段删除。

### J.5 本任务验收标准

- `RawResultResolveService` 不再直接导入具体 store 实现类。
- 新增任一 store 实现时，无需修改 `resolve` 服务核心逻辑。
- `resolve/download` 在 `mem/redis/file/txt` 四类存储上行为一致。

## 四、实施顺序与里程碑建议

- 第 1~2 周：任务 I（先模型后调用点，完成类型化入口）。
- 第 3~4 周：任务 J（先接口与注册表，再解析服务与控制器）。
- 第 5~6 周：任务 K（切换、清理、架构防回退）。
- 第 7~8 周：压力回归、文档收口、发布验证（按实际进度可裁剪）。

建议顺序：`I -> J -> K`。

## 六、风险与回滚策略

- 风险 1：类型化迁移导致字段遗漏，运行期出现空值分支。
  - 缓解：先建立类型对象与适配层，再逐类替换调用，最后删除兼容。
- 风险 2：Raw 抽象升级后，某存储模式读取行为不一致。
  - 缓解：在 `RawResultStoreEndToEndFlowTest` 做跨存储参数化回归。
- 风险 3：一次性删除兼容路径影响联调稳定性。
  - 缓解：按任务拆批发布，每任务独立可回滚。

回滚策略：

- 按任务维度回滚：`I`、`J`、`K` 独立提交与回退。
- 若 `I` 回滚：保留 `StepInputView` 类但恢复调用方旧入口。
- 若 `J` 回滚：恢复 `RawResultResolveService` 旧依赖注入方式。
- 若 `K` 回滚：仅回滚清理提交，不回滚已验证的新抽象。

## 七、完成定义（Definition of Done）

- 架构层：`resolve` 完成抽象化路由，不依赖具体 store 实现。
- 代码层：核心链路高频字段完成类型化访问，魔法键显著收敛。
- 测试层：分阶段定向测试与每阶段 `mvn test` 全流程回归通过。
- 文档层：阶段验收记录落盘到 `doc/notes/`，并更新阶段状态。
