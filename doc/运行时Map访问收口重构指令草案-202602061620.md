# 运行时 `Map`/`JSON` 键访问收口重构指令草案（新项目，无历史包袱）

## 0. 背景与目标

本草案基于 `docs/runtime-map-access-audit.md` 的静态扫描结果整理。

目标（面向对象、边界清晰、可读可复用）：

1. 将核心链路中对 `Map<String, Object>` 与 `JsonNode` 的硬编码键访问收口到极少数“权威点”。
2. 明确“输出契约”：对外（跨包/跨模块）只暴露数据传输对象（`DTO`）/值对象，禁止消费方直接 `map.get("rawRef")` 之类的访问。
3. 统一同语义字段命名与优先级（例如 `tool` 与 `toolName`，`raw` 与 `rawResult` 与 `result`），避免每个类各自解释一遍。

## 1. 核心结论（新项目视角的最优架构取向）

### 1.1 这不是单点缺陷，是“边界不清 + 解析逻辑外溢”

对照审计报告可以看到以下典型现象：

1. 同一语义字段在多个类被重复解析（例如 `rawRef` 至少在 `AgentRuntime`、`ReactLoopService`、`LlmStepService`、`RawOutputEnvelopeBuilder`、`StepExecutionOutput` 中出现解析片段）。
2. 同一语义字段存在多套键（例如 `tool` 与 `toolName` 同时存在；输出载体 `raw` / `rawResult` / `result` / `data` 并存）。
3. 跨模块（`capabilities`、`reflection`）出现对运行时上下文/输出结构的直接 `Map` 读取：
   - 例如 `src/main/java/com/example/agent/capabilities/llm/DefaultModelProvider.java` 中存在 `context.get("tool")` 的访问点（详见审计报告 A2 与附录）。
   - `src/main/java/com/example/agent/reflection/ReflectionService.java` 中读取 `outputSummary`、`outputDigest` 并对 `outputSummary.get("summary")` 做兜底拼装。

结论：如果下一步重构会影响其它模块，通常不是“被迫兼容”，而是这些模块同样存在边界设计缺陷：它们在消费运行时内部表示（`Map`）而不是消费稳定契约（数据传输对象，`DTO`）。

### 1.2 最优方案：建立“输出契约层”，把 `Map` 限制在边界内

建议形成两条硬边界：

1. **执行器边界**  
   执行器对外只返回 `StepExecutionOutput`（数据传输对象，`DTO`），内部可以保留 `payload` 的原始 `Map`，但消费方不得解析键。

2. **输出封装边界**  
   `rawRef/refs/truncated/data` 的提取与裁剪只允许在 `RawOutputEnvelopeBuilder`（或在 `StepExecutionOutput` 内部委托 `RawOutputEnvelopeBuilder`）中完成，禁止在其它类复制 `resolveRawRef`。

对应地，需要将“权威点”明确为：

- `src/main/java/com/example/agent/runtime/step/StepExecutionOutput.java`
- `src/main/java/com/example/agent/runtime/raw/RawOutputEnvelopeBuilder.java`
- `src/main/java/com/example/agent/runtime/summary/StepOutputSummaryBuilder.java`

并新增一个纯常量层（只给权威点使用）：

- `com.example.agent.runtime.output.OutputKeys`（建议新增）

## 2. 下一步重构指令草案（建议按 `P0`~`P3` 推进）

说明：本草案是“指令级别”的重构路线图，不在本轮执行范围。

### `P0`（必做，先立规矩）：确立契约与白名单

目标：先把“唯一正确的键定义、优先级、路径”固化下来，避免边拆边漂移。

1. 新增 `OutputKeys` 常量类（仅供权威点使用）
   - 新增文件：`src/main/java/com/example/agent/runtime/output/OutputKeys.java`
   - 常量建议至少包含：
     - `RAW_REF`、`REFS`、`TOOL_NAME`、`TOOL`（仅用于输入兼容）、`RAW_RESULT`、`RAW`、`RESULT`、`DATA`
     - `OUTPUT_SUMMARY`、`STEP_SUMMARY`、`OUTPUT_DIGEST`、`TRUNCATED`、`SUMMARY`
     - `DECISION_RAW_REF`、`SUMMARY_RAW_REF`、`TOOL_RAW_REF`、`MODEL_RAW_REF`
2. 把键使用点“收口白名单”写成工程约束
   - 白名单：`RawOutputEnvelopeBuilder`、`StepExecutionOutput`、`StepOutputSummaryBuilder`、`OutputKeys`（以及极少数输入适配器）
3. 增加契约测试（优先级固定住）
   - 新增测试：`RawOutputEnvelopeBuilder` 的 `rawRef` 优先级与路径
     - 顶层 `rawRef` 优先
     - `rawResult.rawRef` 次之
     - `result.rawRef` 次之
     - `raw.rawRef` 兜底
   - 新增测试：工具名称解析优先级（建议把 `tool` 视为输入兼容字段，内部统一成 `toolName`）

预期收益：

- 下一步任何大规模替换，都以契约测试兜底，避免“修一处、坏三处”。

### `P1`（先消重）：删除重复解析函数，让消费方只能走权威点

目标：清掉同义重复实现，把解析逻辑集中到 1 处。

1. 收口 `rawRef/refs` 提取
   - 迁移/删除以下重复实现（以调用 `RawOutputEnvelopeBuilder` 或 `StepExecutionOutput` 为准）：
     - `src/main/java/com/example/agent/runtime/engine/AgentRuntime.java` 中的 `resolveRawRef(...)`
     - `src/main/java/com/example/agent/runtime/react/ReactLoopService.java` 中的 `resolveRawRef(...)`
      - `src/main/java/com/example/agent/runtime/llm/LlmStepService.java` 中的 `resolveRawRefFromToolResult(...)`、以及 `refs` 合并逻辑
2. 收口摘要生成
    - 禁止 `AgentRuntime` 自己 `buildStepOutputSummary(...)` 再塞回 `Map`
   - 统一调用 `StepOutputSummaryBuilder`
3. 把“输入适配”与“输出契约”拆开
   - 输入（例如模型输出、工具输出）允许是 `Map`
    - 一旦进入运行时核心链路，必须转为数据传输对象（`DTO`）（`StepExecutionOutput`、`RawOutputEnvelope`、`StepOutputSummary` 等）

影响面（需要联动的消费方）：

- `runtime`：`AgentRuntime`、`ReactLoopService`、`LlmStepService`
- `reflection`：`ReflectionService`（如果直接读 `outputSummary/outputDigest`，应改为消费 `DTO` 或统一视图模型）

### `P2`（结构优化）：跨模块依赖反转，消除“`capabilities` 读取 `runtime` 的 `Map`”

目标：把 `capabilities`、`reflection` 对运行时输出的依赖，从“读取 `Map` 键”改为“读取 `DTO`”。

1. 明确共享契约的归属
    - 方案 A（同模块同工程）：把 `DTO` 放到 `com.example.agent.runtime.api`（或 `runtime.model`）并声明为稳定契约
    - 方案 B（多模块）：拆出 `runtime-contract` 子模块，`capabilities/reflection/runtime` 共同依赖
2. 改造 `capabilities` 中对运行时上下文的读取方式
   - 将 `context.get("tool")` 这类访问迁移为读取 `ToolCallContext`（值对象）或 `RuntimeContextView`（只读投影）
3. 改造 `reflection` 的摘要读取方式
   - `ReflectionService` 不应该自己拼接 `outputSummary.get("summary")` 的兜底逻辑
   - 应改为读取 `StepOutputSummary`（或其只读视图），再在反思输出层做渲染

判断标准：

- `capabilities` 与 `reflection` 内部不再出现对 `rawRef/refs/toolName/outputSummary/outputDigest` 等关键键的 `.get("...")` 访问。

### `P3`（治理落地）：自动化静态检查，阻止回潮

目标：工程层面禁止新增散乱键访问。

1. 新增审计脚本（示例）
   - 新增：`scripts/runtime-map-key-audit.ps1`
   - 规则：除白名单文件外，出现 `.get("rawRef")` / `.get("toolName")` 等关键访问即失败
2. 接入持续集成
   - 合并请求必跑

## 3. 建议的“先动哪一刀”（最小但最值钱的切入点）

优先顺序建议：

1. 先把 `tool` 与 `toolName` 统一（输入兼容只保留一处适配）
   - 原因：同语义多键是最高风险，且会影响审批、时间线、工具执行等多个链路
2. 再把 `rawRef` 的提取路径统一（删除重复 `resolveRawRef`）
   - 原因：当前重复实现很容易出现微差异（`trim`、空白判断、路径覆盖），导致线上偶发不一致
3. 最后推进摘要的统一生成（统一走 `StepOutputSummaryBuilder`）

## 4. 是否意味着其它模块“有设计缺陷”

在“新项目、追求可读可复用”的前提下：

- 只要某模块需要通过 `Map` 键去理解另一模块的内部输出结构（而不是通过 `DTO`/契约），就属于边界设计缺陷。
- 缺陷不一定立刻造成错误，但会显著增加未来迭代成本与不一致风险（同字段多处解释、同名键不同含义、兜底规则漂移）。

建议将这些缺陷视为“架构债”，并按 `P2` 的方式做依赖反转与契约层抽取。
