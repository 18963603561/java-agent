## 2. 分级口径定义

### 2.1 业务优先级（缺口等级）

- `P0`：阻断主流程闭环或核心契约。
- `P1`：高优先级能力缺失，影响治理或安全主线。
- `P2`：中优先级能力缺口，影响稳定性与可观测性完备度。

### 2.2 变更等级（实施复杂度）

- `L1`：单文件/小范围逻辑调整。
- `L2`：同一子域内多文件改造。
- `L3`：跨 2~3 个包改造，含测试联动。
- `L4`：跨域架构改造，含配置与扩展点设计。

### 2.3 包设计合理性等级

- `A`：分层稳定、职责边界清晰、扩展点完备。
- `B`：分层基本清晰，存在少量职责耦合或扩展点不足。
- `C`：边界混杂、扩展成本高、跨层依赖风险明显。

## 3. 当前总体判断（基于功能复核）

- 当前总体包设计合理性等级：`B`
- 当前风险等级：`P1（中高风险）`
- 主要原因：
  - `P0` 缺口：`LLM_OUTPUT` 终态事件发布缺失。
  - `P1` 缺口：`OPA` 引擎未接入，策略域扩展点不足。
  - `P2` 缺口：背压事件矩阵未落地（`BACKPRESSURE_APPLIED` 未发布）。

## 4. 必改项（Confirmed Missing）文件影响分析

## 4.1 P0：补齐 `LLM_OUTPUT` 终态事件

### 4.1.1 设计建议

- 原则：不在 `ModelInvocationService` 回流 `LLM_OUTPUT` 逻辑（受架构守卫约束）。
- 推荐落点：在运行时收口阶段发布 `LLM_OUTPUT`，保持“最终答案事件”语义清晰。
- 建议通过现有 `RuntimeControlEventPublisher` 接口发布，避免新建跨层依赖。

  - `src/main/java/com/example/agent/runtime/output/FinalOutputService.java`
- 业务代码（可选新增，若需解耦）：

## 4.3 P2：落地背压事件矩阵（`BACKPRESSURE_APPLIED`）

### 4.3.1 设计建议

- 优先在“有租户与工作流上下文”的位置发布事件，避免在底层治理组件硬注入业务上下文。
- 推荐在工具执行编排边界发布：
  - `RATE_LIMITED`/`CIRCUIT_OPEN` -> `BACKPRESSURE_APPLIED`
  - 熔断已打开 -> `CIRCUIT_OPENED`
- 先补事件发布，再补更细粒度背压 payload。

### 4.3.2 预计变更文件

- 业务代码（修改）：
  - `src/main/java/com/example/agent/capabilities/tools/enforcement/EnforcementGateway.java`
  - `src/main/java/com/example/agent/capabilities/tools/execution/ToolExecutor.java`
  - `src/main/java/com/example/agent/runtime/recovery/FailureClassifier.java`（若需统一错误归类）
- 业务代码（可选修改）：
  - `src/main/java/com/example/agent/governance/ratelimit/RateLimitService.java`
  - `src/main/java/com/example/agent/governance/circuitbreaker/CircuitBreakerManager.java`

## 7. 实施顺序建议

### 第一批（必须先做）

1. `P0`：补 `LLM_OUTPUT` 终态事件。
2. `P1`：完成 `PolicyEngine` SPI 化并接入 OPA provider。

### 第二批（随后收口）

3. `P2`：补齐背压事件矩阵（`BACKPRESSURE_APPLIED`、`CIRCUIT_OPENED`）。

### 第三批（质量加固）

4. 针对 Requires Runtime Only 项补回归用例与 smoke 脚本（以测试/脚本为主，少改业务）。

## 8. 风险与边界提醒

- `LLM_OUTPUT` 改造需避免触碰 `ModelInvocationService` 的守卫红线（见 `LlmArchitectureGuardTest`）。
- `OPA` 接入建议采用 SPI，不建议在 `PolicyEngine` 中硬编码远端调用细节。
- 治理事件建议在有 `tenantId/workflowId` 的边界发布，避免治理底层被业务上下文污染。

## 9. 结论

- 该实现改造属于“可分批推进、可控风险”的架构收口工作。
- 从包设计合理性看，当前处于 `B`，完成三项必改后可进入 `A-`。
- 建议以“P0+P1 先行、P2 收口、验证增强最后补齐”的节奏推进，避免跨域改造一次性过大。
