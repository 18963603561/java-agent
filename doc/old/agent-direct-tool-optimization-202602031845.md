# 规划阶段提供完整工具参数与“直达工具”优化路径分析

## 1. 结论
- 规划阶段“可以”提供完整工具参数，但前提较多：需要工具 schema、明确工具名、参数来源可靠。
- 在满足条件时，可新增“直达工具”路径，减少一次模型决策调用；否则风险较高，应保留原有决策路径。

## 2. 当前规划链路能否产出完整参数
可行点：
- `PlannerService.parsePlan` 会把模型返回的 `steps[*].input` 原样写入 `StepRequest.input`，可承载 `arguments` 或平铺参数。
- `PlannerService.buildHeuristicPlan` 可从 `context` 中读取 `tool` 并写入 `toolInput`，理论上也可扩展写入参数。

限制点：
- 规划阶段未强制注入工具 schema，`toolInjectMode=summary` 时模型看不到完整参数定义，难以生成可靠参数。
- 规划 prompt 中对“工具参数字段”要求较弱，模型输出可能缺参或类型不匹配。
- 规划阶段通常只知道 `query`，缺少业务必填字段时参数完整性无法保证。

## 3. 让规划阶段产出完整参数的必要条件
- 已明确工具名（`tool` 或 `toolName`）且不可被模型改写。
- 规划阶段能获取工具 schema（建议在规划模型请求里注入完整 schema）。
- 业务上下文能提供关键参数（如租户、时间范围、ID 列表）。
- 规划输出对参数字段有严格约束与校验（缺参即判失败）。

## 4. “直达工具”路径的触发条件（建议）
满足全部条件才进入直达路径：
1) `stepType=TOOL`。
2) 已解析出 `toolName`。
3) 参数存在且校验通过：
   - `input.arguments` 存在，或平铺参数经白名单过滤后完整可用。
4) 明确不需要模型进行“是否调用工具”的判断。

否则继续走 `llmStepService.run` 进行决策与参数生成。

## 5. 直达工具路径的收益与风险
收益：
- 少一次模型调用，降低延迟与成本。
- 行为更确定，执行路径更可控。

风险：
- 参数完整性不足导致工具失败。
- 缺少模型补救（参数修复与推断）。
- 需要补齐总结能力（保持输出结构一致）。

## 6. 落地建议（不改业务语义）
- 规划阶段强化参数生成：
  - 在规划请求中注入完整工具 schema。
  - 约束输出：`stepType=TOOL` 时必须包含 `toolName + arguments`。
- 执行阶段新增“直达工具”分支：
  - 参数校验通过则直接 `executeToolStep`。
  - 失败回退到 `llmStepService.run`，保持可用性。
- 输出结构统一：
  - 直达路径需补齐 `mode/tool/toolStatus` 与摘要字段，保证后续链路兼容。

## 7. 建议的演进顺序
1) 先增强规划输出质量（schema 注入 + 参数校验）。
2) 再引入直达路径（带回退）。
3) 最后评估是否减少决策模型调用配额。
