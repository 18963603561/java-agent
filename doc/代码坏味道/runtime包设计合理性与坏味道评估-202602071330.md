# `runtime` 包设计合理性与坏味道评估

## 一、评估目标与范围

- 评估目标：分析 `src/main/java/com/example/agent/runtime` 下包结构的合理性、可维护性、可扩展性与代码坏味道风险。
- 评估范围：`runtime` 目录下全部 Java 代码，共 `95` 个文件。
- 评估方法：
  - 静态结构扫描（包职责、依赖方向、双向依赖）
  - 关键类复杂度抽样（类体量、职责聚合、分支复杂度）
  - 关键链路一致性检查（执行控制、原始数据存储与提取、步骤记录）
  - 结合当前单元测试分布进行可测试性判断

---

## 二、总体结论与等级

### 2.1 总体等级

- 总体等级：`三级（可用但需治理）`
- 结论摘要：
  - 优点明显：分域拆包已经形成，运行时主流程阶段划分清晰，观测埋点较完整。
  - 风险集中：核心类过大、双向依赖较多、动态 `Map` 边界过宽、部分实现语义不一致。
  - 当前状态适合持续迭代，但不适合继续在现状上无约束叠加复杂功能。

### 2.2 分维度等级

- 职责划分：`二级（良好）`
- 依赖稳定性：`三级（一般）`
- 可维护性：`四级（偏弱）`
- 可扩展性：`三级（一般）`
- 可测试性：`二级（良好）`
- 可观测性：`二级（良好）`

---

## 三、包结构合理性分析

### 3.1 当前结构优点

- 运行时阶段拆分较清晰：`prepare`、`step`、`recovery`、`finalize`、`output`、`raw`、`structured`、`control` 等子域边界可识别。
- 关键对象已显式化：`StepExecutionRequest`、`StepExecutionOutput`、`RuntimeContext` 等对象减少了裸参数透传。
- 原始数据链路有统一协议方向：`rawref` 编解码与 `resolve` 统一提取接口已经形成。
- 观测基础较完整：步骤开始、完成、失败、审批与暂停恢复都有日志和事件。

### 3.2 结构薄弱点

- 编排层过于集中：`AgentRuntime` 承担了流程控制、事件发布、上下文回填、反思调度、恢复策略协同等多重职责。
- 模块内存在多处双向依赖，削弱了分层稳定性。
- `runtime` 对外部能力层耦合较重，领域内聚度仍可提升。

## 四、关键坏味道清单（按风险分级）

### 4.1 一级（高风险）

- 超大类与职责聚合过高
  - `src/main/java/com/example/agent/runtime/llm/LlmStepService.java`
  - `src/main/java/com/example/agent/runtime/summary/StepOutputSummaryBuilder.java`
  - `src/main/java/com/example/agent/runtime/engine/AgentRuntime.java`
  - `src/main/java/com/example/agent/runtime/react/ReactLoopService.java`
  - 问题：单类承担过多策略与流程分支，理解成本与回归风险显著升高。

- 执行控制逻辑重复实现
  - 已有门禁：`src/main/java/com/example/agent/runtime/control/RuntimeExecutionGate.java:41`
  - 已有门禁：`src/main/java/com/example/agent/runtime/control/RuntimeApprovalGate.java:47`
  - 重复实现：`src/main/java/com/example/agent/runtime/react/ReactLoopService.java:666`
  - 重复实现：`src/main/java/com/example/agent/runtime/react/ReactLoopService.java:693`
  - 问题：同一控制语义在多处实现，后续规则变更容易出现行为漂移。

### 4.2 二级（中高风险）

- 双向依赖较多，层级稳定性不足
  - `engine` 与 `finalize` 双向耦合
    - `src/main/java/com/example/agent/runtime/engine/AgentRuntime.java:12`
    - `src/main/java/com/example/agent/runtime/finalize/RuntimeFinalizationService.java:6`
  - `step` 与 `step.executor` 双向耦合
    - `src/main/java/com/example/agent/runtime/step/StepExecutionDelegate.java:5`
    - `src/main/java/com/example/agent/runtime/step/executor/StepExecutorRouter.java:3`
  - `raw` 与 `raw.store` 双向耦合
    - `src/main/java/com/example/agent/runtime/raw/RawResultResolveService.java:7`
    - `src/main/java/com/example/agent/runtime/raw/store/SizeAwareRawResultStore.java:3`
  - `structured` 与 `structured.result` 双向耦合
    - `src/main/java/com/example/agent/runtime/structured/StructuredExtractorRegistry.java:7`
    - `src/main/java/com/example/agent/runtime/structured/result/StructuredResult.java:3`
  - 问题：后续拆分与替换难度变大，影响长期演进。

- 动态 `Map` 作为主边界，类型约束偏弱
  - `src/main/java/com/example/agent/runtime/model/StepSpec.java:25`
  - `src/main/java/com/example/agent/runtime/step/RuntimeContext.java:31`
  - `src/main/java/com/example/agent/runtime/step/StepExecutionOutput.java:23`
  - 问题：字段拼写、类型转换、兼容分支风险上升，问题常在运行期暴露。

- 原始数据提取对具体实现类耦合
  - 接口能力过窄：`src/main/java/com/example/agent/runtime/raw/store/RawResultStore.java:18`
  - 解析服务直接依赖具体实现：
    - `src/main/java/com/example/agent/runtime/raw/RawResultResolveService.java:30`
    - `src/main/java/com/example/agent/runtime/raw/RawResultResolveService.java:31`
    - `src/main/java/com/example/agent/runtime/raw/RawResultResolveService.java:32`
  - 问题：新增存储介质时需要改解析服务，开放封闭性不足。

### 4.3 三级（中风险）

- 仓储语义不一致（内存与数据库）
  - 内存仓储追加模式：
    - `src/main/java/com/example/agent/runtime/step/repository/InMemoryStepRecordRepository.java:29`
  - 数据库仓储为冲突更新语义：
    - `src/main/java/com/example/agent/runtime/step/repository/JdbcStepRecordRepository.java:65`
  - 运行时会多次保存同一 `StepRecord`：
    - `src/main/java/com/example/agent/runtime/step/StepRuntimeService.java:110`
    - `src/main/java/com/example/agent/runtime/step/StepRuntimeService.java:194`
  - 问题：在内存模式下可能出现重复记录，影响时间线与调试判断一致性。

- 阻塞等待缺少超时治理
  - `src/main/java/com/example/agent/runtime/control/ExecutionControlService.java:173`
  - `src/main/java/com/example/agent/runtime/control/ExecutionControlService.java:176`
  - 问题：在异常控制路径下可能出现长时间等待，线程资源回收弹性不足。

- 异常处理存在“静默失败”点
  - `src/main/java/com/example/agent/runtime/codec/StepResultJsonCodec.java:37`
  - `src/main/java/com/example/agent/runtime/codec/StepResultJsonCodec.java:55`
  - `src/main/java/com/example/agent/runtime/codec/StepResultJsonCodec.java:72`
  - 问题：序列化失败直接返回空，若缺少配套日志，排障链路会变长。

### 4.4 四级（低风险）

- 局部死代码迹象
  - `src/main/java/com/example/agent/runtime/raw/output/RawOutputEnvelopeBuilder.java:215`
  - 现象：`readString` 方法当前未被调用。
  - 风险：低，但会增加后续阅读噪音。

- `prepare`：`二级（良好）`

## 六、整改优先级与路线

### 6.1 第一阶段（优先，建议一到两周）

- 抽离并统一执行控制
  - 让 `ReactLoopService` 复用 `RuntimeExecutionGate` 与 `RuntimeApprovalGate`。
- 统一步骤仓储语义
  - `InMemoryStepRecordRepository` 改为按 `stepId` 更新，和数据库实现保持一致。
- 增强异常可观测性
  - 对 `StepResultJsonCodec` 增加失败日志与最小上下文信息。

### 6.2 第二阶段（中优先，建议两到四周）

- 拆分超大类
  - `AgentRuntime` 拆为主流程编排器、事件发布协同器、上下文回填协同器。
  - `LlmStepService` 拆为决策器、工具执行器、结果汇总器。
  - `StepOutputSummaryBuilder` 拆为摘要生成器、快照器、裁剪器。
- 消除关键双向依赖
  - 先处理 `engine` 与 `finalize`、`step` 与 `step.executor`。

### 6.3 第三阶段（长期，建议四到八周）

- 收敛动态边界
  - 对高频字段引入类型化对象，逐步减少核心链路中的裸 `Map`。
- 扩展原始存储抽象
  - 将“写入+读取/解析能力”统一到可扩展接口，降低 `resolve` 服务对具体实现的感知。

---

## 七、结论

- 当前 `runtime` 架构不是“失控状态”，但已经进入“复杂度临界区”。
- 如果继续直接叠加功能而不治理，将优先在以下方面出现质量问题：
  - 回归影响面扩大
  - 行为不一致概率上升
  - 新人上手成本显著增加
- 建议优先推进“控制逻辑统一 + 仓储语义一致 + 超大类拆分”三件事，可在较小成本下显著降低维护风险。
