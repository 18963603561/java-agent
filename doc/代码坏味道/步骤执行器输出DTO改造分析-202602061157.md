# 步骤执行器输出从 `Map<String,Object>` 过渡到 `DTO` 的可行性分析

## 1. 背景与目标

当前步骤执行器接口为 `Map<String, Object> execute(StepExecutionRequest request)`，执行器输出在运行时链路中被多处跨层透传与解析，导致以下问题：

- 输出键约定隐式分散：上层通过字符串键（例如 `tool`、`rawRef`、`result`）解析输出，缺少编译期约束。
- 同类解析逻辑重复：`rawRef`、`refs`、`toolName` 的提取逻辑在多个位置重复实现，维护成本高。
- 可测试性弱：无法用类型表达“关键字段必有/可选”的约束，回归用例难以覆盖所有键形态。

本次分析的目标是：

- 减少 `Map<String,Object>` 在运行时核心链路的跨层透传。
- 为“步骤执行器输出”定义显式输出对象（`DTO`），并梳理涉及改动点与可落地路径。

## 2. 现状梳理

### 2.1 调用链路与透传点

步骤输出的主链路如下：

1. `AgentRuntime` 组织执行流程。
2. `StepExecutionDelegate.execute(...)` 调用 `StepExecutorRouter.execute(...)`。
3. `StepExecutorRouter` 选择具体 `StepTypeExecutor.execute(...)`。
4. 执行器返回 `Map<String,Object>` 作为步骤原始输出。
5. `AgentRuntime` 将输出用于：
   - `enrichOutputSummaryForReflection(...)`：可选生成摘要并合并回输出映射，用于反思。
   - `ReflectionService.reflect(step, output, ...)`：反思阶段直接消费输出映射。
   - `StepRuntimeService.completeStep(record, output, ...)`：落库前构建 `StepResult`。
   - `updateRuntimeContext(runtimeContext, record, output)`：将最后一步摘要与原始输出写入运行时上下文。
6. 异常时 `StepFailureRecoveryService` 可能调用 `StepExecutionDelegate.executeTool(...)` 获取兜底输出，并在输出映射上追加 `fallbackFrom`、`fallbackReason`。

### 2.2 输出映射中的关键键（隐式约定）

从现有实现可归纳出一组“被上层解析/复用”的键：

- 原始引用：`rawRef`，以及嵌套形态 `rawResult.rawRef`、`result.rawRef`、`raw.rawRef`。
- 引用集合：`refs`，以及扁平引用 `decisionRawRef`、`summaryRawRef`、`toolRawRef`、`modelRawRef`。
- 工具信息：`tool`、`toolName`。
- 反思/摘要字段（由 `StepOutputSummaryBuilder` 生成并可能合并到输出中）：
  - `outputSummary`、`toolResultSummary`、`stepSummary`、`outputDigest`、`truncated`。
- 兜底字段（由恢复逻辑写入）：`fallbackFrom`、`fallbackReason`。

不同执行器还会输出各自的业务键，例如 `finalAnswer`、`iterations`、`citations` 等。

### 2.3 当前类型边界的特点

- `StepRecord.output` 已经是显式对象 `StepResult`，并非 `Map`。
- 但 `StepResult.raw.data` 仍为 `Map<String,Object>`，用于保留原始输出。
- 也就是说：`Map` 目前主要承担“执行器输出的临时载体”与“原始输出快照”的双重职责。

## 3. `DTO` 改造的可行性评估

### 3.1 方案对比

#### 方案 A：执行器直接返回 `StepResult`

做法：将 `StepTypeExecutor.execute(...)` 返回类型从 `Map<String,Object>` 改为 `StepResult`。

优点：

- 跨层透传对象完全类型化，主链路不再直接传 `Map`。
- 与 `StepRecord.output` 的最终存储对象一致，认知成本低。

缺点：

- `StepResult` 目前由 `StepRuntimeService` 统一构建（补齐 `meta`、`rawRef`、`structured`、`summary` 等），下沉到执行器会导致职责外溢。
- 反思阶段在 `completeStep` 之前发生，仍需要把输出转为 `Map` 或抽取可反思视图。
- 外部工具输出天然为 `Map`，执行器仍需把 `Map` 填进 `StepResult.raw.data`，类型收益有限。

结论：可行但侵入性较强，不建议作为首个落地版本。

#### 方案 B：引入“执行器输出 `DTO`”作为统一封装（推荐）

做法：新增 `DTO`（例如 `StepExecutionOutput`），执行器统一返回 `DTO`，`DTO` 内部保留原始 `Map`，同时显式暴露关键字段。

建议 `DTO` 至少包含：

- `Map<String,Object> payload`：原始输出映射（保持兼容性）。
- `String toolName`：统一的工具名视图（优先来自显式字段，其次从 `payload` 解析）。
- `String rawRef`：统一的原始引用视图（集中实现解析逻辑）。
- `Map<String,String> refs`：统一的引用集合视图（可选）。
- `Map<String,Object> summaries`：反思/摘要字段的聚合视图（可选，或仍放在 `payload` 中）。
- 便捷方法：`Map<String,Object> toMapForReflection()`、`Map<String,Object> toMapForPersistence()`。

优点：

- 主链路签名从 `Map` 升级为 `DTO`，显著减少跨层裸 `Map` 透传。
- `rawRef`、`refs`、`toolName` 提取逻辑可以集中，消除 `AgentRuntime`、`StepRuntimeService`、`RawOutputEnvelopeBuilder` 等处的重复。
- 可在 `DTO` 层对关键字段做校验与归一化，提升稳定性。
- 对外部工具输出仍保持 `Map` 弹性，不强行类型化不可控数据。

缺点：

- 需要改动 `StepTypeExecutor` 及所有实现类，属于一次性“接口级”变更。
- 反思服务 `ReflectionService` 目前以 `Map` 为入参，仍需通过 `DTO` 转换或增加重载。

结论：可行性高，收益明确，且改动面可控，建议采用。

#### 方案 C：不改接口，仅增加工具类集中解析

做法：保持 `Map` 返回不变，新增 `StepOutputExtractor` 或类似工具类，集中实现 `rawRef`、`toolName`、`refs` 的解析。

优点：

- 改动最小，风险最低。

缺点：

- 无法减少跨层 `Map` 透传，只是把解析集中，目标达成度较低。

结论：可作为方案 B 的前置或补充，但不单独满足目标。

### 3.2 推荐结论

推荐采用方案 B：引入“执行器输出 `DTO`”作为统一封装对象，通过 `DTO` 实现关键字段归一化，并将 `Map` 收敛到 `DTO` 内部和持久化原始快照层。

## 4. 落地影响范围与改动文件清单

以下为按“必须改动 / 可选改动”划分的文件清单。

### 4.1 必须改动（签名与主链路）

- `src/main/java/com/example/agent/runtime/step/executor/StepTypeExecutor.java`
  - `execute(...)` 返回类型从 `Map<String,Object>` 改为 `DTO`（例如 `StepExecutionOutput`）。
- `src/main/java/com/example/agent/runtime/step/executor/StepExecutorRouter.java`
  - `execute(...)` 返回类型跟随调整。
- `src/main/java/com/example/agent/runtime/step/StepExecutionDelegate.java`
  - `execute(...)` 与 `executeTool(...)` 返回类型跟随调整。
- `src/main/java/com/example/agent/runtime/engine/AgentRuntime.java`
  - 将 `output` 从 `Map` 改为 `DTO`。
  - 反思入口、上下文更新与落库调用点通过 `DTO` 的 `toMap...()` 或显式字段获取数据。
- `src/main/java/com/example/agent/runtime/step/StepRuntimeService.java`
  - `completeStep(...)` 接收 `DTO`（或保持入参为 `Map`，但建议随主链路统一）。
  - `buildStepResult(...)` 读取 `DTO` 的统一字段（例如 `rawRef`、`toolName`），减少对 `payload` 字符串键的散落依赖。
- `src/main/java/com/example/agent/runtime/recovery/StepFailureRecoveryService.java`
  - `fallbackOutput` 类型改为 `DTO`，并把 `fallbackFrom`、`fallbackReason` 转为 `DTO` 的显式字段或扩展字段。

### 4.2 必须改动（执行器实现类）

以下执行器需将返回值从 `Map` 改为 `DTO`：

- `src/main/java/com/example/agent/runtime/step/executor/LlmStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/ToolStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/ReactStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/ChainOfThoughtStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/ThoughtTreeStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/MultiAgentStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/DebateStepExecutor.java`
- `src/main/java/com/example/agent/runtime/step/executor/ResearchStepExecutor.java`

执行器内部仍可先构建 `Map`，再通过 `DTO` 工厂方法封装，例如 `StepExecutionOutput.of(payload)`，保证改动小且可渐进演进。

### 4.3 建议改动（集中解析与去重）

为最大化 `DTO` 价值，建议将以下重复解析逻辑收敛到 `DTO` 或工具类中：

- `rawRef` 解析：目前 `AgentRuntime`、`StepRuntimeService`、`RawOutputEnvelopeBuilder` 各有一份逻辑。
- `toolName` 解析：目前 `StepRuntimeService.buildMeta(...)` 仅取 `payload.get("tool")`，而 `StepOutputSummaryBuilder` 兼容 `toolName`。

建议在 `DTO` 中提供统一的 `resolveRawRef(...)`、`resolveToolName(...)`，并逐步替换重复实现。

### 4.4 测试改动与建议新增

现有测试将受签名影响需要调整：

- `src/test/java/com/example/agent/runtime/StepRuntimeServiceTest.java`
- `src/test/java/com/example/agent/runtime/AgentRuntimeApprovalIntegrationTest.java`
- `src/test/java/com/example/agent/runtime/engine/StepFailureRecoveryServiceTest.java`

建议新增或补强的回归点：

- `DTO` 对 `rawRef` 多形态输入的解析用例（顶层与嵌套）。
- `DTO` 对 `toolName` 的归一化策略用例。
- 反思阶段与落库阶段对 `DTO` 的 `Map` 视图一致性用例（确保不改变现有行为）。

## 5. 风险与注意事项

- 外部工具输出结构不稳定：`DTO` 不应强行对工具返回做强类型约束，建议保留 `payload` 作为扩展承载。
- 可变性与副作用：当前逻辑会对输出映射执行 `put`（例如兜底字段与反思摘要合并）。引入 `DTO` 时需要明确：
  - `DTO` 是否允许在内部持有可变 `Map`；
  - 或者 `DTO` 提供“复制并追加字段”的方法以避免共享引用带来的副作用。
- 兼容性要求：如果 `StepResult.raw.data` 的结构被外部依赖（例如前端或审计），`DTO` 改造应保证 `payload` 形态不变。

## 6. 建议落地路径（按可验证的小步）

1. 新增 `DTO`（例如 `StepExecutionOutput`）与最小解析能力（`rawRef`、`toolName`）。
2. 调整 `StepTypeExecutor` 及其实现类返回 `DTO`，但 `DTO` 仍仅包裹现有 `payload`，不改变键结构。
3. 调整 `AgentRuntime`、`StepRuntimeService`、`StepFailureRecoveryService` 使用 `DTO`。
4. 补齐单元测试，确保 `mvn test` 全绿，并增加 `DTO` 解析回归用例。
