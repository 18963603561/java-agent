# 运行时核心链路类型边界最优方案（新项目无历史包袱）

## 1. 结论先行（最优方案）

在“新项目、不考虑历史兼容”的前提下，最优方案不是把 `Map<String,Object>` 简单换成一个包裹 `Map` 的 `DTO`，而是将 `Map` **收敛到集成边界**，在运行时核心链路内建立清晰的类型边界：

- **核心链路只流转显式对象**：步骤执行、反思、落库、上下文更新都使用显式输入输出对象。
- **`Map` 只允许出现在两类位置**：
  - 外部/不受控数据边界（例如工具返回、模型返回、动态上下文扩展）。
  - 原始快照层（例如持久化的 `raw` 数据，用于审计与回放）。
- **消除“魔法键”跨层传播**：将 `rawRef`、`toolName`、`summary`、`truncated`、`fallbackFrom` 等关键字段从字符串键约定提升为对象字段，并提供统一解析与归一化规则。

这套方案能同时提升可读性、可复用性与可测试性，并把后续扩展成本控制在“新增执行器/新增字段”而非“全链路字符串键联动”。

## 2. 现状与问题（影响其他模块 = 边界设计问题的信号）

你看到的“改动会影响其他模块”，在当前代码里不仅是正常耦合，更是边界不清晰的信号，典型表现如下：

1. **执行器输出 `Map` 贯穿多层**
   - `StepTypeExecutor.execute(...)` 返回 `Map`，一路被 `AgentRuntime`、`ReflectionService`、`StepRuntimeService`、`StepFailureRecoveryService` 等直接消费。
2. **摘要字段被“写回”输出映射**
   - `AgentRuntime.enrichOutputSummaryForReflection(...)` 将 `StepOutputSummaryBuilder` 的结果合并回 `output`，导致“原始输出”和“摘要输出”混在一个 `Map` 里，边界模糊。
3. **运行时上下文 `runtimeContext` 依赖魔法键**
   - `AgentRuntime.updateRuntimeContext(...)` 写入 `lastStepSummary` 等键。
   - `ChainOfThoughtService.extractObservation(...)` 读取 `lastStepSummary`、`observationSummary` 等键。
   - 这意味着上下文契约不是通过类型体现，而是靠字符串约定，极易漂移。
4. **重复的解析逻辑分散**
   - `rawRef`/`refs` 的提取逻辑在 `AgentRuntime`、`StepRuntimeService`、`RawOutputEnvelopeBuilder` 等多处重复。
5. **组件装配方式影响可复用性**
   - `StepExecutionDelegate` 在构造函数里 `new` 各种执行器，导致依赖耦合、测试替换困难、扩展不利于插件化。

因此，“牵一发而动全身”并不代表必须接受，而是提示我们需要把运行时链路的契约提升为显式类型。

## 3. 最优架构设计（建议落地形态）

### 3.1 核心类型（建议新增）

1. `StepExecutionOutput`（步骤执行输出 `DTO`）
   - 用途：作为 `StepTypeExecutor` 的统一返回对象，承载“原始输出快照 + 关键字段显式化 + 统一解析”。
   - 建议字段：
     - `Map<String,Object> payload`：原始输出（外部工具/模型返回或执行器自行构建）。
     - `String toolName`：统一工具名视图。
     - `String rawRef`：统一原始引用视图。
     - `Map<String,String> refs`：统一引用集合视图（可选）。
     - `boolean truncated`：原始层裁剪标记（可选）。
     - `Map<String,Object> summaries`：摘要字段聚合（可选，但建议不要与 `payload` 混放）。
   - 建议行为方法：
     - `withFallback(...)`：追加兜底信息而不直接修改 `payload` 引用。
     - `toMapForReflection()`：生成反思需要的视图（优先摘要，必要时附带受控的原始片段）。
     - `toMapForPersistence()`：生成落库需要的原始输出视图（通常就是 `payload` 或其封装）。
2. `RawOutputEnvelope`（原始输出封装对象）
   - 用途：替代 `RawOutputEnvelopeBuilder.build(...)` 直接返回 `Map` 的方式，让“原始层结构”类型化。
   - 字段：`rawRef`、`refs`、`data`、`truncated`。
3. `RuntimeContext`（运行时上下文对象）
   - 用途：替代跨层直接读写 `Map` 的方式，至少把核心字段类型化，例如：
     - `lastStepId`、`lastStepType`、`lastStepSummary`、`lastStepRawRef` 等。
   - 保留 `extensions`：用于承载确实需要动态扩展的键值对，但禁止业务逻辑依赖隐式键名。

### 3.2 主链路职责分层（推荐）

- `AgentRuntime`：只做流程编排（计划、执行、反思、重试、收敛输出）。
- `StepExecutorRouter`：只做“按 `stepType` 路由”。
- `StepTypeExecutor`：只做“执行某类步骤，返回 `StepExecutionOutput`”。
- `StepRuntimeService`：只做“落库/事件发布/构建 `StepResult`”，不再承担输出归一化的重复解析。
- `ReflectionService`：只消费“反思输入视图”，建议改为接收 `StepExecutionOutput` 或更窄的 `ReflectionInput`，而不是裸 `Map`。

### 3.3 依赖注入与扩展方式（建议改造）

- 将各执行器改为 Spring Bean（例如 `@Component`），由 Spring 注入 `List<StepTypeExecutor>` 给 `StepExecutorRouter`。
- `StepExecutionDelegate` 不负责 `new` 执行器，只持有 `StepExecutorRouter` 与必要的专用接口（例如 `ToolStepExecutor` 的兜底能力可以下沉为单独接口）。

这样可以显著提高可测试性与复用性，并使新增步骤类型不需要改动装配代码。

## 5. 落地路径（新项目建议直接“一次到位”）

由于你明确“不需要考虑历史包袱”，建议采用一次到位的改造节奏：

1. 定义 `StepExecutionOutput`、`RawOutputEnvelope`、`RuntimeContext` 三类核心类型，并补齐单测。
2. 将 `StepTypeExecutor` 返回类型统一切换为 `StepExecutionOutput`，并同步改造所有执行器实现。
3. 改造 `AgentRuntime`、`StepRuntimeService`、`StepFailureRecoveryService` 使用 `StepExecutionOutput`。
4. 将 `ReflectionService`、`ReactLoopService`、`ChainOfThoughtService` 等消费侧从 `Map` 迁移到“视图对象/显式字段”。
5. 将执行器装配改为 Spring 注入模式，移除 `StepExecutionDelegate` 内部 `new` 的行为。

## 6. 备注：为什么这是“最优”

- 类型边界清晰：核心流程可读性显著提升，代码意图通过字段而非字符串键表达。
- 复用性更强：摘要、原始封装、引用解析不再散落多处，可以被多个执行器与模块复用。
- 测试成本更低：关键字段有编译期约束，回归用例更容易覆盖。
- 扩展更安全：新增步骤类型不再需要修改上层多个位置的字符串键处理逻辑。
