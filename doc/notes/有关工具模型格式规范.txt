你现在做的这套 Java Shannon Agent Orchestrator，如果没有 EvidencePack（证据包），系统是不可审计、不可回放、不可解释的。

很多人把它误以为是“日志增强”，其实完全不是一回事。

EvidencePack 是 让多智能体系统具备“可解释推理链”的核心部件。
它解决的是：模型的结论从哪来？依据了什么？用了哪些外部信息？

这在你现在做的 Memory / Tool / Research / Hook / Summary / Replay / Audit 整条链路里，是中枢角色。

一句话理解
EvidencePack = 本次任务中，模型做出结论时“用过的全部外部证据清单”

包括：

用过哪些 Tool 的结果

召回了哪些 Memory

引用了哪些 Research 来源

截断了哪些上下文

最终回答依赖了哪些证据

在哪里生成？（非常关键）
EvidencePack 不是某一步生成的，而是在运行时被持续“写入”。

生成位置分布在 4 个关键节点：

阶段	触发位置	写入什么证据
Step 执行前	HookManager.preStep	记录计划/意图/上下文快照引用
Tool 调用后	HookManager.postTool	最重要：工具结果证据
Memory 召回后	MemoryRecallService	召回的 memory 证据
Research 完成后	AgentRuntime	外部来源证据（URL/文档/引用）
注意：EvidencePack 是边跑边长大的。

结构长什么样？
一个典型 EvidencePack（精简示意）：

{
  "packId": "ep-xxx",
  "tenantId": "t1",
  "workflowId": "w1",
  "snapshotId": "s3",
  "evidences": [
    {

      "source": "fmdb.query",
      "stepId": "step-2",
      "digest": "rows=120, cols=8",
      "ref": "toolResultRef-abc"
    },
    {
      "type": "memory",
      "source": "memory_records",
      "memoryId": "m-77",
      "summary": "用户偏好：中文+结构化",
      "ref": "memoryRef-77"
    },
    {
      "type": "research",
      "source": "https://xxx/doc",
      "title": "FMDB FRC 建表规范",

    "memoryCount": 1,
    "researchCount": 1
  }

你会发现：这里面不放大文本，只放引用和摘要。

因为真正的大内容在：

tool_result 表

memory_records 表

research 引用缓存

step output summary

EvidencePack 是索引层。

EvidencePack 在哪里被用到？（这才是精髓）
1️⃣ 给 LLM 做最终总结时
在 FINAL / LLM Step：

PromptAssembler 会把 EvidencePack 注入进去

模型看到的不是一堆上下文，而是：

你可以基于以下证据回答：
- 工具 fmdb.query 返回 120 行
- 用户偏好：中文结构化
- 引用文档：FRC 建表规范
这叫 Evidence-aware answering。

2️⃣ 用于 Summary / Digest 层裁剪
StepOutputSummaryBuilder 会：

根据 EvidencePack 决定哪些内容必须保留，哪些可以截断。

因为有证据引用，就不怕截断正文。

3️⃣ 用于 Replay / 审计 / 回放
回放任务时，不需要完整上下文：

只需要 EvidencePack + Snapshot，就能还原推理依据。

这是你做 Task History Timeline 的关键。

4️⃣ 用于 Reflection Reviewer（是否重试）
你之前那套 步骤质量审查提示词：

判断是否 retry 的核心依据就是：

Evidence 是否完整、是否合理

不是看 answer，而是看 EvidencePack。

5️⃣ 用于 Memory 写回决策
MemoryWriteService 会判断：

这次结论是不是基于稳定证据产生的？

如果 EvidencePack 很弱，就不写长期记忆。

为什么必须有 EvidencePack（没有会发生什么）
如果没有：

Step Summary 只能靠全文压缩（token 爆炸）

无法判断模型结论依据

Replay 时必须还原全部上下文（不现实）

无法做审计

无法做可解释 AI

Memory 写回完全拍脑袋

这也是 Shannon memory-system-architecture 里专门强调 Evidence 的原因。

和日志的本质区别
日志	EvidencePack
给人看	给模型 + 系统用
文本记录	结构化证据索引
事后查看	运行时参与决策
不参与推理	直接参与 Prompt 与裁剪

总结（非常重要）
EvidencePack 不是附属功能
是 让 Agent 系统具备“推理可解释性 + 上下文可裁剪性 + 任务可回放性”的核心枢纽

没有它，你做的：

分层摘要

上下文预算

记忆系统

反思重试

任务回放

审计能力

全部会退化成“日志系统”级别。

你说：
多个步骤输入输出时，对模型或工具生成的结果一般有哪几个方面组成，原始结果和摘要是否必须要有？当任务依赖上一个步骤时给出的数据是什么，如何设计
ChatGPT 说：
在多步骤（plan → step1 → step2 …）里，每个步骤的“输入/输出”建议拆成 4 层，这样既能控体积、又能可追溯、还能让后续步骤稳定依赖。

1) 每个步骤输出一般由哪几部分组成
建议把 Step 的输出统一成下面这几块（不管是 LLM 还是 TOOL）：

状态与元信息（Meta）

stepId / seq / type（TOOL/LLM/FINAL/RESEARCH…）

status（COMPLETED/FAILED…）

modelId 或 toolName

timings（开始/结束/耗时）

attempt / retry 等

原始结果（Raw payload）

TOOL：工具返回的完整 JSON / 表格 / 文本（可能很大）

LLM：模型原始回复（完整文本/JSON）

结构化可依赖结果（Structured result）

从 raw 提取出的、供后续 step 稳定消费的字段

例如：rows[]、topK[]、entities[]、sql、error_code、next_action 等

这是“契约层”，比 raw 稳定、比摘要可编程

证据与引用（Evidence refs）

toolResultRef / memoryRef / citationRef 等

用 EvidencePack 做索引，不在 step output 里重复塞大文本

2) 原始结果和摘要是否必须要有？
原始结果（Raw）——建议有，但不一定必须“常驻”
必须可回溯：要么落库（大对象表/对象存储），要么可重放再取回

但不一定要在“步骤上下文里一直携带”，否则 token/内存爆炸

✅ 结论：Raw 必须可获取，但不必须常驻上下文

摘要（Summary）——强烈建议有，但不是绝对必须
摘要有两类用途：

上下文预算：给后续 step 作为短上下文输入

可观测性/审计：快速看懂每步做了啥

如果你已经有 Structured result（契约层）且足够短，摘要可以弱化；但在现实里：

工具返回大、字段杂、模型输出长

只靠 structured 很难覆盖所有“给人看、给模型用”的信息

✅ 结论：建议每步都产出摘要（受限、可截断），但不是逻辑硬依赖

最稳的组合：Raw（可回溯） + Structured（可编程依赖） + Summary（可控上下文）

3) 当任务依赖上一个步骤时，给出的数据是什么？
后续步骤依赖前一步时，不要直接依赖 raw，也不要只给摘要（摘要不可编程）。

推荐依赖顺序（从强到弱）：

依赖 Structured result（首选）

例如：previous.outputs.structured.topTables[]

例如：previous.outputs.structured.sql

例如：previous.outputs.structured.entities

依赖 Evidence refs（需要时再取回/展开）

例如：toolResultRef=xxx，后续若要更细节，再去拉取 raw 或分页数据

依赖 Summary（兜底给模型理解）

例如：把上一环节摘要作为自然语言上下文补充

✅ 结论：真正传给下一步的是：structured + refs（必要时）+ 少量摘要

4) 如何设计：一套通用的 Step I/O 合同
StepInput（后续步骤拿到的“可执行输入”）
{
  "question": "本步要解决的问题（所有 step 必填）",
  "dependsOn": ["step-1"],
  "contextRefs": ["ep:pack-1"], 
  "upstream": {
    "step-1": {
      "structured": { "topTables": ["t1","t2"] },
      "refs": { "toolResultRef": "tr-abc" },
      "summary": "上一步找到手机号字段表：t1,t2"
    }
  },
  "constraints": { "maxRows": 50 }
}
StepOutput（每步产物）
{
  "meta": { "stepId":"step-1","type":"TOOL","status":"COMPLETED","tool":"fmdb.search" },
  "rawRef": "tr-abc",               
  "structured": { "topTables": ["t1","t2"], "matchRules": ["手机号","mobile"] },
  "summary": "命中2张表：t1,t2；优先级：t1>t2",
  "errors": []
}
要点：

raw 不直接塞 output，只放 rawRef（你已经在做 summary builder / evidence pack，很合适）

structured 是稳定契约，下一步直接用

summary 是给模型读的短文本，受 maxChars/maxListItems 控制

5) 设计上的关键取舍（你这类工程最容易踩坑）
坑 1：只传摘要
摘要不可编程，后续步骤要“猜”

容易幻觉、容易丢关键信息

✅ 必须有 structured（哪怕很小）

坑 2：把 raw 全塞进上下文
token 爆、内存爆、传输爆

还容易触发 JSON 解析/最大字符串限制（你前面遇到过）

✅ raw 走引用（ref）+ 按需展开

坑 3：structured 设计成“随意 JSON”
今天工具A给字段x，明天工具B给字段y，后续步骤写不动

最终又回到摘要/原文依赖

✅ structured 要有 schema/contract（哪怕用 JSON Schema 或接口定义）

推荐的最小落地方案（不重构也能做）
每个 step output 固定含：meta + structured + summary + refs

raw 只存储在外部（DB/对象存储），step output 只记录 rawRef

后续 step 输入里，只注入：

upstream structured（必选）

upstream summary（可选）

upstream refs（可选）

PromptAssembler 里对注入顺序固定：

structured（机器可用）

summary（模型可读）

refs（提示可追溯、可按需展开）

你说：
原始结果和结构化可依赖结果区别是什么
ChatGPT 说：
这个问题是多步骤智能体是否稳定的分水岭。

很多系统把这两者混在一起，结果就是：

后续步骤要么读不懂、要么强依赖原文、要么疯狂幻觉。

一句话先记住
Raw（原始结果）是“事实全量”
Structured（结构化结果）是“为后续步骤准备的契约数据”

两者目的完全不同。

Raw 是什么？
工具 / 模型真实返回的完整内容，不做任何语义加工。

例子（FMDB 工具返回）：

{
  "rows": [
    {"table":"t_user","column":"mobile","type":"string","comment":"手机号"},
    {"table":"t_order","column":"phone","type":"string","comment":"联系电话"}
  ],
  "cost": 183,
  "scanPartitions": 24,
  "traceId": "xxx"
}
特点：

很大

字段很多

结构不稳定（工具升级字段就变）

包含大量后续步骤不关心的信息

但它是完整事实来源（可追溯）

Raw 是“档案袋”。

Structured 是什么？
从 Raw 里抽取出来、专门给后续步骤使用的一小撮稳定字段。

同样这个例子，structured 可能是：

{
  "matchedTables": ["t_user","t_order"],
  "matchedColumns": ["mobile","phone"],
  "matchCount": 2
}
特点：

很小

字段极稳定（你定义的契约）

后续步骤可以直接编程依赖

与工具实现解耦

Structured 是“任务接力棒”。

本质区别（非常关键）
维度	Raw 原始结果	Structured 可依赖结果
目的	完整事实留档	给下一步用
体积	大	小
稳定性	低（随工具变化）	高（你定义）
可读性	给人/审计	给程序/模型
是否进上下文	❌ 不应该	✅ 必须
是否可被依赖	❌	✅
是否可截断	❌	✅
来源	工具/模型	你在 StepRuntime 提取
为什么不能让下一步直接用 Raw？
因为你会立刻遇到这 4 个灾难：

工具字段一改，后续步骤全挂

token/内存爆炸（你已经踩过）

模型读 Raw 会被噪音淹没

后续步骤要“理解 JSON 语义” → 幻觉

正确的数据流（你现在的架构其实非常适配）
Tool 返回 Raw
        ↓
StepRuntime 提取 Structured（契约层）
        ↓
StepOutputSummaryBuilder 生成 Summary（给模型）
        ↓
EvidencePack 记录 rawRef
后续步骤拿到的是：

structured + summary + rawRef
绝对不是 raw。

一个非常贴近你场景的例子
Step1：找出包含手机号的表
Raw（FMDB 返回 200 行各种字段） ❌ 后续不能用

Structured：

{
  "tablesWithMobile": ["t_user","t_order"]
}
Summary：

找到2张包含手机号字段的表：t_user, t_order

Step2：基于这些表生成治理 SQL
它依赖的是：

previous.structured.tablesWithMobile
不是去解析 200 行 raw。

这就是可编排和不可编排的差别。

一句话总结到位
Raw 是为了 可追溯
Structured 是为了 可编排

没有 Raw → 不可审计
没有 Structured → 不可多步骤协作

两个都要，但职责完全不同。

你说：
因为工具和模型输出的原始数据都不一样，如何设计出稳定的structured呢
ChatGPT 说：
你这个点非常关键：Raw 天生不稳定（不同工具/不同模型/同一工具升级都可能变），所以 Structured 的稳定性只能来自一件事：

Structured 不是“工具返回长什么样”，而是“编排系统规定后续步骤需要什么”。

也就是说：Structured 的稳定性靠 你定义的契约（contract）+ 适配层（extractor/adapter），而不是靠工具自觉。

下面给你一套在智能体编排里最常用、最稳的设计方法。

1) 先定“稳定的语义域”，不要定“稳定的字段细节”
你要稳定的是语义类型（例如：查询命中表、生成 SQL、识别实体、计算指标、错误分类），而不是每个工具五花八门的字段。

建议：先抽象出 8~12 个“通用结果类型”（ResultKind）
比如（够你覆盖 80% 场景）：

TABLE_MATCHES：命中表/字段（数据发现、治理检索）

SQL：SQL 产物（生成/修复/优化）

RECORDSET：表格/行集（查询结果）

ENTITY_LIST：实体集合（手机号/IMSI/IMEI…识别）

DECISION：决策/路由（下一步做什么）

DIAGNOSIS：诊断（根因、建议、风险）

DOCUMENT_CITATIONS：引用/来源（research）

ERROR：错误分类与可行动建议

Structured 的第一层稳定字段就是：kind。

2) 用“统一外壳 + kind-specific payload”的契约
不要搞“每个工具一个 structured 结构”，会炸。

推荐契约长这样：

{
  "kind": "TABLE_MATCHES",
  "schemaVersion": 1,
  "data": { ... },
  "quality": { "confidence": 0.82, "warnings": ["truncated"] },
  "refs": { "rawRef": "tr-abc", "evidenceIds": ["ev-1","ev-2"] }
}
外壳固定：kind / schemaVersion / quality / refs

data 随 kind 变化：但每个 kind 的 data 你可以定义成稳定 schema

3) 每个 kind 的 data 要“够用且最小”，只放后续必需
举 2 个你最常见的：

3.1 TABLE_MATCHES（数据发现/治理检索）
{
  "kind": "TABLE_MATCHES",
  "schemaVersion": 1,
  "data": {
    "items": [
      {
        "table": "dwd_user",
        "column": "mobile",
        "matchType": "SEMANTIC|NAME|COMMENT",
        "score": 0.93,
        "reason": "列注释包含手机号"
      }
    ],
    "topTables": ["dwd_user", "dwd_order"],
    "requiredFieldsCovered": ["mobile", "imsi"],
    "missingRequiredFields": ["imei"]
  }
}
注意：这里完全不关心工具 raw 里的 rows/cost/traceId/extra 字段。

3.2 SQL（生成 SQL/修复 SQL）
{
  "kind": "SQL",
