# P3改造任务清单-包设计合理性-202602112220

## 1. 输入与范围
- 依据文档：`doc/20260211/multiagent包设计评审-P0P4分级-202602111841.md`
- 关联基线：
  - `doc/20260211/P0改造落地与测试报告-包设计合理性-202602111936.md`
  - `doc/20260211/P1改造落地与测试报告-包设计合理性-202602112110.md`
  - `doc/20260211/P2改造落地与测试报告-包设计合理性-202602112210.md`
- 改造范围：`src/main/java/com/example/agent/orchestration/multiagent`
- 本清单目标：仅落地 `P3` 低优先级问题，聚焦“包内分层清晰化”和“职责边界进一步收敛”，不改变已完成的 P0~P2 运行语义。

## 2. P3改造总目标（必须全部达成）
1) 在 `dag` 子域内形成稳定的分层结构，避免“按能力 + 按层”混合增长导致后续耦合扩散。
2) 将 `MultiAgentRoleResolver` 的解析、修复、回退、诊断职责解耦为可独立测试的组件。
3) 建立包依赖守护规则，防止后续迭代把已收敛结构重新耦合回去。
4) 补齐包级设计文档与不变式说明，保障团队协作一致性。

## 3. P3具体改造任务清单

### T-P3-PKG-01：`dag` 子域分层重整（先局部，不全局大迁移）
- 问题来源：`P3-1 包内仍是按能力 + 按层混合组织`。
- 主要涉及目录：
  - `src/main/java/com/example/agent/orchestration/multiagent/dag`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/actor`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/audit`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/diagnosis`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/replay`
- 改造要求：
  - 在 `dag` 子域内建立三层语义分组并迁移类归属：
    - `application`：编排用例、流程协调、查询聚合。
    - `domain`：实体、值对象、策略、领域服务、端口接口。
    - `infrastructure`：仓储实现、传输实现、外部系统适配。
  - 迁移时禁止行为变更，只做结构重排与依赖收敛。
  - 所有迁移类保留原有日志与异常语义，不引入历史兼容分支。
- 验收标准：
  - `dag` 子域内核心类可以按 `application/domain/infrastructure` 明确归类。
  - 运行主链路（计划、执行、审计、诊断、回放）行为与 P2 基线一致。

### T-P3-PKG-02：`dag` 端口接口与实现分离（依赖方向显式化）
- 问题来源：`P3-1` 的延伸风险，后续实现类容易反向侵入核心流程。
- 主要涉及文件：
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/actor/state/DagRuntimeStateRepository.java`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/actor/state/DagMessageDedupRepository.java`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/actor/recovery/DagDeadLetterRepository.java`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/audit/DagAuditRepository.java`
  - 及其对应 `InMemory/Redis` 实现类
- 改造要求：
  - 将上述接口归口到 `dag/domain/port`（或等价的明确端口目录）。
  - 将 `InMemory/Redis` 等实现归口到 `dag/infrastructure/*`。
  - `application` 仅依赖端口，不直接依赖具体实现。
- 验收标准：
  - 代码层面可以清晰看出“上层依赖端口，下层实现端口”。
  - 不存在 `application/domain` 直接引用 `InMemory*` 或 `Redis*` 具体类。

### T-P3-PKG-03：`MultiAgentRoleResolver` 职责拆分
- 问题来源：`P3-2 部分类职责边界仍可进一步收敛`。
- 主要涉及文件：
  - `src/main/java/com/example/agent/orchestration/multiagent/MultiAgentRoleResolver.java`
  - 新增建议：
    - `src/main/java/com/example/agent/orchestration/multiagent/role/RolePlanParser.java`
    - `src/main/java/com/example/agent/orchestration/multiagent/role/RolePlanRepairService.java`
    - `src/main/java/com/example/agent/orchestration/multiagent/role/RoleFallbackFactory.java`
    - `src/main/java/com/example/agent/orchestration/multiagent/role/RoleResolveDiagnostics.java`
- 改造要求：
  - 解析（JSON→角色）、修复（调用修复服务）、回退（默认角色构建）、诊断（错误类型与日志策略）分离。
  - `MultiAgentRoleResolver` 保留门面职责，负责流程编排与结果聚合。
  - 关键逻辑块补充中文注释，日志上下文字段保持一致（`workflowId/stepType`）。
- 验收标准：
  - `MultiAgentRoleResolver` 代码体量显著收敛，单方法职责明确。
  - 解析失败、修复失败、回退路径可以分别单测。

### T-P3-PKG-04：包依赖守护测试（防止结构回退）
- 问题来源：P3结构问题如果无守护，后续迭代会快速回退。
- 主要涉及文件（新增建议）：
  - `pom.xml`（新增架构守护测试依赖，如 `archunit-junit5`）
  - `src/test/java/com/example/agent/orchestration/multiagent/architecture/MultiAgentPackageArchitectureTest.java`
- 改造要求：
  - 增加可执行的包依赖规则：
    - `domain` 不依赖 `infrastructure`。
    - `application` 不依赖 `api/http/controller`。
    - `infrastructure` 仅实现端口，不承载业务编排。
  - 将规则纳入默认测试集，避免成为“可选检查”。
- 验收标准：
  - 违反依赖方向时测试能稳定失败并给出清晰错误信息。
  - 现有合法结构下架构测试通过。

### T-P3-PKG-05：包级文档与不变式固化
- 问题来源：P3/P4 交叉问题，结构演进缺少显式文档导致口径分裂。
- 主要涉及文件（新增建议）：
  - `src/main/java/com/example/agent/orchestration/multiagent/README.md`
  - `src/main/java/com/example/agent/orchestration/multiagent/dag/README.md`
  - 可选：`package-info.java`（用于包注释）
- 改造要求：
  - 明确包边界、依赖方向、关键不变式与禁止事项。
  - 明确“新增类放置规则”，减少后续乱放。
  - 文档内容与现有代码保持一致，禁止“文档先行但代码不落地”。
- 验收标准：
  - 新成员可基于文档快速判断类应落在哪一层与哪个子域。
  - 代码评审时可用文档作为一致性检查基线。
