1) 当前串行 DAG 演进为 Actor 模式是否可行。

## 3. Actor 模式下如何确保消息依赖

### 3.1 依赖正确性的三层保障

第一层：静态校验（规划期）

- 节点 ID 唯一校验。  
- `dependsOn` 目标节点必须存在。  
- DAG 必须无环，发现环立即拒绝执行。  
- 可选：校验 topic 依赖是否存在至少一个合法生产者。

第二层：运行时门控（执行期）

- 每个节点维护 `remainingDeps` 计数，初值为其依赖数量。  
- 仅当收到有效依赖满足消息后才递减计数。  
- 当且仅当 `remainingDeps == 0` 且必需 topic 数据可见时，节点进入 `READY`。  
- `READY` 节点进入运行队列后，才允许触发执行。

第三层：一致性与幂等（消息期）

- 每个节点 mailbox 串行消费，避免并发乱序修改本节点状态。  
- 状态流转使用 CAS 语义：`PENDING -> READY -> RUNNING -> SUCCEEDED/FAILED`。  
- 重复消息去重，不重复扣减依赖计数。

### 3.2 推荐消息模型

建议消息类型：

- `DEPENDENCY_SATISFIED`：上游完成后通知下游依赖满足。  
- `NODE_START`：节点启动。  
- `NODE_COMPLETE`：节点成功完成并附带产物元信息。  
- `NODE_FAIL`：节点失败并附带异常上下文。

建议去重键：

- `workflowId:producerNode:consumerNode:topic:version`

说明：采用“至少一次投递 + 去重消费”即可满足当前单进程版本可靠性目标。

### 3.3 依赖门控执行流程（建议）

1) 运行时启动时初始化 `remainingDeps`、下游索引表、节点状态表。  
2) 所有入度为 0 的节点直接入 `READY` 队列。  
3) 节点执行成功后，写入 workspace topic，并向所有下游发送 `DEPENDENCY_SATISFIED`。  
4) 下游 actor 消费消息后先去重，再扣减 `remainingDeps`。  
5) 当下游满足执行条件，原子切换到 `READY` 并入队。  
6) 节点失败按监督策略处理：重试、跳过或快速失败。

### 3.4 丢消息与补偿机制

建议增加两道防线：

- 启动补偿：运行时启动时扫描 workspace 已有 topic，补发等价依赖满足事件。  
- 周期校验：定时执行依赖重算，发现“状态与事实不一致”时自动纠偏。

该思路可参考 Shannon 在等待、选择与退避中的处理方式：

- `vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:643`  
- `vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:677`  
- `vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:720`  
- `vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:101`

### 3.5 超时、失败传播与背压

- 节点等待依赖超时后进入 `WAITING` 或 `FAILED`，由策略决定是否继续流程。  
- 对可恢复错误进行有上限重试，重试过程必须发布治理事件。  
- 当就绪队列或 mailbox 超阈值，发布 `BACKPRESSURE_APPLIED` 并限制新激活节点数。

## 5. 优先级方案（聚焦依赖保障）

### P0：先落地“依赖门控 + 并行骨架”

- 目标：先保证“依赖正确 + 可并行”。  
- 产出：`DagActorRuntime`、`DagNodeActor`、`DagMessage`、最小事件集。  
- 验收：无依赖节点可并行；有依赖节点只在依赖满足后运行。

### P1：补齐监督策略与背压治理

- 目标：保证异常场景下可控、可恢复。  
- 产出：重试策略、失败传播策略、背压限制。  
- 验收：压力场景无雪崩，失败路径可观测。

### P2：补齐审计、回放与诊断

- 目标：进入稳定生产可运维状态。  
- 产出：状态审计、消息轨迹、执行回放、关键指标。  
- 验收：可定位依赖阻塞根因，可重放关键故障链路。

### P3：再考虑跨进程 Actor 扩展

- 目标：在单进程稳定后再扩展分布式。  
- 产出：外置 mailbox、分片路由、跨实例一致性方案。  
- 验收：跨实例场景保持幂等与依赖正确。

## 6. 最终建议

建议按 `P0 -> P1 -> P2` 推进，`P3` 按容量需求启动。  
其中 P0 必须优先完成“依赖门控 + 幂等去重 + 状态原子流转”，这是 Actor 化后确保消息依赖正确的最小闭环。
