## 2. P2问题复核结论（结合当前代码）

### 2.1 P2-01 多智能体交接状态一致性规则缺失（仍成立）

- 本项目现状证据：
  - `HandoffRecord` 仅有基础字段，缺少 `version`、状态迁移约束、冲突信息字段：`src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffRecord.java:13`
  - `HandoffService` 直接写入字符串状态 `FAILED/COMPLETED`，未经过显式状态机：`src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffService.java:63`
  - `HandoffService` 当前仅构建内存对象并返回，未接入仓储持久化与并发冲突控制：`src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffService.java:52`
  - 依赖等待采用固定轮询 + 线程睡眠，缺少指数退避和等待阶段事件：`src/main/java/com/example/agent/orchestration/multiagent/handoff/TopicDependencyCoordinator.java:47`
- Shannon 对照证据：
  - `SupervisorWorkflow` 使用版本门控保证演进兼容（`mailbox_v1/p2p_sync_v1/team_workspace_v1`）：`vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:101`
  - 依赖等待使用等待事件、超时日志、选择器与退避机制：`vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:643`
  - 依赖满足后发布 `DEPENDENCY_SATISFIED`，并将产物写入 workspace：`vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:748`
  - 使用失败阈值与重试计数控制失败传播：`vendor/Shannon/go/orchestrator/internal/workflows/supervisor_workflow.go:472`
- 结论：P1 虽补齐了 `Handoff` 主链路，但“状态一致性规则”仍未形成完整能力闭环，维持 `P2`。

### 2.2 P2-02 `BACKPRESSURE_APPLIED` 事件矩阵缺失（仍成立）

- 本项目现状证据：
  - 事件枚举已定义 `BACKPRESSURE_APPLIED` / `CIRCUIT_OPENED`，但主链路未发布：`src/main/java/com/example/agent/streaming/domain/EventType.java:134`
  - `McpToolClient` 已有限流与熔断拒绝分支（`RATE_LIMITED`、`CIRCUIT_OPEN`），但未发布对应治理事件：`src/main/java/com/example/agent/capabilities/tools/mcp/McpToolClient.java:174`
  - `EnforcementGateway` 当前只发布 `TOOL_INVOKED/TOOL_OBSERVATION/TOOL_ERROR`，未覆盖背压事件：`src/main/java/com/example/agent/capabilities/tools/enforcement/EnforcementGateway.java:127`
  - `RateLimitService` 与 `CircuitBreakerManager` 的 `allow` 仅返回布尔值，缺少结构化拒绝原因与事件载荷：`src/main/java/com/example/agent/governance/ratelimit/RateLimitService.java:48`、`src/main/java/com/example/agent/governance/circuitbreaker/CircuitBreakerManager.java:51`
- Shannon 对照证据：
  - 预算预检返回背压结构化结果并执行延迟：`vendor/Shannon/go/orchestrator/internal/workflows/middleware_budget.go:29`
  - 背压结构含 `BackpressureActive/BackpressureDelay/CircuitBreakerOpen/BudgetPressure`：`vendor/Shannon/go/orchestrator/internal/budget/manager.go:676`
  - 预算阈值触发时发布 `BUDGET_THRESHOLD` 流式事件：`vendor/Shannon/go/orchestrator/internal/budget/manager.go:271`
  - 预算活动层对背压与熔断状态进行可观测日志输出：`vendor/Shannon/go/orchestrator/internal/activities/budget.go:109`
- 推断说明：
  - Shannon 未直接使用事件名 `BACKPRESSURE_APPLIED`，但其“结构化背压结果 + 延迟执行 + 阈值事件发布”已经形成等价的生产治理可观测语义。
- 结论：本项目背压治理仍停留在“错误码可见、事件不可见”，维持 `P2`。

## 4. 具体改造任务清单

### 4.1 批次 P2-1：交接状态一致性（P2-01）

#### T-P2-HOF-01：统一 `Handoff` 状态模型与字段（复杂度 `L2`）

- 目标：把“字符串状态”升级为“受控状态模型”，为后续冲突检测和恢复提供结构基础。
- 改造点：
  - 新增 `HandoffStatus` 枚举：`PENDING/WAITING/RUNNING/SUCCEEDED/FAILED/CANCELLED`
  - 为 `HandoffRecord` 增加 `version`、`updatedAt`、`idempotencyKey`、`errorCode` 字段
  - `HandoffResult.status` 统一使用枚举值序列化输出
- 涉及文件：
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffRecord.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffResult.java`
  - 新增 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffStatus.java`
- 验收标准：
  - 代码中不再出现 `"COMPLETED"/"FAILED"` 这类硬编码交接状态字面量
  - 状态输出仍兼容现有接口字段

#### T-P2-HOF-02：新增交接状态机与迁移守卫（复杂度 `L3`）

- 目标：将状态跃迁规则显式化，避免并发与异常路径出现非法迁移。
- 改造点：
  - 新增 `HandoffStateMachine`，集中管理合法迁移
  - 迁移守卫包含：重复完成、失败后重入、取消后重试等非法场景
  - 迁移失败统一抛出可识别错误码（建议：`HANDOFF_INVALID_TRANSITION`）
- 涉及文件：
  - 新增 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffStateMachine.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffService.java`
- 验收标准：
  - `HandoffService` 所有状态变更均经过状态机
  - 非法迁移可稳定复现并返回可追溯错误

#### T-P2-HOF-03：引入仓储与版本冲突检测（复杂度 `L3`）

- 目标：补齐交接记录生命周期存储，支持并发更新冲突检测。
- 改造点：
  - 新增 `HandoffRepository` 接口
  - 提供最小实现（先内存仓储，后续可替换数据层）
  - 增加 `compareAndSet` 版本更新接口，失败时返回冲突
- 涉及文件：
  - 新增 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffRepository.java`
  - 新增 `src/main/java/com/example/agent/orchestration/multiagent/handoff/InMemoryHandoffRepository.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffService.java`
- 验收标准：
  - 并发更新同一 `handoffId` 时，只有一个写入成功，其他请求得到冲突反馈
  - 冲突日志包含 `handoffId/expectedVersion/actualVersion`

#### T-P2-HOF-04：补齐幂等键与重复请求治理（复杂度 `L2`）

- 目标：保证调用重试不会产生重复交接记录。
- 改造点：
  - 在 `HandoffRequest` 中支持显式 `idempotencyKey`（无则按规则生成）
  - `HandoffService` 对相同幂等键返回同一结果（或同一 `handoffId`）
  - 记录幂等命中日志，便于故障排查
- 涉及文件：
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffRequest.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffService.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/HandoffRepository.java`
- 验收标准：
  - 同一幂等键重复调用不会新增记录
  - 幂等命中返回字段完整、状态一致

#### T-P2-HOF-05：Supervisor 链路接入等待态与恢复态（复杂度 `L3`）

- 目标：把 `awaitConsumes` 从“单次结果判断”提升为“可观测状态推进”。
- 改造点：
  - 进入依赖等待时推进 `WAITING`
  - 依赖满足后推进 `RUNNING`
  - 依赖超时推进 `FAILED`，并保留缺失 topic 明细
  - 发布 `TEAM_STATUS` 时补充 `handoffId/status/version/missingTopics`
- 涉及文件：
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/supervisor/SupervisorCoordinator.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/handoff/TopicDependencyCoordinator.java`
  - 修改 `src/main/java/com/example/agent/orchestration/multiagent/MultiAgentEventPublisher.java`
- 验收标准：
  - 交接全过程存在连续状态轨迹
  - 依赖等待超时可从事件直接定位到缺失 topic

#### T-P2-HOF-06：状态一致性测试补齐（复杂度 `L2`）

- 涉及文件：

#### T-P2-BP-04：网关统一发布背压/熔断事件（复杂度 `L3`）
