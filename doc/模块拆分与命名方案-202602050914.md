# 模块拆分与命名方案（基于现有包结构）

**目标**
在保持现有包结构风格的前提下，细化“Step I/O、Structured、Evidence、Hook 收口”的模块拆分与命名规则，便于新工程落地与后续扩展。

**现有包结构概览（关键域）**
`com.example.agent.agentcore`：工具执行与安全控制。
`com.example.agent.runtime`：步骤运行、状态机与记录。
`com.example.agent.context`：上下文快照、证据包、装配输入。
`com.example.agent.tools.hook`：Hook 管理与执行。
`com.example.agent.model`：Prompt 组装、模型调用。
`com.example.agent.memory`：记忆召回与写入。
`com.example.agent.research`：研究引用生成。
`com.example.agent.streaming`：事件与回放载荷。

**推荐模块拆分（维持现有命名风格）**

`1. runtime（步骤编排核心）`
职责：管理步骤生命周期、输出契约落库、回放查询。
建议新增子包：
`com.example.agent.runtime.io`
- `StepInput`、`StepOutput`、`StepMeta`、`StepUpstream`
- `StepSummary`、`StepError`、`StepTiming`

`com.example.agent.runtime.raw`
- `RawRef`、`RawResultStore`、`RawResultMeta`

`com.example.agent.runtime.structured`
- `StructuredResult`、`StructuredQuality`、`StructuredRefs`
- `ResultKind`
- `StructuredExtractor`、`StructuredExtractorRegistry`

`com.example.agent.runtime.summary`
- `SummaryBuilder`（或对齐现有 `StepOutputSummaryBuilder`）
- `SummaryLimits`、`SummaryTruncation`

`2. context（上下文与证据索引）`
职责：EvidencePack 结构与上下文快照。
建议新增子包：
`com.example.agent.context.evidence`
- `EvidencePack`、`EvidenceItem`、`EvidenceStats`
- `EvidenceRef`、`EvidenceDigest`
- `EvidencePackService`

`com.example.agent.context.snapshot`
- `ContextSnapshot`、`WorkingMemory`、`RuntimeMeta`
- `TaskIntent`、`RoleBoundary`、`ToolState`

`com.example.agent.context.assembly`
- `PromptAssemblyInput`
- `ContextAssembler`、`DefaultContextAssembler`

`3. tools.hook（证据收口与生命周期事件）`
职责：Hook 统一入口与证据写入收口。
建议新增类：
- `EvidencePackHookHandler`：接收 `postTool/postRecall/postResearch/postTrim`，写入 `EvidencePack`。
- `HookPayloadMapper`：统一将 `HookContext` 映射为 `EvidenceDigest`。

`4. agentcore（工具执行与原始结果）`
职责：执行工具与模型，产出 `raw` 并落库。
建议新增：
- `RawResultWriter`：统一 `raw` 存储与 `RawRef` 生成。
- `ToolExecutionResult`：替代散落 `Map`，保留 `rawRef` 与核心元信息。

`5. model（模型调用与 Prompt 组装）`
职责：模型调用、Prompt 组装、EvidencePack 注入。
建议新增：
- `EvidencePackFormatter`：将 `EvidencePack` 渲染为可注入提示词段落。
- `PromptInjectionPolicy`：统一注入顺序（structured → summary → refs）。

`6. memory/research（数据来源与证据生成）`
职责：召回、研究与引用产出。
建议调整：
- 仅产出业务结果，不直接写证据。
- 证据写入由 `Hook` 统一收口。

**命名规范建议**
- `*Service`：具备流程与副作用的服务类。
- `*Repository`：数据持久化接口。
- `*Result`：执行产物。
- `*Request`：请求输入。
- `*Summary`：摘要对象。
- `*Ref`：引用或指针类型。
- `*Registry`：注册表或路由器。
- `*Extractor`：结构化抽取器。
- `*Handler`：事件处理或 Hook 处理器。

**模块边界与依赖方向**
- `runtime` 依赖 `structured` 与 `summary`，但不依赖 `context.evidence` 的写入逻辑。
- `context` 只维护证据索引与快照，不参与 `runtime` 编排。
- `tools.hook` 可依赖 `context.evidence`，但业务层不可反向依赖 `tools.hook`。
- `agentcore` 只产 `raw`，不参与 `structured/summary/evidence`。

**对齐现有类的映射建议**
- `StepRuntimeService` → 迁入 `runtime` 主流程，补齐 `StepOutput` 契约落库。
- `StepOutputSummaryBuilder` → 迁入 `runtime.summary`，并使其优先基于 `structured`。
- `EvidencePackService` → 迁入 `context.evidence`，仅追加与统计。
- `ToolExecutor` → 迁入 `agentcore`，只输出 `rawRef`。
- `HookManager` → 保持 `tools.hook`，新增证据收口处理器。

**最小落地路线（避免过度拆分）**
阶段一：新增 `runtime.structured` 与 `runtime.raw` 包，补齐 `StructuredResult` 与 `RawRef`。
阶段二：新增 `context.evidence` 包，迁移 `EvidencePack` 与 `EvidencePackService`。
阶段三：新增 `tools.hook.EvidencePackHookHandler`，将证据写入集中到 Hook。

**结论**
建议以 `runtime/structured/raw/summary` 与 `context/evidence` 为核心扩展包，保持现有包风格，形成“编排主流程 + 证据收口”的稳定结构。该拆分能最小化对现有模块的扰动，同时满足格式规范的设计目标。
