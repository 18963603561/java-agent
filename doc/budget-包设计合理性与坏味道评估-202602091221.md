# budget 包设计合理性与坏味道评估

## 1. 评审范围与方法

- 评审范围：`src/main/java/com/example/agent/budget` 下 `cost`、`token`、`trim` 三个子包。
- 代码规模统计：`cost` 1 个文件/20 行，`token` 13 个文件/1439 行，`trim` 17 个文件/2753 行，总计约 4212 行。
- 结构观察：`trim` 代码量占比约 65.4%，复杂度明显集中在 `trim` 子包。
- 验证动作：执行定向单测
  - `mvn "-Dtest=ContextCompressionControllerTest,DefaultContextBudgetAllocatorTest,DefaultContextPrunerPolicyTest,DefaultContextPrunerTest,DefaultContextTrimmerTest" test`
  - 结果：9 个测试全部通过。

## 2. 总体结论（等级）

- 总体设计等级：`B-`
- 风险等级：`P2（中风险）`
- 结论摘要：
  - 当前包拆分方向是合理的，核心能力链路完整（预算分配 -> 裁剪 -> 压缩 -> 指标/日志）。
  - 但存在明显的结构债务：双向包依赖、超大类、重复估算逻辑、并发细节风险。
  - 现状可运行、可测试，但在未来功能扩展和多人协作阶段，维护成本会快速上升。

## 4. 坏味道分级清单（P0-P4）

### P0（阻断级）

- 本次未发现直接阻断发布的问题。

### P1（高优先级）

#### 问题 1：`token` 与 `trim` 存在双向依赖（包循环）

- 证据：
  - `token` 依赖 `trim`：
    - `src/main/java/com/example/agent/budget/token/ContextBudgetAllocation.java:4`
    - `src/main/java/com/example/agent/budget/token/ContextBudgetProperties.java:9`
  - `trim` 反向依赖 `token`：
    - `src/main/java/com/example/agent/budget/trim/ContextTrimRequest.java:4`
    - `src/main/java/com/example/agent/budget/trim/DefaultContextTrimmer.java:31`
- 风险：
  - 破坏分层稳定性，后续重构或模块拆分时容易“牵一发而动全身”。
  - 对测试替身隔离和模块独立发布不友好。
- 建议：
  - 抽取 `budget-core`（仅保留 `ContextSection`、预算模型、策略模型）为稳定内核。
  - `token` 与 `trim` 只依赖 `budget-core`，互不直接依赖。

#### 问题 2：`DefaultContextTrimmer` 过大且职责混杂（大类坏味道）

- 证据：
  - 文件体量很大（1083 行），入口方法承载流程编排、策略执行、估算、统计、文本裁剪：
    - `src/main/java/com/example/agent/budget/trim/DefaultContextTrimmer.java:59`
    - `src/main/java/com/example/agent/budget/trim/DefaultContextTrimmer.java:724`
    - `src/main/java/com/example/agent/budget/trim/DefaultContextTrimmer.java:930`
- 风险：
  - 修改任一裁剪细节都可能影响全局，回归验证范围大。
  - 新人接手成本高，代码评审难度高。
- 建议：
  - 拆为“流程编排 + 各 section 裁剪器 + 估算器 + 统计器”四类角色。
  - 保留 `DefaultContextTrimmer` 仅做 orchestrator。

### P2（中优先级）

#### 问题 3：内存仓储实现存在并发与可变对象泄漏风险

- 证据：
  - `ConcurrentHashMap` value 使用 `ArrayList`，并发写无保护：
    - `src/main/java/com/example/agent/budget/token/InMemoryTokenUsageRepository.java:17`
    - `src/main/java/com/example/agent/budget/token/InMemoryTokenUsageRepository.java:30`
  - 查询返回内部列表对象，外部可改写：
    - `src/main/java/com/example/agent/budget/token/InMemoryTokenUsageRepository.java:37`
- 风险：
  - 高并发下可能出现数据竞争、丢写、`ConcurrentModificationException`。
  - 外部误改内部状态，导致统计结果不稳定。
- 建议：
  - value 改为线程安全容器（如 `CopyOnWriteArrayList` 或同步封装）。
  - `findByTask` 返回不可变副本。

#### 问题 4：`ContextCompressionController` 仍是“多职责大类”

- 证据：
  - 触发判定、冷却、外部调用、摘要回填、估算均在同一类：
    - `src/main/java/com/example/agent/budget/trim/ContextCompressionController.java:41`
    - `src/main/java/com/example/agent/budget/trim/ContextCompressionController.java:69`
    - `src/main/java/com/example/agent/budget/trim/ContextCompressionController.java:346`
- 风险：
  - 与 `DefaultContextTrimmer` 职责重叠（估算函数重复），演进中容易逻辑漂移。
- 建议：
  - 抽取公共 `ContextTokenEstimator`。
  - 压缩触发策略、摘要回填策略独立成组件。

#### 问题 5：估算逻辑重复，存在一致性漂移隐患

- 证据：
  - `estimateSectionTokens` 及大量 `estimateXxxTokens` 在两处重复：
    - `src/main/java/com/example/agent/budget/trim/DefaultContextTrimmer.java:724`
    - `src/main/java/com/example/agent/budget/trim/ContextCompressionController.java:346`
- 风险：
  - 一处修复另一处漏改，导致“裁剪前后”和“压缩触发”判定不一致。
- 建议：
  - 建立单一估算组件并共享，统一测试基线。

#### 问题 6：`TokenBudgetManager` 职责聚合偏重

- 证据：
  - 同时承担记录、汇总、阈值判断、降级决策、事件发布：
    - `src/main/java/com/example/agent/budget/token/TokenBudgetManager.java:69`
    - `src/main/java/com/example/agent/budget/token/TokenBudgetManager.java:101`
    - `src/main/java/com/example/agent/budget/token/TokenBudgetManager.java:154`
    - `src/main/java/com/example/agent/budget/token/TokenBudgetManager.java:170`
- 风险：
  - 该类成为单点复杂中心，后续接入更多预算策略时容易继续膨胀。
- 建议：
  - 拆分 `UsageRecorder`、`BudgetThresholdEvaluator`、`BudgetEventPublisher`。

### P3（低优先级）

#### 问题 7：`allocate` 通过 `null` 表示“未启用”语义不清晰

- 证据：
  - `src/main/java/com/example/agent/budget/token/DefaultContextBudgetAllocator.java:34`
  - `src/main/java/com/example/agent/budget/token/DefaultContextBudgetAllocator.java:38`
- 风险：
  - 调用方必须广泛判空，分支易遗漏。
- 建议：
  - 使用显式对象（如零预算对象）或 `Optional` 表达“无分配”。

#### 问题 8：命名语义与 Spring 角色不完全一致

- 证据：
  - `ContextCompressionController` 使用 `@Service`：
    - `src/main/java/com/example/agent/budget/trim/ContextCompressionController.java:40`
    - `src/main/java/com/example/agent/budget/trim/ContextCompressionController.java:41`
- 风险：
  - 代码阅读时对层次定位产生误判。
- 建议：
  - 命名改为 `ContextCompressionService` 或 `ContextCompressionOrchestrator`。

### P4（建议优化）

#### 问题 9：`cost` 子包仅有单类，包粒度略细

- 证据：
  - `src/main/java/com/example/agent/budget/cost/CostCalculator.java:1`
- 风险：
  - 当前风险很低，更多是结构整洁性问题。
- 建议：
  - 若短期无扩展，可并入 `token` 下 `pricing` 或 `billing` 子域；若未来会扩展成本策略则可保留。

## 5. 分阶段改造建议

### 第一阶段（1 个迭代，先降风险）

- 处理 P1：消除 `token` 与 `trim` 循环依赖。
- 将估算逻辑抽到共享组件，先消除重复判定。
- 修复内存仓储并发与可变返回问题。

### 第二阶段（1~2 个迭代，提升可维护）

- 拆分 `DefaultContextTrimmer` 与 `ContextCompressionController`。
- 拆分 `TokenBudgetManager` 多职责。
- 将 `null` 语义改为显式对象语义。

### 第三阶段（持续演进）

- 统一命名规范与包层次命名。
- 完善契约级测试：估算一致性、裁剪策略一致性、压缩触发一致性。

## 6. 结论复述

- 当前 `budget` 包“可用且已有基础工程化能力”，但架构债务已出现并开始堆积。
- 建议按 `P1 -> P2 -> P3` 顺序推进，优先解决循环依赖与大类问题。
- 若完成第一阶段改造，预计总体等级可由 `B-` 提升到 `B+` 或 `A-`。
